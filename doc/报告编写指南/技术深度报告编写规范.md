# 技术深度报告编写规范 v1.0

## 一、核心写作哲学（三大铁律）

在动笔前，必须将以下三条原则内化为文档的灵魂：

1. **动机驱动（Motivation First）**：永远不要从“它是什么”开始，而要从“它出现之前的世界有多痛”开始。读者只有理解了痛点，才能真正理解设计的精妙。
2. **概念锚定（Concept Anchoring）**：每个抽象的技术概念（如虚拟 DOM、Fiber、依赖预构建）必须配备一个**日常生活类比**（“新人小结”），用已知解释未知。
3. **结构化迭代（Structured Iteration）**：遵循“背景 → 目的 → 架构 → 细节 → 原理 → 流程 → 历史”的认知闭环，这是人类学习复杂系统的自然路径。

---

## 二、强制性大纲结构（七章黄金法则）

任何技术报告必须严格包含以下七个章节，顺序不可调换：

| 章节             | 核心任务                  | 定位与作用                                   |
| :------------- | :-------------------- | :-------------------------------------- |
| **一、设计背景**     | 讲述技术诞生前的“黑暗时代”，引出核心痛点 | 从宏观演进讲起、历史演进脉络（历史溯源）、旧技术的局限、催生该技术的决定性因素 |
| **二、设计目的**     | 明确该技术要达成的终极目标（非功能特性）  | 目标宣言、明确工具要解决什么问题、达成什么目标                 |
| **三、完整技术设计架构** | 建立全景心智模型（鸟瞰图）         | **整体架构图**、核心模块职责划分、建立心智模型               |
| **四、设计细节**     | 深入关键模块的实现肌理           | 拆解关键模块的具体实现原理、核心算法原理、关键数据结构、边界情况处理      |
| **五、工作原理**     | 解析运行时/编译时的执行流程        | 从"执行流程"角度解析各个阶段、**流程图**、时序关系            |
| **六、工作流程**     | 贴合开发者日常操作的实用指南        | 从开发者日常操作角度梳理典型场景、初始化、调试、部署、迁移、性能调优的具体步骤 |
| **七、发展历程**     | 呈现版本演进脉络与未来趋势         | 回顾版本迭代，展望未来趋势、关键版本里程碑、生态变迁、下一代技术方向      |

---

## 三、详细的编写标准（写作风格与格式规范）

### 1. 叙事视角与语调
*   **视角**：资深工程师/技术布道者给团队做内部培训。既要有专业深度，又要有一颗“想教会新人”的同理心。
*   **语调**：客观、冷静、结构化，但在关键时刻（如对比优劣、揭示巧妙设计时）要有适度的“兴奋点”。

### 2. 强制组件：新人小结（Newcomer's Summary）
*   **触发条件**：每当引入一个难以理解的核心抽象概念时，要完整清晰解释这个概念。
*   **格式**：使用 `> **新人小结**` 引用块。
*   **内容要求**：必须包含一个**生活化类比**，将技术逻辑映射为物理世界的常识。

### 3. 数据可视化策略
*   **对比表格**：涉及对比时，必须使用 Markdown 表格，维度包含：**维度名称**、**方案 A**、**方案 B**、**胜出原因**。
*   **ASCII 流程图**：对于复杂的生命周期或请求链路，必须使用缩进箭头绘制分层流程图，不能用大段文字描述顺序，必须用视觉引导。
*   **最小化代码示例**：代码只用于说明核心逻辑，拒绝粘贴大段业务代码。

### 4. 术语管理
*   首次出现关键术语时，必须在括号内给出中文全称。
*   对于争议性设计，必须在设计细节章节中解释**为什么要这样设计**（Trade-off 分析）。

## 四、给 AI 模型的完整 Prompt 模板（可直接复制使用）

将此模板复制并填入 `[技术/框架名称]` 和 `[核心特性]`，即可生成定制化需求。

```markdown
# 角色设定
你是一位拥有 10 年软件设计与开发经验的架构师，擅长撰写内部技术参考文档。你的读者是包含零基础新人在内的开发团队。

# 核心任务
撰写一份关于 **[请在此处填写技术名称，例如：React]** 的深度技术报告。

# 输出要求（必须严格遵守）
请严格按照以下七章结构输出，并遵循“动机驱动”和“概念锚定”原则：

## 第一章：设计背景
- 回溯该技术诞生前的行业痛点（至少列举 3 个历史阶段或旧框架的缺陷）。
- 描述催生该技术的决定性外部因素（如：硬件发展、语言标准更新）。

## 第二章：设计目的
- 以列表形式列出该技术的 6-10 个核心设计目标。
- 每个目标需包含：具体描述 + 一句话概括的“核心价值”。

## 第三章：完整技术设计架构
- **必须绘制整体架构图**（使用 Markdown 代码块或缩进层级关系图）。
- 解构核心模块（如：Core、Renderer、Compiler）及其职责。
- 阐述核心模块之间的通信机制。

## 第四章：设计细节
- 深入 5-8 个最核心的技术细节（如：Diffing 算法、依赖收集机制、调度器实现）。
- 对每个细节，必须提供最小化的代码示例或数据结构定义。
- **强制要求**：针对最抽象的概念，插入一个 `> **新人小结**`，使用生活化类比进行解释。

## 第五章：工作原理
- 从“运行时/编译时”角度出发。
- 绘制核心流程的完整生命周期（如：启动流程 → 请求处理 → 更新机制）。
- 使用文本流程图（如：`A → B → C`）展示顺序。

## 第六章：工作流程
- 以“开发者视角”撰写日常操作指南（如：初始化、迁移、调试、性能分析）。
- 提供针对性的故障排查步骤（如：“如果遇到 X 问题，请检查 Y 和 Z”）。

## 第七章：发展历程
- 按时间线列出关键大版本的发布时间及核心特性。
- 预测该技术未来 1-3 年的演进方向。

# 写作风格约束
1. 语调：专业、结构化，但保持亲和力。
2. 表格：比较性质的内容必须使用 Markdown 表格。
3. 代码：仅用于说明原理，保持精简。
4. 禁止：堆砌无意义的 API 列表，专注于“为什么这么设计”和“如何工作的”。
```

## 五、辅助性 Prompt 增强技巧（针对特定章节）

如果你对某个章节的质量不满意，可以使用以下**增强 Prompt** 单独强化：

### 1. 强化“设计背景”（提升历史纵深感）
> “请扩充第一章的背景描述，重点说明 [技术 A] 和 [技术 B] 在解决 [某类问题] 上的根本缺陷是什么？并描述浏览器/硬件在那段时间发生了哪些关键变化，让新技术有了可乘之机。”

### 2. 强化“架构图”（提升视觉逻辑）
> “请重新绘制第三章的架构图，必须采用分层结构。顶部为用户层，中间为核心层（包含 [模块1]、[模块2]），底部为基础设施层。箭头必须标注数据的流向是自上而下还是双向。”

### 3. 强化“工作原理”（强制流程化）
> “请将第五章的内容重写。不要平铺直叙，请以 `执行命令 ->` 为起点，分解为 **8 个关键步骤**，并说明每个步骤输入和输出的数据结构变化。”

### 4. 强制生成“新人小结”（确保易读性）
> “请检查全文，在涉及 [核心抽象概念] 的地方，强制插入一个‘新人小结’部分。利用物理世界（如文件柜、流水线、转换器）的类比来解释这个计算机科学概念。”

## 六、最终交付检查清单（Quality Checklist）

在模型生成文档后，请对照以下清单进行验收，确保不偏离规范：

- [ ] **是否包含七章结构**？（缺少任何一章视为不合格）
- [ ] **是否从“历史痛点”而非“功能介绍”开篇**？
- [ ] **是否包含至少一个 ASCII 架构图或分层图**？
- [ ] **是否包含至少三个对比表格**？
- [ ] **对于核心算法，是否给出了简化版的数据结构定义（Interface/Type）**？
- [ ] **是否为最晦涩的概念提供了“新人小结”类比**？
- [ ] **是否区分了“开发模式”和“生产模式”（或“运行时”与“编译时”）的行为差异**？

---

通过这套规范，你可以让任何大语言模型稳定输出像 Vite 和 React 报告那样**兼具历史深度、架构广度和新人友好度**的高质量技术文档。
