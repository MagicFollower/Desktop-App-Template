# 两个 tsconfig 配置文件的设计与解析机制分析

用户提到的两个 `tsconfig` 配置文件（`tsconfig.main.json` 与根目录 `tsconfig.json`）是 **TypeScript 项目多配置文件的典型实践**。它们的核心设计意图是 **“分离关注点”** ——为项目中两个截然不同的运行环境（Electron 主进程与浏览器渲染进程）分别提供独立的编译设置。


## 一、为什么需要两个 tsconfig 文件？

**核心答案：因为“主进程”和“渲染进程”运行在完全不同的 JavaScript 环境中，它们对代码编译的要求完全不同。**

### 1.1 环境差异决定配置差异

| 对比维度 | 主进程 (main) | 渲染进程 (renderer) |
| :--- | :--- | :--- |
| **运行环境** | **Node.js** 桌面端 | **浏览器** 或 Electron 沙盒 |
| **模块规范** | **CommonJS** (`require`) | **ES Module** (`import`) |
| **可用 API** | `fs`、`path`、`process` 等 Node API | **DOM API** (`window`、`document`) |
| **JSX/TSX** | **不需要**（纯逻辑） | **需要**（React UI 组件） |
| **输出位置** | `dist/main/` | 由 Vite 处理（`dist/renderer/`） |
| **类型检查目标** | 主进程代码 | 渲染进程 React 代码 |

> **💡 认知桥接**
>
> 可以想象成一家餐厅有两间厨房：
> - **主厨房**（主进程）：做**传统热菜**（Node.js 风格），用中式炒锅（CommonJS）。
> - **甜品间**（渲染进程）：做**精致蛋糕**（React UI），用进口烤箱（ES Module）和裱花工具（JSX）。
>
> 两间厨房用的设备（module）、操作规范（`lib`）、出菜口（`outDir`）完全不同。如果让他们共用一张菜单（同一个 `tsconfig`），不是热菜做不好，就是蛋糕烤砸了。


### 1.2 具体配置差异（关键点解析）

**① 模块系统差异：`"module": "commonjs"` vs `"module": "ESNext"`**

| 配置 | `tsconfig.main.json` | 根目录 `tsconfig.json` |
| :--- | :--- | :--- |
| **模块格式** | `commonjs` | `ESNext` |
| **输出代码** | Node.js 风格的 `require()` | 浏览器原生 ESM `import` |
| **为什么要这样？** | Electron 主进程是 Node.js 进程，必须使用 CommonJS | Vite 开发服务器和现代浏览器原生支持 ESM，无需转译 |
| **对开发的影响** | `import` 被编译为 `require` | `import` 保留为 ESM 格式 |

> **💡 深度理解**
>
> 在 Node.js 中运行 ESM 是可行的（通过 `.mjs` 或 `"type": "module"`），但在 Electron 主进程中使用 CommonJS 是最稳定、最兼容的方式——许多原生 Node 模块（如 `fs`、`path`）在 CommonJS 下工作更可靠。`tsc` 会将你写的 `import` 语法自动转换为 `require` 调用，输出 `dist/main/` 中的 `.js` 文件可以直接被 Node.js 执行。

**② 运行环境 API 差异：`"lib": ["ES2020"]` vs `"lib": ["ES2020", "DOM"]`**

| 配置 | `tsconfig.main.json` | 根目录 `tsconfig.json` |
| :--- | :--- | :--- |
| **包含的 API 类型** | 仅 ECMAScript 标准库 | ECMAScript + 浏览器 DOM API |
| **允许的全局对象** | `Buffer`、`process`、`__dirname` | `window`、`document`、`localStorage` |
| **为什么会报错？** | 在 main 中写 `document.getElementById` 会报错 `Cannot find name 'document'` | 在 renderer 中写 `process.cwd()` 会报错（除非额外配置） |
| **为什么这样设计？** | 防止在主进程中意外使用浏览器 API | 为 React 组件提供完整的 DOM 类型检查 |

> **💡 深度理解**
>
> `lib` 决定了 TypeScript 在类型检查时**承认哪些全局对象是合法的**。主进程中没有任何 DOM 对象，因此不需要加载 `dom` 类型定义库，这不仅能防止意外误用浏览器 API，还能略微提升类型检查速度。渲染进程中要操作 DOM、监听事件、访问 `localStorage`，这些都需要 `dom` 库提供的类型定义才能通过类型检查。

**③ JSX 支持差异：`无配置` vs `"jsx": "react-jsx"`**

| 配置 | `tsconfig.main.json` | 根目录 `tsconfig.json` |
| :--- | :--- | :--- |
| **JSX 支持** | **不配置**（不允许 JSX 语法） | **启用** `react-jsx` |
| **作用** | 主进程文件若包含 `<div>` 会报错 | 支持 React 17+ 的新 JSX Transform |
| **为什么要这样？** | 主进程纯逻辑，不需要处理 UI 标签 | 渲染进程是 React 应用，必须有 JSX 编译 |

> **💡 深度理解**
>
> 在根目录 `tsconfig.json` 中设置 `"jsx": "react-jsx"` 意味着 TypeScript 期望你使用 React 17+ 的 **Automatic Runtime**。编译时，`<div>Hello</div>` 会被自动转换为 `import { jsx } from 'react/jsx-runtime'`，而不需要你在每个文件里写 `import React from 'react'`。在主进程中，如果意外写了 JSX，TypeScript 会直接报错，将错误扼杀在编码阶段。

**④ 输出与构建差异：`"outDir"` vs `"noEmit": true`**

| 配置 | `tsconfig.main.json` | 根目录 `tsconfig.json` |
| :--- | :--- | :--- |
| **输出位置** | `"outDir": "dist/main"` | `"noEmit": true`（不输出文件） |
| **谁负责编译？** | **tsc** 直接生成 `.js` 文件 | **Vite/esbuild** 负责转换，`tsc` 只做类型检查 |
| **为什么要这样？** | 主进程需要可执行的 `.js` 文件 | 渲染进程的编译由 Vite 完成，`tsc` 仅作为类型检查器 |

> **💡 深度理解**
>
> 根目录 `tsconfig.json` 中的 `"noEmit": true` 是一个关键设计决策。它告诉 `tsc`：**不要输出任何 `.js` 或 `.d.ts` 文件**。这意味着 Vite 在开发时负责将 TS/TSX 编译为浏览器可执行的 JS，而 `tsc` 只在后台做类型检查（通过 VSCode 或 `tsc --noEmit` 命令）。这种 **“分离编译与类型检查”** 的模式是现代前端工具链（Vite、Next.js）的标准实践，目的是大幅提升开发速度——esbuild 编译 TS 比 tsc 快 50-100 倍。


## 二、两个 tsconfig 分别在哪里被使用？

### 2.1 `tsconfig.main.json` 的使用场景

**解析器**：**TypeScript 编译器（`tsc`）**

**使用方式**：通过 `package.json` 中的 `build:main` 脚本**显式指定**：

```json
{
  "scripts": {
    "build:main": "tsc -p tsconfig.main.json"
  }
}
```

**解析时机**：**执行 `npm run build:main` 时**

**解析流程**：
1. 终端执行 `npm run build:main`
2. npm 调用 `tsc -p tsconfig.main.json`
3. `tsc` 读取该配置文件
4. 根据配置编译 `src/main/**/*.ts` 中的代码
5. 输出到 `dist/main/`


### 2.2 根目录 `tsconfig.json` 的使用场景

这个配置文件有两个主要使用者：

#### 场景一：VSCode / IDE 的 TypeScript 语言服务（最主要的使用者）

**解析器**：**VSCode 内置的 TypeScript 语言服务器（`tsserver`）**

**何时解析**：
- 打开项目时
- 每次保存 `.ts`/`.tsx` 文件时
- 执行“类型检查”、“自动补全”、“跳转定义”时

**工作原理**：

```
开发者打开 VSCode
        ↓
VSCode 启动 TypeScript 语言服务
        ↓
检测到项目根目录存在 tsconfig.json
        ↓
读取配置，应用类型检查规则
        ↓
在编辑器中实时显示类型错误、提供智能提示
```

#### 场景二：Vite 构建过程（通过 esbuild）

**解析器**：**Vite 的依赖预构建和 TS 转换流程**

**使用方式**：Vite 会**自动读取根目录的 `tsconfig.json`**，但**用途有限**——主要用于：
- 确定路径别名（`paths` 配置）
- 确定目标 ECMAScript 版本（`target`）
- 其他与编译相关的有限配置

**何时解析**：
- 执行 `npm run dev`（Vite 开发服务器启动时）
- 执行 `npm run build:renderer`（渲染进程构建时）


## 三、完整的解析流程与时机对比

### 3.1 时序总览

| 命令 | 涉及文件 | 解析器 | 解析时机 |
| :--- | :--- | :--- | :--- |
| `npm run dev` | `tsconfig.json` | VSCode（实时）、Vite（启动时） | 启动瞬间 + 每次文件变更 |
| `npm run build:main` | `tsconfig.main.json` | TypeScript Compiler (tsc) | 命令执行时（一次性） |
| `npm run build:renderer` | `tsconfig.json` | Vite → esbuild（部分配置） | 命令执行时（一次性） |

### 3.2 详细解析流程

#### 流程一：开发模式（`npm run dev`）

```
用户执行 npm run dev
        ↓
Vite 开发服务器启动
  → 读取根目录 tsconfig.json
  → 提取 paths（路径别名）、target、lib 等
  → 配置 esbuild 的编译选项
        ↓
Vite 监听文件变化
  → 当 .tsx 文件被编辑时
  → Vite 调用 esbuild 进行转换（逐文件、极速）
  → esbuild 读取 tsconfig.json 中的部分配置
  → 生成浏览器可执行的 JS 代码
        ↓
与此同时（独立、并行）：
  → VSCode 的 TypeScript 语言服务实时监控
  → 读取 tsconfig.json 的完整配置
  → 在编辑器中显示类型错误、提供智能提示
```

#### 流程二：主进程构建（`npm run build:main`）

```
用户执行 npm run build:main
        ↓
npm 执行：tsc -p tsconfig.main.json
        ↓
tsc 编译器启动
  → 读取 tsconfig.main.json 的完整配置
  → 解析 include 模式：src/main/**/*.ts
  → 加载所有匹配的 .ts 文件
  → 进行全项目类型检查（跨文件）
  → 编译输出：.ts → .js
  → 输出到 outDir: dist/main/
  → 同时生成 .d.ts 声明文件和 .map 文件
```

#### 流程三：渲染进程构建（`npm run build:renderer`）

```
用户执行 npm run build:renderer
        ↓
Vite 调用 Rollup 执行生产构建
  → Vite 读取 vite.renderer.config.ts
  → 检测到 tsconfig.json 的存在
  → 读取 tsconfig.json 中的 paths 和 target 配置
  → Rollup 调用 @rollup/plugin-typescript 或 esbuild
  → 执行 TS/TSX 编译
  → 输出到 dist/renderer/
        ↓
（注意：此时 tsc 并未直接参与编译）
（类型检查已经在开发阶段由 VSCode 完成）
```


## 四、多个 tsconfig 配置文件的通用设计模式

### 4.1 共享基础配置 + 环境特化（推荐模式）

如果项目有更多进程（如 Preload 脚本、Worker 等），可以采用 **“基础配置 + 继承”** 的模式：

```
tsconfig.base.json          ← 所有配置的公共基础
  │
  ├── tsconfig.main.json    ← 主进程（Node.js）
  ├── tsconfig.renderer.json ← 渲染进程（浏览器 + React）
  ├── tsconfig.preload.json  ← Preload 脚本（特殊环境）
  └── tsconfig.test.json     ← 测试环境（Jest）
```

**基础配置示例**：

```json
// tsconfig.base.json
{
  "compilerOptions": {
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true,
    "resolveJsonModule": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true
  }
}
```

**继承基础配置**：

```json
// tsconfig.main.json
{
  "extends": "./tsconfig.base.json",
  "compilerOptions": {
    "target": "ES2020",
    "module": "commonjs",
    "lib": ["ES2020"],
    "outDir": "dist/main",
    "rootDir": "src/main"
  },
  "include": ["src/main/**/*.ts"]
}
```

### 4.2 多个配置的解析与引用关系

在 monorepo 或多进程 Electron 应用中，每个 `tsconfig.*.json` 的解析器和引用关系可能是：

| 配置文件 | 解析器 | 引用者 | 用途 |
| :--- | :--- | :--- | :--- |
| `tsconfig.main.json` | `tsc` | `package.json` → `build:main` | 主进程编译 |
| `tsconfig.renderer.json` | `tsc` + VSCode | `vite.renderer.config.ts` | 渲染进程类型检查 + 路径别名 |
| `tsconfig.preload.json` | `tsc` | `package.json` → `build:preload` | Preload 脚本编译 |
| `tsconfig.json` | VSCode / Vite | 根目录（默认） | 开发时类型检查 + 路径解析 |

### 4.3 解析器的选择原则

| 场景 | 推荐解析器 | 原因 |
| :--- | :--- | :--- |
| **生产构建（需要输出 JS 文件）** | `tsc -p` | 类型安全、完整检查、可靠输出 |
| **日常开发（需要实时反馈）** | VSCode 语言服务 | 类型检查 + 智能提示 + 即时错误反馈 |
| **极速开发（需要即时编译）** | esbuild / swc（通过 Vite） | 速度至上，类型检查由 IDE 负责 |


## 五、如何快速查看当前哪些配置正在生效？

### 方法一：在 VSCode 中查看正在使用的 TypeScript 配置

1. 在 VSCode 中打开任意 `.ts` 文件
2. 点击右下角的 **TypeScript 版本号**（如 `3.0.0`）
3. 在弹出的菜单中选择 **“显示正在使用的配置文件”**
4. VSCode 会显示当前工作区正在使用的 `tsconfig` 文件路径

### 方法二：手动执行 `tsc` 并指定配置

```bash
# 查看特定配置文件的解析结果
npx tsc -p tsconfig.main.json --showConfig

# 查看根目录配置的解析结果
npx tsc -p tsconfig.json --showConfig
```

### 方法三：检查 `package.json` 中的脚本

```json
{
  "scripts": {
    // 以下脚本会显式指定使用哪个配置文件
    "build:main": "tsc -p tsconfig.main.json",
    "build:renderer": "vite build --config vite.renderer.config.ts",
    "type-check": "tsc --noEmit",  // 默认使用根目录 tsconfig.json
    "type-check:main": "tsc -p tsconfig.main.json --noEmit"
  }
}
```


## 六、总结

| 问题 | 答案 |
| :--- | :--- |
| **为什么有 2 个配置文件？** | 主进程（Node.js）与渲染进程（浏览器+React）的运行环境完全不同，需要独立的编译配置 |
| **`tsconfig.main.json` 在哪里使用？** | 由 `tsc -p tsconfig.main.json` 显式调用，用于构建主进程代码 |
| **根目录 `tsconfig.json` 在哪里使用？** | 由 VSCode 语言服务（日常开发）和 Vite 构建过程（部分配置）使用 |
| **它们被什么解析？** | `tsc`、VSCode `tsserver`、Vite/esbuild |
| **如果还有多个呢？** | 可以采用 `tsconfig.base.json` 作为公共配置，通过 `extends` 继承，每个进程/环境维护自己的特化配置 |

**核心原则**：
- **`tsc`** 负责**构建输出**（生成 `.js`）—— 主进程使用它
- **VSCode** 负责**类型检查**（IDE 实时反馈）—— 渲染进程使用它
- **Vite/esbuild** 负责**极速编译**（开发 HMR）—— 渲染进程使用它
- **多个配置 = 多个环境**，每个环境各取所需，互不干扰
