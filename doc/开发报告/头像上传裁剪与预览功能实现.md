### 1.3 为什么选择"裁剪 + 压缩合一"的单 Canvas 方案

最初的设计是两步走：先用 Canvas 压缩图片到 200×200，再保存。引入裁剪需求后，面临一个选择：

**方案 A：裁剪和压缩分两步**
1. 裁剪弹窗输出裁剪后的 dataURL
2. 拿到裁剪结果后再创建第二个 Canvas 做压缩

缺点：两次 Canvas 操作、两次 `toDataURL` 编码、中间产物多一次内存分配。

**方案 B：裁剪和压缩合二为一（最终方案）**

裁剪弹窗的 `handleConfirm` 直接从原图裁出目标区域，绘制到 200×200 的输出 Canvas 上，一次性 `toDataURL('image/jpeg', 0.85)` 完成压缩。

```typescript
// 一步到位：裁剪 + 缩放 + 压缩
const out = document.createElement('canvas');
out.width = 200;
out.height = 200;
octx.drawImage(img, srcX, srcY, srcSize, srcSize, 0, 0, 200, 200);
onConfirm(out.toDataURL('image/jpeg', 0.85));
```

选择方案 B 的理由：
- 裁剪的目标区域本身就要缩放到 200×200 输出，`drawImage` 的 9 参数形式天然支持"从源矩形绘制到目标矩形"
- JPEG 压缩在 `toDataURL` 时自动完成，不需要额外步骤
- 内存峰值更低：只有一个输出 Canvas，无需保留中间裁剪结果

## 第 2 章：文件选择与前置校验

### 2.1 实现代码

```typescript
const MAX_AVATAR_SIZE = 2 * 1024 * 1024; // 2MB

const handleAvatarSelected = (e: React.ChangeEvent<HTMLInputElement>) => {
  const file = e.target.files?.[0];
  // 清空 value，保证连续选择同一文件也能触发 change
  e.target.value = '';
  if (!file) return;
  if (!file.type.startsWith('image/')) {
    setMessage({ type: 'error', text: '只能上传图片文件（jpg / png / gif / webp）' });
    return;
  }
  if (file.size > MAX_AVATAR_SIZE) {
    setMessage({ type: 'error', text: '图片大小不能超过 2MB' });
    return;
  }

  // 读取为 dataURL 后打开裁剪弹窗
  const reader = new FileReader();
  reader.onload = (readEvent) => {
    const result = String(readEvent.target?.result || '');
    setCropSrc(result);
    setCropVisible(true);
  };
  reader.onerror = () => setMessage({ type: 'error', text: '头像读取失败，请重试' });
  reader.readAsDataURL(file);
};
```

### 2.2 文件类型校验

使用 `file.type.startsWith('image/')` 做 MIME 类型前缀匹配：

- **覆盖范围**：`image/jpeg`、`image/png`、`image/gif`、`image/webp`、`image/svg+xml`、`image/bmp` 等所有浏览器识别的图片格式
- **局限性**：
  - 依赖浏览器对 MIME 类型的识别，极少数情况下文件扩展名被篡改可能导致误判
  - SVG 虽然是图片但不适合做头像（矢量图无法裁剪为位图），不过后续 Canvas `drawImage` 会正常处理
  - `<input accept="image/*">` 在文件选择器层面已做了初步过滤，这里的校验是二次保险

### 2.3 文件大小限制

`MAX_AVATAR_SIZE = 2MB` 的设定考量：

- 头像最终会被裁剪压缩到 200×200 JPEG 0.85，输出体积通常在 5-30KB
- 2MB 的限制是为了防止用户选择超大原图（如手机拍摄的 10MB+ 照片）导致：
  - FileReader 读取耗时过长
  - Image 解码占用大量内存
  - Canvas 绘制卡顿
- 原图大小与输出质量无直接关系（无论原图多大，输出都是 200×200），但过大的原图会影响裁剪弹窗的交互流畅度

### 2.4 关键细节：清空 input value

```typescript
e.target.value = '';
```

这一行解决了一个容易被忽略的问题：**连续选择同一个文件时 `onChange` 不会触发**。

浏览器 `<input type="file">` 的行为是：只有当 `value` 变化时才触发 `change` 事件。如果用户选择了一张图片、取消裁剪、再次选择同一张图片，由于 `value` 与上次相同，事件不会触发。

在每次 `onChange` 回调开头清空 `value`，保证下次选择时 `value` 从空变为文件路径，事件必然触发。

### 2.5 FileReader 读取时序

```
FileReader.readAsDataURL(file)
    │  （异步读取，不阻塞 UI）
    ▼
reader.onload 触发
    │
    ├── setCropSrc(dataURL)   → 设置裁剪弹窗的图片源
    └── setCropVisible(true)  → 打开裁剪弹窗
```

为什么不在 `onChange` 中直接打开弹窗？因为弹窗需要 `imageSrc` 来初始化 Canvas，而 `imageSrc` 必须是完整的 dataURL。FileReader 的读取是异步的，必须等 `onload` 回调拿到完整数据后才能打开弹窗。

## 第 3 章：Canvas 圆形裁剪算法

这是整个头像功能中最核心、最复杂的部分。裁剪算法的正确性直接决定了用户体验——如果约束有 bug，用户会看到裁剪区域内出现黑边或空白。

### 3.1 方案选型对比

| 方案 | 优点 | 缺点 | 评估 |
|------|------|------|------|
| `react-cropper` / `cropperjs` | 功能全面（矩形/圆形/自由裁剪） | 新增 ~50KB 依赖，API 重，与现有压缩逻辑耦合复杂 | 杀鸡用牛刀 |
| `react-easy-crop` | 交互优秀（双指缩放等） | 新增依赖，输出格式需额外处理才能接入压缩流程 | 集成成本高 |
| **纯 Canvas 自实现** | **零依赖、完全可控、裁剪压缩合一** | 需手写拖拽/缩放/约束逻辑 | **最优** |

选择纯 Canvas 的决策理由：

1. **项目已有 Canvas 压缩逻辑**，技术栈一致，不需要引入新的图像处理范式
2. **裁剪和压缩可以合二为一**（见第 1.3 节），零新增依赖，包体无增长
3. **交互需求明确且有限**：只需圆形区域内的拖拽 + 缩放，不需要旋转、自由选区等高级功能
4. **核心代码量可控**：裁剪算法 + 交互约 270 行，提取公共方法后每个 handler 仅 3-5 行

### 3.2 画布坐标系与常量定义

```typescript
const SIZE = 300;   // 画布 CSS 尺寸（像素）
const R = 120;      // 圆形裁剪半径
const OUTPUT = 200; // 输出头像尺寸（与压缩逻辑一致）
```

三个常量的关系：

- `SIZE` 是用户看到的画布大小（300×300）
- `R` 定义了圆形可视区域的半径（直径 240，占画布 80%）
- `OUTPUT` 是最终输出的头像尺寸（200×200，独立于画布尺寸）

**圆形区域在画布上的坐标范围：**

```
圆形中心 = (SIZE/2, SIZE/2) = (150, 150)
圆形左边界 = SIZE/2 - R = 150 - 120 = 30
圆形右边界 = SIZE/2 + R = 150 + 120 = 270
圆形上边界 = 30
圆形下边界 = 270
```

**空间关系图解：**

```
    0         30              270   300
  0 +----------+---------------+----+
    |          |               |    |
    |  遮罩区  |               |    |
    |          |               |    |
 30 +----------+---------------+----+
    |          |   圆形可视区域 |    |
    |          |   (240×240)   |    |
    |          |    中心(150,150)   |
    |          |               |    |
270 +----------+---------------+----+
    |          |               |    |
    |  遮罩区  |               |    |
    |          |               |    |
300 +----------+---------------+----+
```

图片绘制在 `(x, y)` 位置，尺寸为 `(naturalWidth * scale, naturalHeight * scale)`。用户的拖拽和缩放改变 `x`、`y`、`scale` 三个值，但圆形区域始终固定在画布中心。

### 3.3 clamp 约束函数（区域限制核心）

#### 问题定义

无论用户如何拖拽或缩放，**圆形区域内的每一个像素都必须有图片覆盖**。如果图片移出了圆形区域，裁剪时就会裁到空白（黑色）区域。

#### 数学推导

设图片在画布上的绘制位置为 `(x, y)`，绘制尺寸为 `dw = naturalWidth * scale`，`dh = naturalHeight * scale`。

圆形区域的范围是 `[SIZE/2 - R, SIZE/2 + R]`，即 `[30, 270]`。

**X 轴约束：**

```
条件 1：图片左边界 ≤ 圆形左边界
    x ≤ SIZE/2 - R
    即 x ≤ 30

条件 2：图片右边界 ≥ 圆形右边界
    x + dw ≥ SIZE/2 + R
    即 x ≥ SIZE/2 + R - dw
    即 x ≥ 270 - dw
```

综合：`maxX = SIZE/2 - R`，`minX = SIZE/2 + R - dw`

**Y 轴同理：** `maxY = SIZE/2 - R`，`minY = SIZE/2 + R - dh`

**最终代码：**

```typescript
const clamp = useCallback((x: number, y: number, s: number) => {
  const img = imgRef.current;
  if (!img) return { x, y };
  const dw = img.naturalWidth * s;
  const dh = img.naturalHeight * s;
  const edge = SIZE / 2 - R; // 圆形区域左/上边界 = 30
  const maxX = edge;
  const minX = SIZE / 2 + R - dw; // 圆形区域右/下边界 - 图片宽
  const maxY = edge;
  const minY = SIZE / 2 + R - dh;
  return {
    x: Math.max(Math.min(x, maxX), minX),
    y: Math.max(Math.min(y, maxY), minY),
  };
}, []);
```

#### 踩坑记录：第一版 clamp 的推导错误

**第一版代码：**

```typescript
// 错误版本
const cx = SIZE / 2;
const cy = SIZE / 2;
const minX = cx - R - dw + cx;  // 化简后 = SIZE - R - dw = 180 - dw
const maxX = R;                  // = 120
```

**错误分析：**

原作者的意图可能是从中心点出发推导，但 `cx - R - dw + cx` 的化简结果是 `2*cx - R - dw = SIZE - R - dw`，而非正确的 `SIZE/2 + R - dw`。

| 约束 | 错误值 | 正确值 | 数值对比（dw=240） |
|------|--------|--------|---------------------|
| maxX | `R = 120` | `SIZE/2 - R = 30` | 宽松了 90px |
| minX | `SIZE - R - dw = 180 - dw` | `SIZE/2 + R - dw = 270 - dw` | 宽松了 90px |

**后果：** 约束过于宽松。以 `dw = 240` 为例：

- 错误的 `maxX = 120`：图片可以放到 `x = 120`，此时图片覆盖 `[120, 360]`，但圆形左边界在 `30` → `[30, 120]` 这段 90px 的区域没有图片覆盖 → **黑边**
- 正确的 `maxX = 30`：图片最多放到 `x = 30`，图片覆盖 `[30, 270]`，刚好覆盖圆形 `[30, 270]` → 正确

**修复过程：**

发现问题后，重新从基本定义推导（即 3.3 节中的数学推导），直接使用 `SIZE/2 - R` 和 `SIZE/2 + R` 的显式计算，避免中间变量化简引入的错误。

#### 前提条件

clamp 约束成立的前提是 `dw >= 2R` 且 `dh >= 2R`（图片绘制尺寸不小于圆形直径）。如果图片比圆形小，`minX > maxX`，`Math.max(Math.min(x, maxX), minX)` 会返回 `minX`，此时图片无法覆盖整个圆形。

这个前提由缩放下限 `minS` 保证（见 3.4 节）。

### 3.4 缩放控制与边界

#### 缩放范围计算

```typescript
const getScaleRange = () => {
  const img = imgRef.current!;
  const minDim = Math.min(img.naturalWidth, img.naturalHeight);
  const minS = (R * 2) / minDim; // 短边刚好填满圆形直径
  return { minS, maxS: minS * 4 };
};
```

**为什么 `minS` 是缩放下限：**

`minS = 2R / minDim` 的含义是：将图片的短边缩放到刚好等于圆形直径（240px）。

- 如果图片是 600×400（短边 400），`minS = 240/400 = 0.6`，缩放后尺寸为 360×240
- 短边 240 = 圆形直径，满足 `dh >= 2R`
- 长边 360 > 240，有富余可以在圆形区域内水平移动

低于 `minS` 时，短边 < 240，图片无法覆盖圆形 → clamp 失效 → 黑边。

**`maxS = minS * 4` 的考量：** 4 倍放大提供足够的细节查看能力，同时不会因过度放大导致像素模糊。

#### 中心锚点缩放

缩放时以画布中心为锚点，保证用户关注的中心区域不偏移：

```typescript
const applyScale = (newScale: number) => {
  const cx = SIZE / 2;
  const { scale: oldS, x: oldX, y: oldY } = stateRef.current;
  // 中心锚点公式：新位置 = 中心 - (中心 - 旧位置) × (新缩放 / 旧缩放)
  const newX = cx - (cx - oldX) * (newScale / oldS);
  const newY = cx - (cx - oldY) * (newScale / oldS);
  const pos = clamp(newX, newY, newScale);
  stateRef.current = { scale: newScale, x: pos.x, y: pos.y };
  draw();
};
```

**公式推导：** 设画布中心为 `cx`，图片某像素在旧缩放下的画布坐标为 `oldX`。该像素在图片上的相对位置为 `(oldX - 0) / oldScale`（假设以图片左上角为原点）。缩放后，该像素的新画布坐标应为 `newX = oldX * (newScale / oldScale)`。但我们要以 `cx` 为锚点，所以需要平移：`newX = cx - (cx - oldX) * (newScale / oldScale)`。

#### 滚轮与滑块的一致性

滚轮和滑块是两种不同的交互方式，但必须产生一致的缩放行为：

```typescript
// 滚轮：乘法因子
const handleWheel = (e: React.WheelEvent) => {
  const { minS, maxS } = getScaleRange();
  const factor = e.deltaY > 0 ? 0.92 : 1.08;
  const newScale = Math.max(minS, Math.min(stateRef.current.scale * factor, maxS));
  applyScale(newScale);
  syncZoomSlider(newScale);
};

// 滑块：线性映射
const handleZoomChange = (e: React.ChangeEvent<HTMLInputElement>) => {
  const val = Number(e.target.value);
  setZoomValue(val);
  const { minS, maxS } = getScaleRange();
  applyScale(minS + (val / 100) * (maxS - minS));
};
```

两者共用 `getScaleRange()` 和 `applyScale()`，保证：
- 滚轮缩放到最小值时，滑块也在最左端（`zoomValue = 0`）
- 滑块拖到最右端时，缩放等于 `maxS`

**踩坑记录：** 最初滚轮用硬编码 `Math.max(0.5, Math.min(..., 5))` 做边界，而滑块用动态 `minS` / `maxS`。当 `minS > 0.5` 时，滚轮的最小值比滑块更小，导致：
1. 滚轮可以缩到比 `minS` 更小的值 → 图片无法覆盖圆形 → 黑边
2. 滚轮和滑块的行为不一致，体验割裂

修复后两者统一使用 `getScaleRange()` 返回的动态边界。

#### 代码重构：消除重复

在修复上述问题前，`minS` / `maxS` 的计算和中心锚点缩放公式在 `handleWheel`、`handleZoomChange`、`handleReset` 中各出现一次（每处约 10 行）。提取公共方法后：

- `getScaleRange()` — 计算有效缩放范围
- `applyScale(newScale)` — 中心锚点缩放 + clamp + 重绘
- `syncZoomSlider(currentScale)` — 同步滑块位置

三个 handler 各自简化为 3-5 行，只保留特有逻辑。

### 3.5 裁剪输出

用户点击"确认裁剪"后，需要从原图中裁出圆形区域对应的正方形区域，并压缩输出。

#### 坐标反算

裁剪弹窗中维护的是画布坐标系下的 `(x, y, scale)`，需要映射回原图像素坐标：

```typescript
const handleConfirm = () => {
  const img = imgRef.current;
  if (!img) return;
  const { x, y, scale: s } = stateRef.current;
  const cx = SIZE / 2;
  const cy = SIZE / 2;

  // 圆形区域中心在原图上的坐标
  const srcCx = (cx - x) / s;
  const srcCy = (cy - y) / s;

  // 裁剪正方形边长（原图像素）
  const srcHalf = R / s;
  const srcX = srcCx - srcHalf;
  const srcY = srcCy - srcHalf;
  const srcSize = srcHalf * 2;

  // 输出 200×200，JPEG 0.85 压缩
  const out = document.createElement('canvas');
  out.width = OUTPUT;
  out.height = OUTPUT;
  const octx = out.getContext('2d');
  if (!octx) return;
  octx.drawImage(img, srcX, srcY, srcSize, srcSize, 0, 0, OUTPUT, OUTPUT);
  onConfirm(out.toDataURL('image/jpeg', 0.85));
};
```

**反算原理：**

- 画布上圆心坐标为 `(cx, cy) = (150, 150)`
- 图片绘制在 `(x, y)` 位置，缩放为 `s`
- 圆心在图片上的坐标 = `(圆心画布坐标 - 图片绘制坐标) / 缩放` = `((cx - x) / s, (cy - y) / s)`
- 圆形半径 `R` 在画布上是 120px，在原图上是 `R / s` 像素

**`drawImage` 的 9 参数形式：**

```
drawImage(image, srcX, srcY, srcSize, srcSize, dstX, dstY, dstW, dstH)
```

从原图的 `(srcX, srcY, srcSize, srcSize)` 矩形区域，绘制到目标 Canvas 的 `(0, 0, 200, 200)` 矩形区域。浏览器自动完成缩放插值。

**输出格式：** `toDataURL('image/jpeg', 0.85)` — JPEG 格式，质量 0.85。这是项目原有的压缩参数，保持不变。输出体积通常在 5-30KB，远小于 2MB 的上传限制。

## 第 4 章：Canvas 绘制层叠结构

裁剪弹窗的视觉效果由 `draw()` 函数控制，每次用户交互（拖拽、缩放）都会重新执行。

### 4.1 四层绘制顺序

```typescript
const draw = useCallback(() => {
  const canvas = canvasRef.current;
  const img = imgRef.current;
  if (!canvas || !img) return;
  const ctx = canvas.getContext('2d');
  if (!ctx) return;

  const { x, y, scale: s } = stateRef.current;

  // 第 1 层：清空画布
  ctx.clearRect(0, 0, SIZE, SIZE);

  // 第 2 层：绘制缩放后的图片
  const dw = img.naturalWidth * s;
  const dh = img.naturalHeight * s;
  ctx.drawImage(img, x, y, dw, dh);

  // 第 3 层：半透明遮罩（圆形"挖洞"效果）
  ctx.save();
  ctx.beginPath();
  ctx.rect(0, 0, SIZE, SIZE);
  ctx.arc(SIZE / 2, SIZE / 2, R, 0, Math.PI * 2, true); // 注意 true = 逆时针
  ctx.fillStyle = 'rgba(0, 0, 0, 0.45)';
  ctx.fill();
  ctx.restore();

  // 第 4 层：圆形白色边框 + 中心十字参考线
  ctx.beginPath();
  ctx.arc(SIZE / 2, SIZE / 2, R, 0, Math.PI * 2);
  ctx.strokeStyle = '#fff';
  ctx.lineWidth = 2;
  ctx.stroke();

  ctx.beginPath();
  ctx.moveTo(SIZE / 2 - 10, SIZE / 2);
  ctx.lineTo(SIZE / 2 + 10, SIZE / 2);
  ctx.moveTo(SIZE / 2, SIZE / 2 - 10);
  ctx.lineTo(SIZE / 2, SIZE / 2 + 10);
  ctx.strokeStyle = 'rgba(255,255,255,0.4)';
  ctx.lineWidth = 1;
  ctx.stroke();
}, []);
```

### 4.2 遮罩的"挖洞"技巧

第 3 层的遮罩效果是：圆形区域外覆盖半透明黑色，圆形区域内保持图片原色。这是通过 Canvas 的路径填充规则实现的。

**原理：**

```typescript
ctx.beginPath();
ctx.rect(0, 0, SIZE, SIZE);                    // 顺时针：整个画布
ctx.arc(SIZE / 2, SIZE / 2, R, 0, Math.PI * 2, true); // 逆时针：圆形区域
ctx.fillStyle = 'rgba(0, 0, 0, 0.45)';
ctx.fill();
```

关键在 `ctx.arc(..., true)` 的最后一个参数 `true`，表示逆时针绘制。

Canvas 默认使用 **non-zero winding rule**（非零环绕规则）填充路径：
- 外矩形顺时针绘制，环绕数 +1
- 内圆形逆时针绘制，环绕数 -1
- 圆形区域内的总环绕数 = +1 + (-1) = 0 → **不填充**
- 圆形区域外的环绕数 = +1 → **填充半透明黑色**

效果：圆形区域"挖空"，保持第 2 层绘制的图片原色；圆形外覆盖半透明黑色遮罩。

### 4.3 视觉层次的作用

| 层 | 内容 | 作用 |
|----|------|------|
| 第 1 层 | `clearRect` | 清除上一帧的绘制内容，防止残影 |
| 第 2 层 | `drawImage` | 用户操作的主体：缩放/平移后的图片 |
| 第 3 层 | 半透明遮罩 | 视觉上突出圆形区域，暗示"只有这里会被保留" |
| 第 4 层 | 白色边框 + 十字线 | 明确圆形边界，十字线辅助对准中心 |

## 第 5 章：Hover 气泡预览

### 5.1 方案演进

头像预览功能经历了三次迭代，每次都有明确的问题驱动：

**第一版：Modal 弹窗**

```tsx
<Modal visible={previewVisible} title="头像预览" width={240}>
  <img src={userInfo.avatar} />
</Modal>
```

- 点击头像打开弹窗，关闭点击 ×
- 问题：弹窗太宽（480px 默认 → 调为 240px），一个头像预览不需要这么大的空间

**第二版：全屏灯箱（Portal）**

```tsx
{previewVisible && createPortal(
  <div className="avatar-lightbox" onClick={close}>
    <button className="close-btn">×</button>
    <img src={...} onWheel={zoom} onPointerDown={drag} />
    <span>滚轮缩放 · 拖拽移动 · ESC 关闭</span>
  </div>,
  document.body
)}
```

- 全屏黑色遮罩，图片居中，支持滚轮缩放和拖拽平移
- 问题：对于"看一眼头像"这个简单需求，全屏遮罩过于重量级；需要 Portal 解决 `position: fixed` 被祖先容器约束的问题

**第三版：Hover 气泡（最终方案）**

```tsx
<div className="avatar-hover-wrapper">
  <div className="avatar-preview">...</div>
  <div className="avatar-bubble">
    <div className="avatar-bubble-arrow" />
    <img src={userInfo.avatar} />
  </div>
</div>
```

- 鼠标悬停在头像上时，右侧弹出聊天气泡式的大图预览
- 纯 CSS 控制显隐，零 JS 状态

### 5.2 最终方案的纯 CSS 实现

#### 核心结构

```html
<div class="avatar-hover-wrapper">  <!-- 相对定位容器 -->
  <div class="avatar-preview">      <!-- 头像（120×120 圆形） -->
    <img src="..." />
  </div>
  <div class="avatar-bubble">       <!-- 气泡预览（200×200） -->
    <div class="avatar-bubble-arrow"></div>  <!-- 三角箭头 -->
    <img src="..." />
  </div>
</div>
```

#### 关键 CSS

```css
/* 包裹容器：为气泡提供定位上下文 */
.avatar-hover-wrapper {
  position: relative;
  display: inline-block;
}

/* 气泡：绝对定位在头像右侧，默认隐藏 */
.avatar-bubble {
  position: absolute;
  left: calc(100% + 12px);   /* 头像右边 + 12px 间距 */
  top: 50%;
  transform: translateY(-50%); /* 垂直居中 */
  width: 200px;
  height: 200px;
  opacity: 0;
  pointer-events: none;       /* 隐藏时不拦截鼠标事件 */
  transition: opacity 0.2s ease;
}

/* hover 时显示气泡 */
.avatar-hover-wrapper:hover .avatar-bubble {
  opacity: 1;
  pointer-events: auto;       /* 显示时允许鼠标进入气泡 */
}
```

#### 为什么气泡不会闪烁

关键设计：**气泡在 `avatar-hover-wrapper` 内部**。

```
avatar-hover-wrapper（hover 区域）
├── avatar-preview（头像）
└── avatar-bubble（气泡，absolute 定位溢出）
```

当鼠标从头像移向气泡时，虽然离开了 `avatar-preview`，但仍在 `avatar-hover-wrapper` 内（气泡虽然视觉上溢出，但 DOM 层级上仍是 wrapper 的子元素）。因此 `:hover` 状态不会中断，气泡不会闪烁消失。

如果气泡是 wrapper 的兄弟元素而非子元素，鼠标离开头像后、进入气泡前的 12px 间距期间，`:hover` 会丢失 → 气泡消失 → 鼠标又进入头像 → 气泡又出现 → 无限闪烁。

#### `pointer-events` 的配合

- `pointer-events: none`（隐藏时）：气泡虽然 `opacity: 0` 不可见，但如果不移除指针事件，它会在头像右侧占据 200×200 的不可见区域，拦截该区域的鼠标事件
- `pointer-events: auto`（显示时）：允许鼠标进入气泡内部，用户可以在气泡区域内移动而不触发关闭

### 5.3 三角箭头的 CSS 实现

气泡左侧的三角箭头指向头像，使用经典的 `border` 三角形技巧：

```css
.avatar-bubble-arrow {
  position: absolute;
  left: -7px;              /* 箭头在气泡左边缘外侧 */
  top: 50%;
  transform: translateY(-50%);
  width: 0;
  height: 0;
  border-top: 8px solid transparent;
  border-bottom: 8px solid transparent;
  border-right: 8px solid var(--color-border);  /* 外层：边框色 */
}

/* 内层填充：覆盖在边框三角形内部，形成空心箭头边框效果 */
.avatar-bubble-arrow::after {
  content: '';
  position: absolute;
  left: 1px;
  top: -7px;
  width: 0;
  height: 0;
  border-top: 7px solid transparent;
  border-bottom: 7px solid transparent;
  border-right: 7px solid var(--color-bg-secondary);  /* 内层：背景色 */
}
```

**原理：** 一个 `width: 0; height: 0` 的元素，设置三边透明边框 + 一边有色边框，浏览器会渲染为一个三角形。`::after` 伪元素叠加一个稍小的同色三角形在内部，形成"带边框的箭头"效果。

### 5.4 为什么不用 JS 状态控制显隐

对比：

| 方案 | 代码量 | 运行时开销 | 闪烁风险 |
|------|--------|------------|----------|
| JS `useState` + `onMouseEnter/Leave` | ~15 行 | 每次 hover 触发 re-render | 需手动处理延迟/气泡连续性 |
| **纯 CSS `:hover`** | **0 行 JS** | **零运行时开销** | **DOM 结构天然避免** |

纯 CSS 方案的优势：
- 零 JS 状态 = 零 re-render，性能最优
- 不需要 `setTimeout` 做延迟关闭（CSS `transition` 天然平滑）
- 不需要计算鼠标是否在"头像 + 气泡"的联合区域内（DOM 层级天然保证）

## 第 6 章：保存、移除与即时生效

### 6.1 双写策略

头像的保存采用"先 store 后数据库"的双写策略：

```typescript
const applyPatch = async (patch: { nickname?: string; email?: string; phone?: string; avatar?: string }) => {
  updateUserInfo(patch);                                    // 第 1 步：Zustand store 即时更新
  await saveProfile({ username: userInfo.username, ...patch }); // 第 2 步：IPC → SQLite 持久化
};
```

**为什么先更新 store：**

- `updateUserInfo` 是同步操作，调用后所有订阅了 `userInfo` 的组件（Profile 页面、Header 头像、TabBar 等）立即 re-render
- 用户感知到"头像瞬间换了"，体验流畅
- 数据库写入是异步的（IPC 跨进程 + SQLite I/O），但不影响 UI 响应

**如果反过来（先数据库后 store）：**

- 用户点击保存 → 等待 IPC 往返（~10-50ms）→ store 更新 → UI 刷新
- 虽然延迟不大，但"先慢后快"不如"先快后慢"的体验好

### 6.2 头像存储方式

头像以 **base64 dataURL** 直接存入 `user_profiles.avatar` 字段：

```sql
INSERT INTO user_profiles (username, avatar)
VALUES (?, ?)
ON CONFLICT(username) DO UPDATE SET avatar = COALESCE(?, avatar)
```

**设计考量：**

| 方案 | 优点 | 缺点 |
|------|------|------|
| **base64 存数据库** | 简单、无文件管理开销、随数据库备份迁移 | 数据库体积增大、查询时需加载 base64 |
| 文件存储 + 数据库存路径 | 数据库轻量 | 需管理文件路径、清理孤立文件、处理跨平台路径差异 |

选择 base64 方案的理由：
- 头像输出为 200×200 JPEG 0.85，体积仅 5-30KB
- 即使 1000 个用户各有头像，总数据量约 5-30MB，SQLite 完全承受
- Electron 应用是单用户本地部署，不需要考虑网络传输 base64 的带宽问题
- 避免了文件路径管理、孤立文件清理等额外复杂度

### 6.3 localStorage 配额问题

`useAuthStore` 在更新 `userInfo` 时会尝试持久化到 `localStorage`：

```typescript
function persistUser(user: UserInfo): void {
  try {
    localStorage.setItem(USER_KEY, JSON.stringify(user));
  } catch {
    // 头像 base64 可能超出 localStorage 配额，此时仅保留内存状态
  }
}
```

**为什么需要 try/catch：**

- `localStorage` 的配额通常为 5-10MB
- base64 编码会使数据膨胀约 33%（30KB 的 JPEG → ~40KB 的 base64）
- 如果用户头像较大（接近 30KB）加上其他用户信息，JSON 序列化后可能接近或超出配额
- 持久化失败时，登录状态仍在内存中有效（`useAuthStore` 的内存状态不受影响），只是刷新页面后需要重新登录

### 6.4 移除头像

移除头像 = 将 `avatar` 设为空字符串：

```typescript
const handleRemoveAvatar = async () => {
  await applyPatch({ avatar: '' });
  setMessage({ type: 'success', text: '已恢复默认头像' });
};
```

UI 侧的条件渲染自动回退到首字母占位：

```tsx
{userInfo.avatar ? (
  <img src={userInfo.avatar} alt="用户头像" />
) : (
  <span className="avatar-fallback">
    {userInfo.username.slice(0, 1).toUpperCase()}
  </span>
)}
```

hover 气泡也通过 `{userInfo.avatar && <div className="avatar-bubble">...}` 条件渲染，移除头像后气泡自动消失。

## 第 7 章：问题排查与修复记录

### 7.1 滚轮缩放无法到最小值

**现象：** 滚轮向下滚动（缩小方向）时，缩放级别无法到达滑块的最小值位置。

**根因：** `handleWheel` 使用硬编码 `Math.max(0.5, Math.min(..., 5))` 做缩放边界，而 `handleZoomChange` 使用动态计算的 `minS = (R * 2) / minDim`。当图片较小导致 `minS > 0.5` 时：

- 滚轮的最小值是 0.5
- 滑块的最小值是 `minS`（如 1.2）
- 两者不一致：滚轮能缩到比滑块更小的值，但那个值低于 `minS` → 图片无法覆盖圆形 → 黑边

**修复：** 滚轮改用与滑块完全一致的 `getScaleRange()` 返回的 `minS` / `maxS` 边界。

```typescript
// 修复前
const newScale = Math.max(0.5, Math.min(stateRef.current.scale * factor, 5));

// 修复后
const { minS, maxS } = getScaleRange();
const newScale = Math.max(minS, Math.min(stateRef.current.scale * factor, maxS));
```

### 7.2 裁剪区域出现黑边

**现象：** 拖拽图片到某些位置时，圆形裁剪区域内出现黑色空白。

**根因：** `clamp` 函数的约束公式推导错误（详见第 3.3 节）。

第一版代码：
```typescript
const cx = SIZE / 2;
const minX = cx - R - dw + cx;  // 化简后 = SIZE - R - dw = 180 - dw（错误）
const maxX = R;                  // = 120（错误）
```

正确应为：
```typescript
const edge = SIZE / 2 - R;           // = 30
const maxX = edge;                    // = 30
const minX = SIZE / 2 + R - dw;      // = 270 - dw
```

错误导致约束宽松了 90px，图片可以移到无法覆盖圆形区域的位置。

**修复：** 重新从基本定义推导，直接使用 `SIZE/2 - R` 和 `SIZE/2 + R` 的显式计算。

### 7.3 预览弹窗显示在左下角

**现象：** 全屏灯箱预览时，遮罩层和所有元素堆积在页面左下角，而非覆盖整个视口。

**根因：** 灯箱渲染在 `.app-content`（`overflow-y: auto` 的滚动容器）内部。虽然 `position: fixed` 理论上应相对于视口定位，但在 Electron 的渲染环境下，祖先容器的 `overflow: hidden`（`.app-layout`）+ `overflow-y: auto`（`.app-content`）组合可能导致 fixed 定位的包含块发生变化。

**修复过程：**

1. 首先尝试用 `createPortal` 将灯箱渲染到 `document.body`，彻底脱离组件树的布局约束 → 问题解决
2. 后来决定将预览方案从全屏灯箱改为 hover 气泡（纯 CSS 方案），从根本上避免了 `position: fixed` 的问题

### 7.4 预览弹窗过宽

**现象：** 头像预览的 Modal 弹窗宽度过大，一个头像不需要 480px 的空间。

**根因：** Modal 组件默认宽度 480px，预览场景不需要这么宽。

**修复：** 给 Modal 组件新增可选 `width` 属性：

```typescript
interface ModalProps {
  // ...
  width?: number;  // 新增
}

// 使用
<Modal visible={previewVisible} title="头像预览" width={240}>
```

后来预览方案改为 hover 气泡后，此 Modal 预览被整体移除，`width` 属性作为通用增强保留在 Modal 组件中。

### 7.5 问题排查总结

| 问题 | 类型 | 根因类别 | 修复复杂度 |
|------|------|----------|------------|
| 滚轮缩放无法到最小值 | 交互不一致 | 硬编码 vs 动态计算的边界不统一 | 低（统一边界） |
| 裁剪区域出现黑边 | 算法错误 | clamp 公式代数化简出错 | 中（重新推导） |
| 预览弹窗显示在左下角 | 布局异常 | `position: fixed` 被祖先 overflow 约束 | 中（Portal / 方案替换） |
| 预览弹窗过宽 | UI 适配 | Modal 默认宽度不适合预览场景 | 低（新增 width 属性） |

**核心教训：**

1. **数学公式不要依赖中间变量化简** — 直接用显式的 `SIZE/2 - R` 而非 `cx - R - dw + cx`，减少化简出错的可能
2. **交互边界必须统一** — 同一功能的多种交互方式（滚轮/滑块/重置）必须共用同一个边界计算函数
3. **`position: fixed` 不是万能的** — 在复杂布局嵌套中，祖先的 `overflow`/`transform`/`filter` 都可能影响 fixed 定位，Portal 是安全的兜底方案
