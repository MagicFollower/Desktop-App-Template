## 1. 十分钟架构速览

### 1.1 三进程与「数据六层通路」

Electron 应用 = **主进程**（Node 环境，管窗口和数据库）+ **渲染进程**（React 应用）+ **preload 桥**（安全地把主进程能力暴露给页面）。本项目所有数据操作都走同一条六层通路：

```
[渲染进程 React]                              [主进程 Node]
DocRuleManagement.tsx   （页面：交互与展示）
  └─ services/sqlite.ts （门面：稳定入口）
      └─ services/adapter.ts（工厂：启动时三选一）
          ├─ IpcAdapter ──→ preload.ts(electronAPI) ──IPC──→ ipc/doc.ts ──┐
          ├─ HttpAdapter ──→ http://127.0.0.1:5174 ────────→ api-server.ts ┤→ service.ts（业务）
          └─ FallbackAdapter（纯浏览器演示数据，动态加载）              │    └─ SqlDriver → app-data.db
                                                                        └──→ dto.ts（类型单一源，全链共享）
```

一次「保存」的完整旅程：页面 `handleSave` → `services/sqlite.ts` 门面函数 → adapter（Electron 环境自动选中 IpcAdapter）→ preload 暴露的 `electronAPI.xxx` → IPC channel → `ipc/doc.ts` 薄壳 → `service.ts` 业务函数 → SqlDriver → `app-data.db` 落盘。

**为什么要这么多层？** 因为同一个页面要能在三种环境跑：Electron 窗口（IPC）、浏览器连 Dev API（HTTP，方便用浏览器 DevTools 调试）、纯浏览器（演示兜底）。adapter 工厂把这些差异从每个业务函数里抽走了——你写页面时**永远不需要判断自己在哪个环境**。

### 1.3 八条铁律（先背下来，后面每一步都在用）

1. **类型只有一个源**：跨进程类型全部定义/引用自 `src/main/dto.ts`；渲染端对它只做 `import type`（编译后完全擦除，不进 bundle，也绕开了主进程 tsconfig 的 `rootDir: src/main` 限制）。
2. **snake_case 不出 service 层**：数据库行是 snake_case（`created_at`），service 出口必须映射成 camelCase DTO（`createdAt`），渲染层不写 `?? ''` 兜底。
3. **写完必 persist**：默认驱动 sql.js 是全内存引擎，任何写函数最后必须 `db.persist()`，否则重启丢数据。
4. **绑定值不许 undefined**：sql.js 绑定 undefined 会直接抛 `tried to bind a value of an unknown type`，可选字段统一 `?? null` 归一。
5. **迁移只增不改**：schema 变更一律**追加**新 migration（内部要幂等），禁止回头修改历史 migration——老用户的库已经跑过旧版本了。
6. **preload 禁运行时 import 主进程模块**：preload 跑在独立的渲染上下文，运行时 import `service/database` 链会在加载阶段炸掉 → contextBridge 注册失败 → **白屏**。只有 `import type` 例外。
7. **纯函数放模块顶层**：`useQueryTable` 的 `filter`、以及一切想测试的逻辑，都要是模块作用域的纯函数（不依赖组件内可变状态）。
8. **加菜单动三处**：schema 种子（Electron/HTTP 环境）、`dev-fallback.ts`（纯浏览器环境）、`Sidebar.tsx` 的 `pathToMenuId` 映射（选中态高亮）。只改一处会出现"菜单看得到但点击不高亮"或"换个环境菜单就消失"的灵异现象。

## 2. 需求分析：把「单据号」想清楚

> 新手最大的误区是"拿到需求就开表写代码"。先花半小时把需求翻译成模型，后面每一步都是在填空。

### 2.1 需求描述

业务系统里每张单据（采购单、报销单、出库单……）都需要一个**全局唯一、有序、可读**的编号。我们要做一个「单据号规则」功能：

- 管理员可以维护若干条规则，每条规则描述某一类单据的编号怎么生成；
- 规则支持指定**前缀**、**日期**（多种精度）、**流水号**（指定位数）；
- 支持流水号按周期**重置**（每日/每月/每年/不重置）；
- 业务方传入单据类型编码，系统**原子地**返回下一个单据号。

### 2.2 单据号长什么样

以 `PO-20260907-0001` 为例拆解：

```
PO-20260907-0001
│     │       │
│     │       └─ 流水号段：0001（4 位补零，同一周期内递增）
│     └─ 日期段：20260907（yyyyMMdd 格式）
└─ 前缀段：PO（固定文本）
      │
      └─ 分隔符：-（段与段之间，可空）
```

### 2.3 数据模型设计

**规则表 `doc_rules`（这是"配置"）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | 技术主键（`doc-<时间戳>`），页面生成 |
| code | TEXT UNIQUE | 单据编码（如 `PO`）——**业务主键**，取号凭据 |
| name | TEXT | 规则名称（采购入库单） |
| prefix | TEXT | 前缀段，可空 |
| date_type | TEXT | 日期段格式：`none`/`yyyy`/`yyyyMM`/`yyyyMMdd` |
| seq_length | INTEGER | 流水号位数 1–8 |
| reset_policy | TEXT | 重置周期：`never`/`daily`/`monthly`/`yearly` |
| separator | TEXT | 分隔符，可空 |
| enabled | INTEGER | 启用/停用 |
| remark | TEXT | 备注 |
| created_at / updated_at | TEXT | 时间戳 |

**计数表 `doc_counters`（这是"状态"）**

| 字段 | 类型 | 说明 |
|---|---|---|
| rule_code + reset_key | 联合主键 | 每个规则在每个周期一行 |
| seq | INTEGER | 当前流水值 |

### 2.4 五个关键设计决策（新手最容易跳过的部分）

**决策 1：dateType 用枚举，不用格式模板。**
更"灵活"的设计是让用户填 `PO{yyyy}{seq:4}` 这样的模板。但灵活的代价是：你要写模板解析器、要处理非法模板、预览和校验都变复杂。枚举四个选项 + 前缀 + 分隔符已覆盖 95% 的真实业务，且**每个组合都能被穷举测试**。模板化留作扩展点，不要一步到位。

**决策 2：规则与计数分两张表。**
规则是低频修改的配置，计数是高频递增的状态。混在一张表里，改规则时的 UPDATE 和取号时的 UPDATE 会互相干扰，而且"删除规则是否清计数"会变成一笔糊涂账。分开后语义干净：删规则 → 计数连带清理。

**决策 3：重置靠 reset_key 周期键，不靠定时任务。**
`resetKey(policy, now)` 把当前时间折叠成一个周期键：每日 → `20260907`，每月 → `202609`，每年 → `2026`，不重置 → `''`。取号时只对 `(rule_code, reset_key)` 这一行 +1。跨天自然落到新的 key 上、从 1 开始——**不需要任何定时任务，也不需要删旧数据**。这是整个设计里最省事的一笔。

**决策 4：取号必须放主进程事务里。**
这个应用有两个并发入口：Electron 窗口走 IPC，浏览器调试走 Dev API（HTTP）。两边可能同时取号。取号 = 读计数 +1 + 写回，如果不在同一个事务里，两个请求可能读到同一个值、发出重复的号。放在主进程 + `db.transaction` 包裹，两条通路天然汇入同一处串行执行。

**决策 5：code 编辑时锁定。**
code 是外部系统取号的凭据（业务代码里 `docNextNumber('PO')`），改 code 会让历史计数和外部引用全部脱钩。所以编辑弹窗里 code 输入框 `disabled`。这是产品决策，但要在表设计阶段就想清楚，不然做出来的表单会允许用户改。

### 2.5 边界与例外（需求完整性检查清单）

| 场景 | 行为 |
|---|---|
| 取号时规则不存在 | 抛错「单据规则不存在：XXX」，页面展示错误，不返回假号 |
| 取号时规则已停用 | 抛错「单据规则已停用」（停用 ≠ 删除，留有恢复余地） |
| 删除规则 | 事务内连带删除其全部计数 |
| 流水号超出位数（seq=12345，位数=4） | 不截断，输出 `12345`（截断会造成重号） |
| resetPolicy 与 dateType 不一致（按月重置但只显示年） | 允许——两者本就是独立维度，文档说明即可 |
| code 与其他规则重复 | SQLite UNIQUE 约束兜底抛错，页面 catch 后展示 |

## 3. Step 1 数据层：迁移 v4

### 做什么

在 `src/main/db/schema.ts` 的 `migrations[]` 数组**末尾**追加版本 4。

### 代码

```ts
{
  version: 4,
  description: '单据号规则：doc_rules 规则表 + doc_counters 计数表 + 菜单种子',
  up: (db) => {
    db.exec(`
      CREATE TABLE IF NOT EXISTS doc_rules (
        id TEXT PRIMARY KEY,
        code TEXT UNIQUE NOT NULL,
        name TEXT NOT NULL,
        prefix TEXT DEFAULT '',
        date_type TEXT NOT NULL DEFAULT 'none',
        seq_length INTEGER NOT NULL DEFAULT 4,
        reset_policy TEXT NOT NULL DEFAULT 'never',
        separator TEXT DEFAULT '',
        enabled INTEGER NOT NULL DEFAULT 1,
        remark TEXT,
        created_at TEXT NOT NULL,
        updated_at TEXT NOT NULL
      )
    `);
    db.exec(`
      CREATE TABLE IF NOT EXISTS doc_counters (
        rule_code TEXT NOT NULL,
        reset_key TEXT NOT NULL DEFAULT '',
        seq INTEGER NOT NULL DEFAULT 0,
        PRIMARY KEY (rule_code, reset_key)
      )
    `);
    // 菜单种子：系统管理下的新入口（roles 限 admin，与迁移 v3 的兄弟菜单一致）。
    // is_system=1 防止在菜单管理页被误删；INSERT OR IGNORE 保证幂等。
    db.exec(`
      INSERT OR IGNORE INTO menus (id, parent_id, label, icon, path, sort_order, is_system, roles) VALUES
        ('system-doc-rules', 'system', '单据号规则', 'FileTextOutlined', '/system/doc-rules', 3, 1, 'admin')
    `);
  },
},
```

### 为什么

- 每个迁移用 `PRAGMA user_version` 记账，启动时 `applySchemaAndSeed` 按序补跑未应用的版本。你的 v4 对新库（建库即 v4）和老库（停在 v3）都只需写一次。
- `up()` 会被包进 `db.transaction`（见 `applySchemaAndSeed`），DDL 在 SQLite 里可回滚，中途失败不会留半成品。
- 菜单也在这里种：**代码即版本**。用菜单管理页手工点出来的菜单，换台电脑/重建库就没了；写进迁移的菜单跟数据库结构一起演进。

### 验证

`npm run start` 启动一次（主进程启动即跑迁移），然后用 IDE 数据源（已配置 `app-data.db`）执行：

```sql
PRAGMA user_version;          -- 预期 4
SELECT * FROM menus WHERE id = 'system-doc-rules';   -- 预期 1 行
```

### 踩坑与经验

1. **千万别把建表写进 v1**。老用户库里 v1 已经执行过（user_version=3），回头改 v1 对他们不生效——只有新增的版本才会被补跑。
2. **迁移必须幂等**：建表用 `IF NOT EXISTS`、种子用 `INSERT OR IGNORE`。因为版本号写入失败重试时会再次执行同一版本。
3. 验证迁移时**不要**手删 `app-data.db` 了事——那只能证明"新库没问题"，证明不了"老库能升级"。两种情况都要看：留着旧库重启一次（升级路径）+ 删库重启一次（全新路径）。

## 4. Step 2 契约：dto.ts 定义类型

### 做什么

在 `src/main/dto.ts` 末尾追加单据号规则的 DTO。

### 代码

```ts
// ==================== 单据号规则 ====================

/** 日期段格式：none=无日期段 */
export type DocDateType = 'none' | 'yyyy' | 'yyyyMM' | 'yyyyMMdd';
/** 流水号重置周期：never=永不重置 */
export type DocResetPolicy = 'never' | 'daily' | 'monthly' | 'yearly';

/** 单据号规则记录：docRuleList 的返回 */
export interface DocRuleRecord {
  id: string;
  code: string;
  name: string;
  prefix: string;
  dateType: DocDateType;
  seqLength: number;
  resetPolicy: DocResetPolicy;
  separator: string;
  enabled: boolean;
  remark: string;
  createdAt: string;
  updatedAt: string;
}

/** 单据号规则保存入参（新增/更新共用；updatedAt 由服务端维护） */
export interface DocRuleInput {
  id: string;
  code: string;
  name: string;
  prefix?: string;
  dateType?: DocDateType;
  seqLength?: number;
  resetPolicy?: DocResetPolicy;
  separator?: string;
  enabled?: boolean;
  remark?: string;
}
```

### 为什么

- **类型即文档**。这两个接口同时被主进程（service 签名、IPC handler、preload）和渲染端（adapter、页面表单）引用——字段一改名，六处编译报错，你不可能漏改。这就是"DTO 单一类型源"（项目 A2 整改成果）的价值。
- 类型放 `src/main/dto.ts` 而不是新建 `src/shared/`：主进程 tsconfig 有 `rootDir: src/main` 限制，新建共享目录要动两份构建配置；而渲染端 `import type` 编译后完全擦除，从主进程目录引类型**零运行时成本**。
- 可选字段（`prefix?`）对应数据库可空列；必填字段由 service 层兜默认值，渲染端不做 `?? ''` 兜底（项目 A5 约定：契约字段除标注外均必填）。

### 踩坑与经验

1. 新手常在这里顺手在 `src/renderer/types/` 下再抄一份类型——**不要**。两份类型必然漂移，漂移三个月后就是一场迁移。
2. `import type` 和 `import` 的区别在这项目里是硬性的：渲染端 `import type` 主进程类型没问题，但普通 `import` 会把主进程代码卷进渲染 bundle（详见 Step 7 预览函数的处理）。

## 5. Step 3 业务层：纯函数 + service

这一步拆成两个文件，是刻意的：

- `doc-number.ts`：**纯函数**（不碰数据库、不碰 Electron）——组装、格式化、校验、周期键计算。放主进程目录是因为取号的"真身"在这，但因为它零依赖，**vitest 可以直接测**（Step 8）。
- `service.ts`：粘合层——SQL、事务、persist、snake→camel 映射。

### 5.1 新建 `src/main/doc-number.ts`

```ts
import type { DocDateType, DocResetPolicy, DocRuleRecord } from './dto';

/**
 * 单据号规则的纯逻辑：不碰数据库、不碰 Electron。
 * 单测见 tests/doc-number.test.ts——正因为它纯，才测得起。
 */

const pad2 = (n: number) => String(n).padStart(2, '0');

/** 日期段格式化：none → 空串（该段被跳过） */
export function formatDateSegment(dateType: DocDateType, now: Date): string {
  switch (dateType) {
    case 'yyyy': return `${now.getFullYear()}`;
    case 'yyyyMM': return `${now.getFullYear()}${pad2(now.getMonth() + 1)}`;
    case 'yyyyMMdd': return `${now.getFullYear()}${pad2(now.getMonth() + 1)}${pad2(now.getDate())}`;
    case 'none': default: return '';
  }
}

/** 流水号补零：位数内左补 0，超出位数不截断（截断会造成重号） */
export function padSeq(seq: number, length: number): string {
  return String(seq).padStart(length, '0');
}

/** 重置周期键：把"当前时间"折叠成周期标识。never → ''（所有流水共用一行计数） */
export function resetKey(policy: DocResetPolicy, now: Date): string {
  switch (policy) {
    case 'daily': return formatDateSegment('yyyyMMdd', now);
    case 'monthly': return formatDateSegment('yyyyMM', now);
    case 'yearly': return formatDateSegment('yyyy', now);
    case 'never': default: return '';
  }
}

/** 组装单据号：前缀/日期为空的段自动跳过，剩余段用分隔符连接 */
export function buildDocNumber(
  rule: Pick<DocRuleRecord, 'prefix' | 'dateType' | 'seqLength' | 'separator'>,
  seq: number,
  now: Date,
): string {
  const segments = [rule.prefix, formatDateSegment(rule.dateType, now), padSeq(seq, rule.seqLength)]
    .filter((s) => s !== '');
  return segments.join(rule.separator);
}

/** 入参校验（service 层最后防线）：返回错误消息，空串 = 通过 */
export function validateDocRule(input: {
  code: string; name: string; seqLength: number; prefix?: string; separator?: string;
}): string {
  if (!/^[A-Z][A-Z0-9_-]{1,15}$/.test(input.code)) return '单据编码需以字母开头，2-16 位大写字母/数字/_/-';
  if (!input.name.trim()) return '请输入规则名称';
  if (!Number.isInteger(input.seqLength) || input.seqLength < 1 || input.seqLength > 8) {
    return '流水号位数需为 1-8 的整数';
  }
  if ((input.prefix ?? '').length > 16) return '前缀不能超过 16 个字符';
  if ((input.separator ?? '').length > 4) return '分隔符不能超过 4 个字符';
  return '';
}
```

### 5.2 `src/main/service.ts` 追加

import { buildDocNumber, resetKey } from './doc-number';

（`import type { ... }` 那行并入既有的 dto 导入即可。）然后在文件末尾追加：

```ts
// ==================== 单据号规则 ====================

/** doc_rules 表的原始行（snake_case） */
interface DocRuleRow {
  id: string;
  code: string;
  name: string;
  prefix: string | null;
  date_type: string;
  seq_length: number;
  reset_policy: string;
  separator: string | null;
  enabled: number;
  remark: string | null;
  created_at: string;
  updated_at: string;
}

const DOC_DATE_TYPES: DocDateType[] = ['none', 'yyyy', 'yyyyMM', 'yyyyMMdd'];
const DOC_RESET_POLICIES: DocResetPolicy[] = ['never', 'daily', 'monthly', 'yearly'];

/** snake_case 行 → camelCase 契约；异常枚举值静默归默认（老库脏数据防线） */
function mapDocRuleRow(row: DocRuleRow): DocRuleRecord {
  return {
    id: row.id,
    code: row.code,
    name: row.name,
    prefix: row.prefix ?? '',
    dateType: (DOC_DATE_TYPES as string[]).includes(row.date_type) ? (row.date_type as DocDateType) : 'none',
    seqLength: row.seq_length,
    resetPolicy: (DOC_RESET_POLICIES as string[]).includes(row.reset_policy)
      ? (row.reset_policy as DocResetPolicy)
      : 'never',
    separator: row.separator ?? '',
    enabled: row.enabled === 1,
    remark: row.remark ?? '',
    createdAt: row.created_at,
    updatedAt: row.updated_at,
  };
}

export async function docRuleList(): Promise<DocRuleRecord[]> {
  const db = await getDatabase();
  const rows = db.all('SELECT * FROM doc_rules ORDER BY created_at DESC') as DocRuleRow[];
  return rows.map(mapDocRuleRow);
}

export async function docRuleUpsert(rule: DocRuleInput) {
  const db = await getDatabase();
  const error = validateDocRuleInput(rule);
  if (error) throw new Error(error);

  const now = new Date().toISOString();
  db.run(`
    INSERT INTO doc_rules (id, code, name, prefix, date_type, seq_length, reset_policy, separator, enabled, remark, created_at, updated_at)
    VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)
    ON CONFLICT(id) DO UPDATE SET
      code = excluded.code, name = excluded.name, prefix = excluded.prefix,
      date_type = excluded.date_type, seq_length = excluded.seq_length,
      reset_policy = excluded.reset_policy, separator = excluded.separator,
      enabled = excluded.enabled, remark = excluded.remark, updated_at = excluded.updated_at
  `, [
    rule.id, rule.code, rule.name,
    rule.prefix ?? null,
    rule.dateType ?? 'none',
    rule.seqLength ?? 4,
    rule.resetPolicy ?? 'never',
    rule.separator ?? null,
    rule.enabled === false ? 0 : 1,
    rule.remark ?? null,
    now, now,
  ]);
  db.persist();
  return { success: true };
}

/** 入参校验的 service 包装：纯函数 validateDocRule 不 import 会失去最后防线 */
function validateDocRuleInput(rule: DocRuleInput): string {
  return validateDocRule({
    code: rule.code, name: rule.name, seqLength: rule.seqLength ?? 4,
    prefix: rule.prefix, separator: rule.separator,
  });
}

export async function docRuleDelete(id: string) {
  const db = await getDatabase();
  const rule = db.get('SELECT code FROM doc_rules WHERE id=?', [id]) as { code: string } | null;
  db.transaction(() => {
    db.run('DELETE FROM doc_rules WHERE id=?', [id]);
    // 计数是规则的状态而非配置：规则删除即一并清理，避免同 code 重建后旧计数复活
    if (rule) db.run('DELETE FROM doc_counters WHERE rule_code=?', [rule.code]);
  });
  db.persist();
  return { success: true };
}

/**
 * 取下一个单据号：定位规则 → 计算周期键 → 事务内计数 +1 → 组装返回。
 * 必须在单个事务里：Electron 窗口（IPC）与浏览器调试（Dev API）可能同时取号，
 * 事务把"读-改-写"串行化，保证不发出重复的号。
 * 跨周期（如跨天）自动落到新的 reset_key 上，从 1 重新计数——无需任何定时任务。
 */
export async function docNextNumber(code: string): Promise<string> {
  const db = await getDatabase();
  const row = db.get('SELECT * FROM doc_rules WHERE code=?', [code]) as DocRuleRow | null;
  if (!row) throw new Error(`单据规则不存在：${code}`);
  if (row.enabled !== 1) throw new Error(`单据规则已停用：${code}`);

  const rule = mapDocRuleRow(row);
  const now = new Date();
  const key = resetKey(rule.resetPolicy, now);
  let next = '';

  db.transaction(() => {
    // UPSERT 起步行（首次取号/新周期）：已存在则什么都不做
    db.run(`
      INSERT INTO doc_counters (rule_code, reset_key, seq) VALUES (?, ?, 0)
      ON CONFLICT(rule_code, reset_key) DO NOTHING
    `, [rule.code, key]);
    db.run('UPDATE doc_counters SET seq = seq + 1 WHERE rule_code=? AND reset_key=?', [rule.code, key]);
    const counter = db.get('SELECT seq FROM doc_counters WHERE rule_code=? AND reset_key=?', [rule.code, key]) as { seq: number };
    next = buildDocNumber(rule, counter.seq, now);
  });
  db.persist();
  return next;
}
```

（记得把 `validateDocRule` 也加进顶部 import：`import { buildDocNumber, resetKey, validateDocRule } from './doc-number';`，然后删掉上面那个 `validateDocRuleInput` 包装、直接在 `docRuleUpsert` 里调用 `validateDocRule(...)`——这里拆开写是为了让 import 的补丁位置一目了然。）

### 为什么

- **UPSERT 三连**（INSERT DO NOTHING → UPDATE +1 → SELECT）在事务里是取号的标准姿势：第一次取号和后续取号走同一条路径，不需要"先 SELECT 判断存在与否"的分支。
- `enabled === false ? 0 : 1`：undefined 视为启用，和 dto 里"可选字段服务端兜默认值"的约定一致。
- `docRuleDelete` 参考了 `userDelete` 的联动模式（B4 整改的遗产）：删除主记录时同步清理无外键的从属数据，包在事务里。

### 踩坑与经验

1. **忘 `db.persist()`** 是本项目历史最高频事故（sql.js 全内存）：写函数写完自查最后一行。better-sqlite3 驱动的 persist 是空操作，所以这个约定对两种驱动都安全，**永远写**。
2. **SQL 里绑定 `undefined` 直接炸**。任何可能为 undefined 的值进 SQL 前都要 `?? null` / `?? 默认值`。
3. `db.transaction` 的回调**不要依赖返回值**向外传数据（本项目驱动的 transaction 包装不保证透传回调返回值），用闭包变量 `let next` 带出来。
4. 取号里抛的 Error 会被 IPC 原样序列化传回渲染端，页面 `catch (err)` 后 `err.message` 就是中文提示——所以**错误消息要写成给用户看的**，不是写给日志的。
5. 跑一遍 `npx tsc -p tsconfig.main.json --noEmit`，此刻应为零错误。

  docRuleUpsert: (rule: DocRuleInput) => Promise<{ success: boolean }>;

### 为什么

四件套分工：`ipc/doc.ts` 声明“哪个频道归谁”；`main.ts` 决定“什么时候接上”；`preload.ts` 把频道包成普通 async 函数挂到 `window.electronAPI`（页面从不需要知道 IPC 的存在）；`electron.d.ts` 给 `window.electronAPI` 补 TypeScript 类型。**channel 名用 `doc:` 前缀**，与既有 `user:` / `menu:` 命名一致。

### 踩坑与经验

1. **同一个 channel 注册两次会崩**：`ipcMain.handle` 重复注册抛 `Attempted to register a second handler for 'doc:xxx'`。遇到这个错，通常是你在 `main.ts` 里 register 了两次，或者新建的 ipc 文件与既有文件撞了 channel 名。
2. **preload 的禁区**：文件头注释写得很清楚——preload 只能 `import type` 主进程内容。运行时 import `service` 链会白屏，而且报错发生在 contextBridge 注册之前，页面什么都看不到，只有主进程日志有线索。遇到“整个窗口空白”先查这里。
3. 改完 preload 记得同步 electron.d.ts——它俩没有编译期强制一致（一个在主进程编译、一个在渲染端），漏改不会报错，只会让页面拿到 any。靠自律 + code review。

### 9.3 页面骨架与交互设计要点

页面完全对齐 `UserManagement.tsx` 的范式：`QueryTableLayout + QueryForm + useQueryTable + Modal`，列表列依次为编码/名称/格式预览/重置周期/状态/备注/操作。关键设计：

1. **实时预览是本页面的灵魂**：单据号规则是“配置型”数据，用户最大的痛点是“我配出来的号到底长什么样”。弹窗底部的预览框随表单每次击键刷新，用户不需要保存后就能看到结果——**让用户在犯错之前就看见后果**。列表的「格式预览」列复用同一个 `previewDocNumber`（接收 `Pick<...>` 收窄参数，表单与记录行共用）。
2. **预览不消耗计数器**：预览永远显示流水号 `0001`，取号测试才是计数器唯一入口——两个入口语义分明。
3. **code 输入自动 toUpperCase**：降低“小写被校验拒绝”的挫败感；编辑态直接 disabled（决策 5）。
4. **取号测试按钮**：让验收变成点击动作，不需要会 SQL 的人也能验证流水递增。注意它是**真实取号**（计数 +1），结果弹窗直接展示号码。
5. **错误就地展示**（saveError 红字）而不是全局 Toast：表单错误应该出现在用户视线焦点处，与 UserManagement 同款模式。
6. **删除文案说后果**（“流水计数将一并清除”）：破坏性操作必须预告副作用。

### 9.4 渲染端预览为什么不 import 主进程的 buildDocNumber

`previewDocNumber` 是 `doc-number.ts` 里 `buildDocNumber` 的渲染端复刻（约 10 行）。不直接 import 的原因：项目约定 `src/main` 的**运行时代码**不进渲染 bundle（跨进程只共享 type），而把 `doc-number.ts` 拆到共享目录需要动两份 tsconfig 的 rootDir。复制 10 行纯逻辑的成本，低于改构建配置的耦合成本——这是有意识的取舍，代价是两处逻辑需人工保持一致（测试用例已覆盖组装语义，漂移会在单测暴露）。

### 踩坑与经验

1. **JSX 里多行箭头函数易漏闭合**：`onChange={(e) => { setForm({...form, code: e.target.value}); setSaveError(''); }}` 这类写法，最后要 `})}` 三个字符分别关掉 setForm 的 `}`、箭头函数体的 `}`、JSX 属性的 `}`。漏一个就是 `TS1109: Expression expected`，报错行号还常指向别处——看到 1109 先数大括号。
2. **filter 必须是模块顶层纯函数**：写进组件里会导致 useQueryTable 每次渲染拿到新引用；依赖组件状态更是直接破坏 memo。项目里 `filterUsers` 的写法就是标准答案，照抄结构。
3. 页面保存无需像 UserManagement 那样“合入 original 保留未暴露字段”——本页表单暴露了全部字段；service 的 UPSERT 自动区分新增/更新（id 存在与否）。

## 12. 感悟（写给刚做完这个功能的你）

**1. 分层不是教条，是杠杆。**
这次你改了 17 个地方，但每一处都只有几行，而且每改一处你都能准确知道“这行代码归谁管”。想象反面：如果所有逻辑堆在页面组件里，加一个字段你要同时小心 SQL、状态、渲染、三种环境分支——那才是真正的“改一处崩三处”。分层的回报是**局部性**：需求变化时，你只在受影响的层动刀。

**2. 契约先行，代码填空。**
回头看：Step 2 把 DTO 写完之后，后面的每一步都是在“填空”——service 填 SQL、preload 填通道、页面填表单。类型不是文档的补充，类型就是施工图。当你发现某一步“不知道怎么写”，八成是契约还没想清楚，回到 dto.ts 改两行，比在第五层返工便宜十倍。

**3. 纯函数是最便宜的测试对象。**
本功能 15 个单测覆盖了全部业务语义（组装、重置、补零、校验），而写它们只花了十分钟——因为 Step 3 就把逻辑从 SQL 和 React 里拽了出来。**可测试性不是测出来的，是设计出来的**：下次写代码前先问“这段逻辑能不能不碰数据库也不碰 UI”。

**4. 假交互的教训。**
这个项目曾经有一个不勾也生效的「记住我」勾选框、一个假装在努力的 800ms 登录延迟（README 问题清单 D5/D6），后来被整体清理。新手期最容易产出这类“看起来像功能的东西”。判据很简单：**每个交互都要有真实后果**——本次的「取号」按钮会真实推进计数器，预览则明确标注“流水号 1”、绝不碰计数。宁可少做一个功能，不要做一个假的。

**5. 读注释，读报错。**
这个仓库的注释密度很高，很多是前人踩坑后写的墓志铭（preload 白屏、bind undefined、迁移幂等…）。遇到报错，先把完整消息读完再搜；两件事都做完了再问人——问出来的答案记得像前人一样写成注释或文档，这就是工程经验的复利。

## 13. 迭代记录：上线后的两个改进（2026-09-07）

功能交付不足一天就来了两个反馈——这很正常，也是新手要适应的节奏：交付不是终点，反馈才是迭代的起点。

### 13.1 改进一：列表显示「当前流水」

**反馈**：运维想知道每条规则现在用到几号了，不想打开数据库查 doc_counters。

**实施**（对照主流程，这次只动了三处——分层的杠杆兑现了）：

1. `dto.ts`：`DocRuleRecord` 增加 `currentSeq: number | null`（**必填**而非可选——所有构造点会被编译器逐一检查，dev-fallback 的演示数据想漏都漏不了）。
2. `service.ts` `docRuleList()`：一次查全部计数行，内存按 rule_code 分组后为每条规则选一行：**优先当前周期行（reset_key 相等），无则取最近使用过的周期行**（字典序最大）。语义细节：daily 规则昨天用过、今天还没取号 → 显示昨天的流水而非「未使用」——用户问的是“最近用到哪了”，不是“今天用到哪了”。
3. 页面：加「当前流水」列，`padStart` 补零展示（与格式预览同风格），null 显示「未使用」。

**经验**：
- 出口加字段走「必填」是免费的编译期检查：字段设为可选，三个构造点（mapDocRuleRow、dev-fallback、测试夹具）漏一个都不报错；设为必填，TS 会把每一个漏网的构造点都揪出来。
- 规则表是配置表（量级个位数～几十），内存聚合比逐规则子查询简单且够快——不要对小数据写聪明的 SQL。

### 13.2 改进二：Tab 标题显示成路径（Bug 修复）

**现象**：打开「单据号规则」页，Tab 显示的是 `/system/doc-rules` 而不是菜单名。

**根因**：[TabBar.tsx](../src/renderer/components/Layout/TabBar.tsx) 里有一份硬编码的 `PATH_TITLE` 映射——这正是本文 1.3 铁律 8 说的“加菜单要同步多处”的又一处（此前已知 schema/dev-fallback/Sidebar 三处，这是第四处）。新增页面漏加一行，fallback 就把路径当标题。

**修复**（根治而非再补一行）：
1. 删除 `PATH_TITLE` 硬编码；TabBar 挂载时从 `loadMenus()` 构建 path→label 映射（菜单树来自 adapter，是**未按角色过滤的完整树**——标题解析不应受当前用户权限影响）；监听 `menu-updated` 事件重建（菜单管理页改名后 Tab 同步）。
2. 竞态兑底：菜单是异步加载的，用户可能在映射就绪前就导航了页面 → 先以路径为 fallback 开 Tab，映射就绪后由修正 effect 用 `updateTabTitle` 改写。
3. `useTabStore` 新增 `updateTabTitle(id, title)`：只改标题不动 `activeTabId`。

**这里有个值得展开的坑**：修正 effect 需要遍历所有 Tab 改标题，第一版直接循环调 `addTab`——而 `addTab` 会顺带 `setActiveTabId`，结果遍历修正会把激活 Tab 误切到最后一个被修正的 Tab。**两个动作（激活、改标题）耦合在一个 API 里，复用时就会互相伤害**。拆出 `updateTabTitle` 单一职责后各自安全。教训：设计 store action 时问一句“调用方会不会只想做其中一半”。

## 14. 迭代二：单据号规则被业务消费——人员管理加用户编码（2026-09-07）

前两轮都在「单据号规则自身」里打转，这一轮是它第一次被另一个功能消费：给【人员管理】的用户加上用户编码（用户账号），由规则 `USER` 自动生成，新增/编辑均不可编辑。

### 14.1 需求拆解

- 既有用户怎么办？→ 迁移时回填（U0001 起，按 created_at 稳定排序）
- 新用户怎么拿号？→ userCreate 服务端取号（客户端不可传入——可编辑的编码会被伪造/冲突）
- 编辑时能改吗？→ 不能：UPDATE 语句根本不碰 user_code 列，不是「表单 disabled」式的只读
- 删了用户号会复用吗？→ 不复用（计数器只进不退，与业务编码不复用原则一致）

### 14.2 实施要点

1. **迁移 v5**（[schema.ts](../src/main/db/schema.ts)）：`ALTER TABLE` 加列（先 PRAGMA table_info 查存在性，幂等）→ 相关子查询模拟 row_number 回填 → UNIQUE 索引 → USER 规则种子 + **计数与回填同步**（`INSERT ... SELECT COUNT(*)`）。计数同步是最容易被漏的一步：漏了则首个新用户拿到 U0001，直接撞回填值的 UNIQUE 索引。
2. **契约设计**：`UserRecord`/`UserInfo` 加必填 `userCode`；**`UserInput` 刻意不加**。输入契约没有这个字段，客户端想传都传不进来——「不可编辑」的安全边界是契约层的，不只是 UI 层的。
3. **service**（[service.ts](../src/main/service.ts)）：`userCreate` 在同事务里推进 USER 计数并写入；规则不存在/停用则拒绝新增（明确报错优于静默降级）。`userUpdate` 一行未改。
4. **页面**：列表加「用户编码」列（等宽字体）；表单顶部只读输入框，新增时显示「保存后自动生成」，编辑时回显。

### 14.3 本轮浮出的存量缺陷：docRuleUpsert 部分更新覆盖字段

冒烟脚本 T5f 失败（拿到 `0014` 而非 `U0014`）暴露了一个既有缺陷：`docRuleUpsert` 只传 `{ id, code, name, enabled }` 时，未传的 prefix 被默认值 `''` 覆盖清空。页面表单总是全量传参所以从没触发过——**UI 的全量传参掩盖了 service 的部分更新语义缺陷，绕过 UI 的调用方（HTTP 直调/脚本）踩中**。修复：先按 id 读既有行合并，未传字段保持原值。

这也是为什么「主进程 service 层是最后防线」：凡是渲染端可以绕过的入口（Dev API、脚本），契约语义必须在 service 层自洽。

### 14.4 验证

- tsc×2 零错、lint 0 错、vitest 33/33、vite build 通过。
- `test-doc-rule.mjs` **23/23**（新增 T1d-T1f 回填/索引/计数同步、T5a-T5f：回填后接续、连续递增、编辑不变、停用拦截、被拦创建不消耗计数——号源无空洞）。
- `test-migration.mjs` **9/9**（版本断言升 v5，新增 T9 回填+种子）。
- 手工验收：新增用户 → 列表出现新编码（回填最后一个的下一个）；编辑 → 编码不变；在单据号规则页停用 USER 规则 → 新增用户被拒并提示。

### 14.5 经验

- **回填型迁移的完整闭环是「改数据 + 同步计数器」**：只回填不同步，下一个号必撞唯一索引。
- **测试脚本自己的副作用会污染后面的断言**（本脚本 T4 删了用户、T5 插了无编码用户，T9 断言若用实时数据必误报）——迁移后立即捕获基线快照再断言。
- **UI 全量传参会掩盖 service 的语义缺陷**：service 对部分更新的行为要自己定义清楚（合并 or 覆盖），不能依赖调用方恰好传全。
- **只读字段的安全边界在契约层**：输入 DTO 不含该字段，比表单 disabled 更硬——后者只能防君子。
