## 第零步：打开项目——从 index.html 到看到登录页

在研究登录逻辑之前，我首先要搞清楚一个更基础的问题：**这个应用是怎么启动的？**

我打开项目根目录，第一眼看到的是 `index.html`——这是整个前端应用的入口。

### 0.1 主进程启动（Electron 的"后端"）

这是一个 Electron 项目，有两套进程：
- **主进程**（`src/main/main.ts`）：相当于"后端"，能访问数据库、文件系统
- **渲染进程**（`index.html` + React）：相当于"前端"，就是用户看到的网页

应用启动时，主进程先跑起来。打开 `src/main/main.ts`：

```ts
app.whenReady().then(async () => {
  // 第一步：初始化数据库
  await getDatabase();
  
  // 第二步：注册 IPC 通道（前端和后端通信的"电话线"）
  await registerUserIpc();   // ← 这里面注册了 'auth:login' 通道！
  await registerMenuIpc();
  await registerDocIpc();
  await registerFileIpc();
  
  // 第三步：开发模式下启动 HTTP API 服务器
  if (process.env.NODE_ENV === 'development') {
    await startApiServer();  // ← 让浏览器调试时也能访问数据库
  }
  
  // 第四步：创建窗口
  createWindow();
});
```

**我的理解：** 主进程做了四件事：
1. 初始化 SQLite 数据库
2. 注册 IPC 通道（包括后面登录要用到的 `auth:login`）
3. 开发模式下启动 Dev API Server（端口 5174）
4. 创建窗口并加载页面

### 0.2 创建窗口——安全配置

继续看 `createWindow()` 函数：

```ts
mainWindow = new BrowserWindow({
  width: Math.min(width * 0.85, 1600),
  height: Math.min(height * 0.85, 1000),
  titleBarStyle: 'hidden',  // ← 隐藏原生标题栏
  frame: false,             // ← 无边框窗口
  transparent: true,        // ← 透明背景（配合 CSS 圆角）
  webPreferences: {
    preload: join(__dirname, 'preload.js'),  // ← 预加载脚本
    contextIsolation: true,                   // ← 上下文隔离
    nodeIntegration: false,                   // ← 禁用 Node 集成
  },
});
```

**新手笔记：** 这三个安全配置很关键：
- `contextIsolation: true`：渲染进程和 preload 脚本运行在隔离的上下文
- `nodeIntegration: false`：网页不能直接用 Node.js API（防止 XSS 攻击）
- `preload`：通过预加载脚本安全地暴露有限 API 给网页

> 这就是为什么前面看到的 `window.electronAPI` 需要通过 preload 脚本来暴露——直接访问 Node.js 是不允许的。

### 0.7 路由决策——为什么看到的是登录页？

用户打开应用时，默认访问 `/`（根路径）。路由配置显示：
- `/login` → 直接显示 `LoginPage`
- `/` → 显示 `AppLayout`，里面包含 `Dashboard` 等子路由

但我第一次打开应用时，看到的是登录页，不是 Dashboard。为什么？

答案在 `AppLayout` 里。回到之前看过的代码：

```tsx
// src/renderer/components/Layout/AppLayout.tsx
function AppLayout() {
  const userInfo = useAuthStore((state) => state.userInfo);
  const navigate = useNavigate();

  useEffect(() => {
    if (!userInfo) {
      navigate('/login', { replace: true });  // ← 没登录就跳转登录页
    }
  }, [userInfo, navigate]);
  
  // ...
}
```

**我的理解：**
1. 用户访问 `/`
2. 路由匹配到 `AppLayout`
3. `AppLayout` 检查 `userInfo`（从 `useAuthStore` 获取）
4. `useAuthStore` 从 `localStorage` 读取缓存的用户信息
5. 第一次打开应用，`localStorage` 里没有缓存 → `userInfo` 为 `null`
6. `useEffect` 检测到 `userInfo` 为 `null` → 跳转到 `/login`
7. 路由切换到 `LoginPage`，用户看到登录界面

> 新手笔记：这就是为什么第一次打开应用会看到登录页——不是路由直接指向登录页，而是主界面检查登录态后主动跳转过去的。

### 0.9 启动链路相关踩坑要点

**1. 开发模式 vs 生产模式的加载差异**

开发时加载 `http://localhost:5173`（Vite 开发服务器），支持热更新——改了代码自动刷新。打包后加载编译好的 `index.html` 文件，通过 `file://` 协议加载。

> 这就是为什么路由要用 `createHashRouter` 而不是 `createBrowserRouter`——`file://` 协议下 `pathname` 是完整的磁盘路径，普通路由匹配不到。

**2. CSP 策略为什么要放行 `unsafe-inline`**

`index.html` 的 CSP 策略里，`script-src` 和 `style-src` 都放行了 `'unsafe-inline'`。这是因为：
- Vite 的 Fast Refresh（热更新）需要注入内联脚本
- React 的内联 `style` 属性需要放行
- 生产构建时这些不需要，但开发阶段必须放行

**3. 无边框窗口 + 圆角设计**

主进程配置了 `frame: false`（无边框）+ `transparent: true`（透明背景），这是为了实现自定义标题栏和窗口圆角。渲染进程通过 CSS 的 `border-radius` 画圆角，通过 `is-electron` 和 `is-maximized` 类名控制样式。

> 这就是为什么 `App.tsx` 里有 `window.electronAPI.isMaximized()` 和 `onMaximizeChange` 的监听——最大化时需要去掉圆角。

## 第二步：点击登录按钮后发生了什么？

继续看 `LoginPage.tsx` 里的 `handleLogin` 函数：

```tsx
const handleLogin = async (e: React.FormEvent) => {
    e.preventDefault();
    setError('');
```

## 第三步：追踪 authLogin 的来源

回到文件顶部，我看到导入：


打开 `src/renderer/services/sqlite.ts`，找到：


**我的思考：** 这个文件是个"门面"（注释里也这么叫），它自己不干活，而是把请求转给 `getDataAdapter()` 返回的适配器。

### 什么是适配器？

继续看 `src/renderer/services/adapter.ts`，注释写得很清楚：

> 渲染进程统一数据访问入口。三端通路的选择在启动时一次性解析：
> - Electron 环境 → IpcAdapter（走 preload 暴露的 electronAPI）
> - 浏览器 + Dev API 在线 → HttpAdapter（走 HTTP 请求）
> - 纯浏览器（无后端）→ FallbackAdapter（演示数据）

```ts
export function getDataAdapter(): Promise<DataAdapter> {
  if (!adapterPromise) {
    adapterPromise = (async () => {
      if (isElectron()) return new IpcAdapter();
      if (await probeDevApi()) return new HttpAdapter();
      const { FallbackAdapter } = await import('./dev-fallback');
      return new FallbackAdapter();
    })();
  }
  return adapterPromise;
}
```

**我的理解：** 这个项目设计得很巧妙——同一个前端代码，可以在三种环境下运行：
1. **Electron 窗口**（正式使用）：通过 IPC（进程间通信）调用主进程
2. **浏览器 + 开发 API**（调试时用）：通过 HTTP 请求调用后端
3. **纯浏览器**（没有后端）：用假的演示数据

对于登录来说，我们主要关注第一种：IpcAdapter。

### IpcAdapter 怎么调登录？

```ts

    } catch {

    }
  }
  // ...
}
```

它调用了 `window.electronAPI.authLogin()`。

## 第四步：preload.ts —— 前端和主进程之间的"安全桥梁"

打开 `src/main/preload.ts`，我看到了答案：

```ts
contextBridge.exposeInMainWorld('electronAPI', {
  // ...
  authLogin: (username: string, password: string) =>
    ipcRenderer.invoke('auth:login', { username, password }) as Promise<UserRecord | null>,
  // ...
});
```

**我的理解：**

Electron 有两个进程：
- **主进程**（Main Process）：拥有 Node.js 全部能力，能读写数据库、操作文件系统
- **渲染进程**（Renderer Process）：就是网页，跑在沙箱里，不能直接访问 Node.js

为了安全，渲染进程不能直接用 Node.js 的能力。那怎么通信？靠 **preload 脚本** 在 `window` 上挂一个安全的 API 对象 `window.electronAPI`。

关键概念：
- `contextBridge.exposeInMainWorld`：安全地往 `window` 上挂东西
- `ipcRenderer.invoke('auth:login', ...)`：通过 IPC 通道发消息给主进程

> 新手踩坑笔记：preload 脚本运行在独立的渲染上下文中，**绝对不能**在运行时 import 主进程的模块（如 service.ts、database.ts），否则会导致白屏！只有 `import type`（纯类型引用）是安全的，因为编译后会被完全擦除。

## 第六步：service.ts 中的 authLogin —— 核心验证逻辑

这是最关键的部分。打开 `src/main/service.ts`，找到 `authLogin` 函数：

```ts
export async function authLogin(username: string, password: string): Promise<UserRecord | null> {
  const db = await getDatabase();
  
  // 第一步：从 passwords 表查出该用户的密码 hash
  const pwd = db.get('SELECT hash FROM passwords WHERE username=?', [username]) as { hash: string } | null;
  if (!pwd || !bcrypt.compareSync(password, pwd.hash)) return null;

  // 第二步：LEFT JOIN 合并用户信息和个人资料
  const row = db.get(`
    SELECT u.*, p.nickname AS profile_nickname, p.avatar AS profile_avatar,
           p.phone AS profile_phone, p.email AS profile_email
    FROM users u
    LEFT JOIN user_profiles p ON p.username = u.username
    WHERE u.username = ?
  `, [username]) as (UserRow & Record<string, string | null>) | null;
  if (!row) return null;

  // 第三步：组装返回（个人资料优先于账号默认值）
  const base = mapUserRow(row);
  return {
    ...base,
    nickname: row.profile_nickname ?? base.nickname,
    avatar: row.profile_avatar ?? base.avatar,
    phone: row.profile_phone ?? base.phone,
    email: row.profile_email ?? base.email,
  };
}
```

**我的理解：** 登录验证分三步：

1. **查密码表**：从 `passwords` 表找这个用户名的 hash，用 `bcrypt.compareSync` 比对明文密码。不匹配直接返回 null。
2. **查用户信息**：从 `users` 表 LEFT JOIN `user_profiles`，同时拿到账号信息和个人资料。
3. **合并返回**：个人资料（昵称、头像等）优先于账号表里的默认值——因为用户可能在"个人信息"页修改过。

> 新手笔记：密码验证用的是 `bcrypt`，这是一种专门用来哈希密码的算法。它的特点是慢——故意慢，防止暴力破解。`compareSync` 是同步比对方法。

> 重要设计：密码的哈希和比对全部在主进程完成，渲染进程只传明文过来。为什么？因为渲染进程可能被 XSS 攻击，如果哈希逻辑在前端，攻击者就能直接接触哈希算法。IPC 是本地进程间通信，传明文反而更安全。


> 新手思考：为什么密码不直接放在 users 表里？
> 答：安全考虑。密码表独立后，查询用户列表时不会意外带出密码哈希。而且这张表没有外键约束——删用户时需要手动删密码记录（service.ts 里确实这样做了）。

### user_profiles 表（可选个人资料）

```sql
CREATE TABLE IF NOT EXISTS user_profiles (
  username TEXT PRIMARY KEY,
  nickname TEXT,
  email TEXT,
  phone TEXT,
  avatar TEXT,
  FOREIGN KEY (username) REFERENCES users(username) ON DELETE CASCADE ON UPDATE CASCADE
)
```

> 注意外键的 CASCADE：删用户时自动删 profile，改名时自动同步。这比 passwords 表设计得更优雅。

## 第八步：登录成功后 —— useAuthStore 保存状态

回到 `LoginPage.tsx`，验证成功后调用了：

```ts
login('mock-token-' + Date.now(), user);
```

这个 `login` 来自 `src/renderer/stores/useAuthStore.ts`：

```ts
export const useAuthStore = create<AuthState>((set, get) => ({
  token: storedToken,
  userInfo: storedUser,
  isAuthenticated: !!storedToken && !!storedUser,
  
  login: (token, user) => {
    persistToken(token);    // 存到 localStorage
    persistUser(user);      // 存到 localStorage
    set({ token, userInfo: user, isAuthenticated: true });
  },
  
  logout: () => {
    localStorage.removeItem(TOKEN_KEY);
    localStorage.removeItem(USER_KEY);
    set({ token: null, userInfo: null, isAuthenticated: false });
  },
  
  updateUserInfo: (patch) => {
    const current = get().userInfo;
    if (!current) return;
    const next = { ...current, ...patch };
    persistUser(next);
    set({ userInfo: next });
  },
}));
```

**我的理解：**

这是一个 Zustand store（状态管理），管理三样东西：
- `token`：登录凭证（目前是演示级的 mock token，不是真正的 JWT）
- `userInfo`：用户信息（id、username、role 等）
- `isAuthenticated`：是否已登录的布尔值

**持久化策略：**
- 登录时把 token 和 userInfo 存到 `localStorage`
- 页面刷新后，从 `localStorage` 读取恢复状态（所以不会每次刷新都要重新登录）
- 退出时清除 localStorage 和内存状态

> 新手踩坑笔记：localStorage 有容量限制（通常 5-10MB）。用户头像如果是 base64 编码的大图，可能超出配额。代码里有 try-catch 兜底——持久化失败不影响登录，只是刷新后需要重新登录。

## 第九步：路由守卫 —— 怎么防止未登录访问？

登录成功后跳转到 `/`，但怎么保证没登录的人不能直接访问首页或其他页面？

### 9.1 路由配置

打开 `src/renderer/routes.tsx`：

```tsx
export const router = createHashRouter([
  {
    path: '/login',
    element: <LoginPage />,
  },
  {
    path: '/',
    element: <AppLayout />,    // ← 所有内部页面的父布局
    children: [
      { index: true, element: <Dashboard /> },
      { path: 'system/profile', element: <Profile /> },
      {
        path: 'system/users',
        element: (
          <RequireRole roles={['admin']}>    // ← 角色守卫
            <UserManagement />
          </RequireRole>
        ),
      },
      // ...
    ],
  },
  {
    path: '*',
    element: <NotFound />,
  },
]);
```

> 新手疑问：为什么用 `createHashRouter` 而不是 `createBrowserRouter`？
> 答：因为 Electron 打包后通过 `file://` 协议加载页面，`location.pathname` 会变成完整的磁盘路径（如 `C:\app\index.html`），导致 `createBrowserRouter` 匹配不到任何路由。HashRouter 从 `location.hash` 读路由（如 `#/system/users`），不受文件路径影响。

### 9.2 AppLayout —— 登录态检查

```tsx
// src/renderer/components/Layout/AppLayout.tsx
function AppLayout() {
  const userInfo = useAuthStore((state) => state.userInfo);
  const logout = useAuthStore((state) => state.logout);
  const navigate = useNavigate();

  useEffect(() => {
    if (!userInfo) {
      logout(); // 统一清除状态
      navigate('/login', { replace: true });
    }
  }, [userInfo, logout, navigate]);

  return (
    <ToastProvider>
      <div className="app-layout">
        <Sidebar />
        <div className="app-main">
          <Header />
          <TabBar />
          <main className="app-content">
            <Outlet />    {/* 子路由的组件在这里渲染 */}
          </main>
        </div>
      </div>
    </ToastProvider>
  );
}
```

**我的理解：** 所有内部页面都在 `AppLayout` 下。如果 `userInfo` 为 null（没登录或 localStorage 里没有），就自动跳转到登录页。

### 9.3 RequireRole —— 角色守卫

```tsx
// src/renderer/components/RequireRole.tsx
function RequireRole({ roles, children }: RequireRoleProps) {
  const userInfo = useAuthStore((state) => state.userInfo);

  if (!userInfo || !roles.includes(userInfo.role)) {
    return (
      <div className="forbidden-page">
        <div className="forbidden-code">403</div>
        <div className="forbidden-title">无访问权限</div>
        {/* ... */}
      </div>
    );
  }

  return <>{children}</>;
}
```

**我的理解：** 即使登录了，如果角色不对（比如普通 user 想访问 admin 才能看的人员管理页），也会显示 403 无权限页面。

> 新手笔记：菜单的可见性过滤和路由守卫是两道独立的防线。菜单过滤只是"看不到入口"，用户还是可以通过地址栏直达。所以路由层的 RequireRole 是必须的。

## 第十步：跨进程契约 —— dto.ts

整个登录链路中，数据在主进程和渲染进程之间传递，靠的是 `src/main/dto.ts` 定义的契约类型：

```ts
export interface UserRecord {
  id: string;
  username: string;
  userCode: string;    // 用户编码（自动生成，如 U0001）
  email: string;
  phone: string;
  avatar: string;
  nickname: string;
  role: UserRole;      // 'admin' | 'manager' | 'user'
  status: UserStatus;  // 'active' | 'disabled'
  createdAt: string;
}
```

**核心约定：**
- 数据库里的字段是 `snake_case`（如 `created_at`、`user_code`）
- 但数据库行**不出 service 层**，出口一律映射为 `camelCase`（如 `createdAt`、`userCode`）
- 渲染进程和主进程共享同一份类型定义，编译期就能发现字段不匹配

映射逻辑在 service.ts 的 `mapUserRow` 函数里：

```ts
function mapUserRow(row: UserRow): UserRecord {
  return {
    id: row.id,
    username: row.username,
    userCode: row.user_code ?? '',
    email: row.email,
    phone: row.phone ?? '',
    avatar: row.avatar ?? '',
    nickname: row.nickname ?? '',
    role: (['admin', 'manager', 'user'] as const).includes(row.role as UserRole) 
      ? (row.role as UserRole) : 'user',
    status: row.status === 'disabled' ? 'disabled' : 'active',
    createdAt: row.created_at,
  };
}
```

> 新手笔记：注意 role 的处理——如果数据库里存了个奇怪的值（不是 admin/manager/user），会静默归为 'user'。这是一种防御性编程，防止脏数据导致前端崩溃。

## 新手踩坑要点总结

### 1. preload 不能运行时 import 主进程模块

preload.ts 运行在独立的渲染上下文中，无法访问主进程的 `app`、`database` 等模块。如果写了 `import { getDatabase } from './database'`，会在模块加载阶段直接报错，导致白屏。

**例外：** `import type` 是安全的，因为纯类型引用在编译后会被完全擦除，不会产生运行时依赖。

### 2. 登录返回的 role 以数据库为准

旧实现曾经只返回布尔值，然后前端硬编码 `username === 'admin'` 来判断角色。这导致数据库中 `zhangsan` 的 `manager` 角色被无视。

现在的实现：`authLogin` 一次返回完整用户信息，role 以数据库为准，前端不二次判断。

### 3. bcrypt 哈希必须在主进程完成

密码的哈希和比对全部在主进程完成。如果把 bcryptjs 打进渲染 bundle，XSS 攻击时攻击者可以直接接触哈希逻辑。IPC 是本地进程间通信，传明文给主进程并不比渲染端先哈希更不安全。

### 4. Token 是演示级占位

当前 token 是 `'mock-token-' + Date.now()`，不是真正的 JWT 或 session token。这是项目的已知取舍——作为模板项目，不做完整的鉴权体系。生产环境需要替换为真实的 token 机制。

### 5. localStorage 可能存储失败

头像如果是 base64 编码的大图，可能超出 localStorage 配额（通常 5-10MB）。代码中有 try-catch 兜底，持久化失败不影响当前登录，但刷新后需要重新登录。

### 6. HashRouter 的必要性

Electron 打包后通过 `file://` 协议加载，`pathname` 是完整的磁盘路径。用 `createBrowserRouter` 会匹配不到任何路由。`createHashRouter` 从 `location.hash` 读路由，与文件路径无关。
