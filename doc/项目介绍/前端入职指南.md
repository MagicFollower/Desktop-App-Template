## 写在开头：你不需要懂所有东西

恭喜你加入团队。看到这份指南的第一反应可能是"这么多东西我完全没接触过"——这很正常。

我在带新人的时候发现一个规律：**新人最大的障碍不是技术难度，而是信息量太大导致的焦虑**。

所以这份指南的设计原则是：

1. **先让你跑起来**——第一章结束你就能在电脑上看到自己的第一个桌面应用界面

你现在不需要理解 Electron、Vite、TypeScript 这些名词。跟着第一章走，看到一个概念就回头查后面的解释，这样循环几次，你就自然掌握了。

## 第一章：5 分钟让你的项目跑起来

### 1.1 你需要准备什么

在开始之前，确保你的电脑上有以下工具：

| 工具 | 用途 | 下载地址 | 版本要求 |
|------|------|---------|---------|
| **Node.js** | 运行 JavaScript 的引擎，也是我们的包管理器 | https://nodejs.org | 推荐 v20 以上，LTS 版本 |
| **Git** | 代码版本管理工具 | https://git-scm.com | 最新版即可 |
| **代码编辑器** | 写代码用的编辑器 | 推荐 VS Code | https://code.visualstudio.com |

**验证安装是否成功**：打开终端（Windows 上按 `Win + R`，输入 `cmd`，回车），输入以下命令：

```bash
node -v
npm -v
git --version
```

如果分别输出了版本号（比如 `v20.11.0`、`10.2.4`、`git version 2.43.0`），说明安装成功。

> **新人小结：终端是什么？**
>
> 终端（Terminal）是一个黑色的命令行窗口，你直接输入文字命令让电脑执行操作。它看起来不如图形界面直观，但效率极高。前端开发中 80% 的操作都在终端完成（安装依赖、启动项目、提交代码等）。
>
> **Windows 用户提示**：除了 cmd，推荐使用 **Windows Terminal**（微软商店免费下载），它支持多标签页，体验更好。也可以在 VS Code 中按 `` Ctrl + ` `` 打开内置终端。

### 1.2 克隆项目并安装依赖

打开终端，进入你的工作目录（比如 `C:\Users\你的用户名\Documents`），然后：

```bash
# 把项目代码下载到你的电脑上
git clone <项目地址>

# 进入项目目录
cd desktop-app-template

# 安装项目依赖（这步需要等一会儿，大概 1-3 分钟）
npm install
```

**`npm install` 在做什么？**

想象你要做一道菜，首先需要去超市买食材。`npm install` 就是这件事——它读取项目中的 `package.json` 文件（里面列出了所有需要的"食材"），然后自动下载到你的电脑上，放在 `node_modules` 文件夹里。

> **新人小结：package.json 是什么？**
>
> `package.json` 是一个 JSON 格式的配置文件，是整个项目的"身份证"。它记录了：
> - 项目叫什么名字（`name`）
> - 版本号是多少（`version`）
> - 需要哪些依赖（`dependencies`）—— 就是项目运行必须的库
> - 开发时需要哪些工具（`devDependencies`）—— 比如编译器、打包工具
> - 可以执行哪些命令（`scripts`）—— 比如 `npm run dev` 就是启动开发服务器
>
> 你可以把它理解为一个项目的"采购清单 + 操作手册"。

### 1.3 启动项目

依赖安装完成后，运行：

```bash
npm run dev
```

这会做两件事：
1. 启动一个 Web 开发服务器（默认在 `http://localhost:5173`）
2. 自动打开一个桌面应用窗口，加载你的网页

**如果看到窗口了，恭喜你——你的第一个桌面应用跑起来了！**

接下来你会看到一个深色界面的应用，左侧有树形导航，右侧有实时更新的图表。这就是我们要搭建的框架的默认界面。

> **新人小结：localhost 是什么？**
>
> `localhost` 意思是"本机"，`http://localhost:5173` 就是"你电脑上的 5173 端口"。开发时你的代码运行在自己的电脑上，不需要联网，也不需要服务器。这就像你在自己家里做饭，不需要去餐厅。
>
> **为什么用 5173 端口？** 这是 Vite（我们用的构建工具）的默认端口号，你也可以在配置文件中修改。

### 1.4 停止项目

按终端中的 `Ctrl + C` 可以停止开发服务器。桌面窗口会保持运行，关掉它即可。

## 第二章：理解这个项目的" anatomy "（解剖结构）

跑起来之后，我们来看看这个项目到底是怎么组织的。

### 2.1 整体架构：两套系统协同工作

这个项目采用的是 **Electron 架构**，简单理解就是：

```
┌─────────────────────────────────────────────┐
│              一个桌面应用窗口                  │
├─────────────────────────────────────────────┤
│                                             │
│   ┌──────────────────┐  ┌────────────────┐  │
│   │   主进程 (Main)   │  │  渲染进程 (UI)  │  │
│   │   后台运行         │  │   你看到的一切   │  │
│   │                   │  │                │  │
│   │  • 创建和管理窗口   │  │  • 页面 UI      │  │
│   │  • 操作文件系统     │  │  • 用户交互     │  │
│   │  • 调用系统 API     │  │  • 数据展示     │  │
│   │  • 网络通信         │  │  • 图表渲染     │  │
│   └───────────────────┘  └───────┬────────┘  │
│            │    IPC 通信桥接       │           │
│            └──────────────────────┘           │
└─────────────────────────────────────────────┘
```

**用生活来类比**：

想象你是一个餐厅：
- **主进程** = 后厨：你在外面看不到，但它负责所有"脏活累活"——买菜（文件系统）、洗碗（系统操作）、跟供应商联系（网络通信）
- **渲染进程** = 前厅+菜品展示：顾客（用户）看到的一切都在这里——菜单（UI）、菜品（数据展示）、服务员的互动（用户交互）
- **IPC 桥接** = 传菜口：前厅和后厨通过传菜口交流，前厅不能直接进后厨（安全限制）

> **新人小结：为什么要分两个进程？**
>
> 这是 Electron 的核心设计思想。如果把所有代码放在一个地方，一个页面的 bug 可能导致整个应用崩溃。分开之后，UI 页面崩溃了，后厨（主进程）还在正常运行，你可以刷新页面恢复，而不需要重启整个应用。
>
> 另外，浏览器页面（渲染进程）不能直接操作文件系统、不能调用系统 API，这是安全限制。主进程可以，所以需要"桥接"——你通过桥接告诉主进程"帮我做这件事"，主进程做完后把结果传回来。

### 2.2 目录结构：每个文件在干什么

```
desktop-app-template/
│
├── package.json              ← "采购清单 + 操作手册"（前面讲过）
├── tsconfig.json             ← 渲染进程的 TypeScript 编译器配置
├── tsconfig.main.json        ← 主进程的 TypeScript 编译器配置
├── vite.renderer.config.ts   ← Vite 构建工具的配置
│
├── public/                   ← 静态资源文件夹（不会被编译，原样复制）
│   └── vite.svg              ← 应用图标
│
├── src/                      ← 源代码目录（你主要在这里工作）
│   │
│   ├── main/                 ← 【主进程】后台代码
│   │   ├── main.ts           ← 主入口：创建窗口、处理事件
│   │   └── preload.ts        ← 安全桥接：定义主进程和渲染进程之间的通信接口
│   │
│   └── renderer/             ← 【渲染进程】你看到的 UI 代码
│       ├── index.html        ← HTML 页面模板
│       ├── main.tsx          ← React 入口：把 App 组件渲染到页面上
│       ├── App.tsx           ← 根组件：整个应用的布局和状态管理
│       ├── index.css         ← 全局样式：重置默认样式、定义主题色
│       │
│       └── components/       ← UI 组件文件夹（每个功能一个文件夹）
│           ├── WindowControls/   ← 窗口控制按钮（红黄绿圆点）
│           ├── Sidebar/          ← 左侧导航栏
│           ├── TabBar/           ← 顶部标签页
│           ├── Dashboard/        ← 主内容区（统计卡片 + 图表）
│           └── RealtimeChart/    ← 实时图表组件
│
└── doc/                      ← 文档目录
    ├── 开发日志.md            ← 项目的开发过程记录
    └── 前端入职指南.md         ← 你正在看的这份文档
```

> **新人小结：为什么 main 和 renderer 分开？**
>
> 你可能注意到 `src/` 下面有 `main/` 和 `renderer/` 两个文件夹。这是因为 Electron 应用有"两个世界"：
>
> - `main/` 里的代码运行在 **Node.js 环境**中，可以 `require('fs')` 操作文件系统
> - `renderer/` 里的代码运行在 **浏览器环境**中，只能访问浏览器提供的 API
>
> 两个世界的代码不能混在一起写。就像你不能在后厨的菜谱上写前厅的菜单——虽然都是"菜"，但写法完全不同。

### 2.3 核心技术栈一览

| 技术 | 全称 | 一句话解释 | 在项目中扮演什么角色 |
|------|------|-----------|-------------------|
| **Electron** | - | 用 Web 技术做桌面应用 | 提供窗口管理、系统 API 访问能力 |
| **React** | - | 一个 JavaScript UI 库 | 构建用户界面，管理 UI 状态 |
| **TypeScript** | - | JavaScript 的超集，加了类型系统 | 给代码加"类型检查"，减少 bug |
| **Vite** | - | 极速的前端构建工具 | 开发时热更新，生产时打包压缩 |
| **Recharts** | - | React 图表库 | 绘制实时更新的图表 |

> **新人小结：TypeScript 是什么？为什么需要它？**
>
> 想象你在写一封邮件，如果不写收件人地址，邮件就寄不出去。TypeScript 就是在写代码之前先"检查地址对不对"。
>
> 普通 JavaScript：
> ```javascript
> function greet(name) {
>   return "Hello, " + name;
> }
> greet(123); // 不会报错，返回 "Hello, 123" —— 但你可能想要的是字符串！
> ```
>
> TypeScript：
> ```typescript
> function greet(name: string) {
>   return "Hello, " + name;
> }
> greet(123); // 报错！name 必须是 string 类型
> ```
>
> 在大型项目中，这种"类型检查"能帮你发现大量潜在 bug。尤其是多人协作时，TypeScript 让代码的"接口"（函数的输入输出）变得清晰明确。

## 第三章：深入理解关键概念

现在你已经能跑项目了，我们来深入理解几个核心概念。

### 3.1 Electron 主进程与渲染进程通信（IPC）

这是整个项目中最关键的机制。

**问题**：渲染进程（UI 页面）想告诉主进程"帮我最小化窗口"，但渲染进程没有这个能力，怎么办？

**解决方案**：通过 IPC（Inter-Process Communication，进程间通信）桥接。

```
┌─────────────────────────────────────────────────┐
│  渲染进程 (React)                                │
│                                                  │
│  用户点击"最小化"按钮                             │
│       │                                          │
│       ▼                                          │
│  window.electronAPI.minimize()                   │
│       │                                          │
│  ┌────▼────────────────────────────────────┐     │
│  │  preload.ts (桥接层)                     │     │
│  │  ipcRenderer.invoke('window:minimize')  │     │
│  └────▲────────────────────────────────────┘     │
│       │                                          │
├───────┼──────────────────────────────────────────┤
│       │  IPC 通信通道                             │
├───────┼──────────────────────────────────────────┤
│  主进程 (Node.js)                                │
│                                                  │
│  ipcMain.handle('window:minimize', () => {       │
│    mainWindow.minimize();                         │
│  });                                              │
│       │                                          │
│       ▼                                          │
│  窗口最小化 ✅                                    │
└─────────────────────────────────────────────────┘
```

**关键代码解读**：

**preload.ts**（桥接层，定义"能做什么"）：
```typescript
contextBridge.exposeInMainWorld('electronAPI', {
  // 暴露给渲染进程的方法
  minimize: () => ipcRenderer.invoke('window:minimize'),
  // ...其他方法
});
```

**main.ts**（主进程，定义"怎么做"）：
```typescript
ipcMain.handle('window:minimize', () => {
  mainWindow?.minimize();  // 真正执行最小化
});
```

**App.tsx**（渲染进程，调用方法）：
```typescript
(window as any).electronAPI?.minimize();  // 调用桥接方法
```

> **新人小结：为什么要这么复杂？**
>
> 你可能会觉得"直接调用不就行了，为什么要绕这么大一圈？"
>
> 这是 **安全设计**。如果渲染进程可以直接调用 `mainWindow.minimize()`，那一个有漏洞的网页就能控制你的整个桌面应用——它可以最小化你的窗口、关闭它、甚至读取你的文件。
>
> 通过 preload 桥接，我们只暴露**有限的、安全的 API** 给渲染进程。就像餐厅前厅只能点菜（发送请求），不能进后厨（操作系统），必须通过传菜口（IPC）来沟通。

### 3.2 实时数据流：从主进程到图表

项目中有一个"实时仪表盘"，每秒钟更新一次数据。我们来看看数据是怎么流动的。

```
主进程 (每 1 秒)                    渲染进程
┌──────────────┐                  ┌──────────────────┐
│ setInterval  │──send──▶         │ ipcRenderer.on   │
│ 生成随机数据   │  'mock-data'   │  接收数据         │
│              │                  │       │          │
│              │                  │       ▼          │
│              │                  │ setMockData()    │
│              │                  │ 更新 React 状态   │
│              │                  │       │          │
│              │                  │       ▼          │
│              │                  │ Recharts 重绘     │
└──────────────┘                  └──────────────────┘
```

**主进程代码**（`main/main.ts`）：
```typescript
const mockDataInterval = setInterval(() => {
  if (mainWindow && !mainWindow.isDestroyed()) {
    const data = {
      timestamp: Date.now(),
      commandsPerSec: Math.floor(Math.random() * 2) + 1,
      connectedClients: Math.floor(Math.random() * 3) + 1,
      // ...
    };
    mainWindow.webContents.send('mock-data', data);
  }
}, 1000);
```

**渲染进程代码**（`App.tsx`）：
```typescript
useEffect(() => {
  const api = (window as any).electronAPI;
  if (api) {
    api.onMockData((data: MockData) => setMockData(data));
    return () => api.removeMockDataListener(); // 组件卸载时清理
  }
}, []);
```

> **新人小结：useEffect 的清理函数为什么重要？**
>
> `return () => api.removeMockDataListener()` 这行代码看起来不起眼，但它是 **防止内存泄漏的关键**。
>
> 想象你租了一个房间（注册了一个事件监听器），搬走了（组件卸载）但没有退租（没有清理监听器），房间就会一直占着（内存泄漏）。在 Electron 应用中，内存泄漏可能导致应用越来越慢，最终崩溃。
>
> **记住这个模式**：任何 `useEffect` 中注册了定时器、事件监听器、WebSocket 连接的地方，都要在 return 中清理它们。

### 3.3 React 状态管理：为什么用 useState 就够了

这个项目没有使用 Redux、Zustand 等状态管理库，而是只用 React 内置的 `useState`。

**原因**：当前项目的状态都是"页面级"的，不需要跨多个组件共享的复杂全局状态。

```typescript
// App.tsx 中的状态
const [activeTab, setActiveTab] = useState('status');      // 当前选中的标签
const [tabs, setTabs] = useState<Tab[]>(initialTabs);      // 所有标签列表
const [sidebarSelected, setSidebarSelected] = useState('json'); // 侧边栏选中的项
const [mockData, setMockData] = useState<MockData | null>(null); // 实时数据
```

**什么时候需要引入 Redux/Zustand？**

| 场景 | 用 useState 够不够 | 建议 |
|------|------------------|------|
| 当前项目：标签、侧边栏选中、图表数据 | ✅ 够用 | 不需要额外库 |
| 用户登录状态需要全局共享 | ⚠️ 可以用 Context | 考虑 Context API |
| 复杂表单、多步骤流程 | ❌ 太复杂 | 考虑 Zustand |
| 大型电商应用，购物车+用户+商品多模块 | ❌ 必须用 | 考虑 Redux Toolkit |

> **新人小结：状态管理是"按需引入"，不是"越早越好"**
>
> 很多新人（甚至一些资深工程师）喜欢在项目一开始就引入 Redux/Zustand，觉得"专业"。但实际上，**过早引入状态管理库是常见的过度设计**。
>
> 判断标准很简单：**如果两个组件需要通过 props 传递数据超过 3 层，才需要考虑提升状态或使用状态管理库**。当前项目的组件层级很浅，`useState` + props 传递完全够用。

### 3.4 构建流程：从代码到可执行文件

理解构建流程对后续开发很重要。

```
开发阶段                          生产阶段
┌──────────────┐                ┌──────────────┐
│ npm run dev  │                │ npm run build │
│              │                │               │
│ Vite 启动    │                │ tsc 编译主进程 │
│ 开发服务器    │                │ Vite 构建渲染   │
│ HMR 热更新   │                │ electron-builder│
│ 加载 localhost│               │ 打包成 .exe     │
└──────────────┘                └──────────────┘
```

**开发阶段**（`npm run dev`）：
- Vite 启动开发服务器，代码改动后自动刷新（HMR = Hot Module Replacement）
- Electron 加载 `http://localhost:5173`，不经过编译
- 开发速度快，修改代码后 instantly 看到效果

**生产阶段**（`npm run build` + `npm run package`）：
1. `tsc` 把 TypeScript 编译成 JavaScript（`dist/main/`）
2. `vite build` 把 React 代码打包压缩（`dist/renderer/`）
3. `electron-builder` 把两个部分打包成一个 Windows 安装程序（`.exe`）

> **新人小结：为什么需要编译？**
>
> TypeScript 和 React JSX 语法（`<div className="xxx">`）浏览器和 Node.js 都看不懂，必须翻译成纯 JavaScript 才能运行。编译就是"翻译"的过程。
>
> 开发时 Vite 做了"懒翻译"——只翻译你当前改动的文件，所以很快。生产构建时 Vite 做了"全量翻译 + 压缩 + 优化"，所以生成的文件更小、运行更快。

## 第四章：组件开发实战指南

现在我们来实际开发一个组件，通过这个过程理解整个开发流程。

### 4.1 组件开发的标准流程

假设你要添加一个新的功能模块，比如"设置页面"。按照以下步骤：

**Step 1：创建组件文件**

```
src/renderer/components/
├── Settings/
│   ├── Settings.tsx        ← 组件逻辑
│   └── Settings.css        ← 组件样式
```

**Step 2：在 App.tsx 中引入并使用**

```typescript
import Settings from './components/Settings';

function App() {
  return (
    <div className="app">
      {/* 现有内容... */}
      <Settings />
    </div>
  );
}
```

**Step 3：在 CSS 中遵循项目的样式规范**

```css
.settings {
  background: #1a1a2e;
  border-radius: 8px;
  border: 1px solid #2a2a3e;
  padding: 24px;
}

.settings h2 {
  font-size: 18px;
  color: #e0e0e0;
  margin-bottom: 16px;
}
```

> **新人小结：组件开发的"三要素"**
>
> 每个组件必须有三个东西：
> 1. **逻辑**（`.tsx`）：组件做什么、怎么响应用户操作
> 2. **样式**（`.css`）：组件长什么样
> 3. **类型**（`.tsx` 中的 TypeScript 接口）：组件接收什么数据、输出什么
>
> 这三个东西缺一不可。缺少类型定义，其他开发者不知道怎么用你的组件；缺少样式，组件没有视觉效果；缺少逻辑，组件是空壳。

### 4.2 理解 Props（组件的输入）

Props 是父组件传给子组件的数据，就像函数的参数。

```typescript
// Sidebar.tsx 定义接收的 Props 类型
interface SidebarProps {
  selected: string;          // 当前选中的项 ID
  onSelect: (id: string) => void;  // 选中时的回调函数
}

// App.tsx 传递 Props
<Sidebar selected={sidebarSelected} onSelect={setSidebarSelected} />
```

**解读**：
- `selected="json"` → 告诉 Sidebar 当前选中的是 "json"
- `onSelect={setSidebarSelected}` → 告诉 Sidebar，当用户点击某个项时，调用 `setSidebarSelected` 来更新选中状态

> **新人小结：回调函数是什么？**
>
> `onSelect={setSidebarSelected}` 看起来有点绕，我们拆开看：
>
> `setSidebarSelected` 是一个函数（由 `useState` 返回），它的作用是"更新侧边栏的选中状态"。
>
> 我们把这个函数"传"给 Sidebar 组件，Sidebar 内部在用户点击时调用它：`onSelect('zh_cn')` → 实际执行 `setSidebarSelected('zh_cn')` → 侧边栏高亮 "zh_cn"。
>
> 这是一种 **"回调"模式**：父组件给子组件一个"做事的能力"，子组件在合适的时候调用它。这比让子组件直接修改父组件的状态要安全得多。

### 4.3 理解 useEffect（组件的生命周期）

`useEffect` 是 React 中最重要但也最容易让人困惑的 Hook。

**简单理解**：`useEffect` = "当某些东西变化时，自动执行一段代码"。

```typescript
// 示例 1：组件加载时执行一次
useEffect(() => {
  console.log('组件加载了！');
}, []); // 空数组 = 只在组件首次渲染时执行

// 示例 2：当 mockData 变化时执行
useEffect(() => {
  console.log('数据变了！', mockData);
}, [mockData]); // mockData 变化时重新执行

// 示例 3：设置定时器，组件卸载时清理
useEffect(() => {
  const timer = setInterval(() => {
    console.log('每秒执行');
  }, 1000);

  return () => clearInterval(timer); // 组件卸载时清理定时器
}, []);
```

> **新人小结：useEffect 的依赖数组**
>
> `useEffect` 第二个参数（依赖数组）决定了"什么时候重新执行"：
> - `[]` 空数组 → 只在组件**首次渲染**时执行一次
> - `[mockData]` → 当 `mockData` **变化**时重新执行
> - 不写第二个参数 → **每次渲染**都执行（不推荐，性能差）
>
> **常见错误**：在 useEffect 中使用了某个变量，但没有把它加入依赖数组。这会导致"闭包陷阱"——effect 中使用的是旧值。
>
> **解决**：把 effect 中用到的所有变量都加入依赖数组。如果 TypeScript 报"依赖不完整"的警告，不要忽略它，把它加进去。

### 4.4 理解 CSS 变量和主题系统

项目使用 CSS 类名来管理样式，而不是 CSS 变量（虽然可以用，但当前项目选择了更直接的类名方式）。

**主题色速查表**（建议收藏）：

```css
/* 背景色 */
#0f0f1a  主背景（最深，用于 body 和图表区域）
#1a1a2e  面板背景（用于侧边栏、卡片、图表容器）
#2a2a3e  边框色 / 悬停背景 / 滚动条

/* 文字色 */
#e0e0e0  主要文字（标题、重要数字）
#c0c0c0  次要文字（标签、普通文本）
#888888  弱化文字（占位符、徽章数字）
#666666  占位文字（输入框提示）

/* 强调色 / 功能色 */
#4a9eff  主强调色（蓝色，链接、选中状态、主按钮）
#ff6b9d  粉色（图表、standalone 标签）
#f5a623  橙色（图表、最大化按钮）
#2ecc71  绿色（成功状态、最小化按钮、master 标签）
#ff5f57  红色（关闭按钮）
```

> **新人小结：为什么不用 CSS 变量？**
>
> CSS 变量（`--primary-color: #4a9eff`）确实更方便管理主题，但当前项目选择了直接用十六进制颜色值。原因是：
> 1. 项目规模小，颜色值不会频繁变动
> 2. 直接写颜色值更直观，新人不需要理解"变量"这个概念
> 3. 后续如果要做主题切换，再引入 CSS 变量也不迟
>
> **建议**：在学完这个项目后，尝试用 CSS 变量重构颜色管理，这是一个很好的练习。

- 主进程和渲染进程的日志是分开的

### 5.2 常见错误及解决方案

**错误 1：`Cannot find module 'electron'`**

```
Error: Cannot find module 'electron'
```

**原因**：没有运行 `npm install`，或者 `node_modules` 损坏。

**解决**：
```bash
rm -rf node_modules package-lock.json
npm install
```

**错误 2：端口被占用**

```
Error: listen EADDRINUSE: address already in use :::5173
```

**原因**：5173 端口已经被其他程序占用（可能是之前启动的项目没有完全关闭）。

**解决**：
```bash
# Windows 上查找占用 5173 端口的进程
netstat -ano | findstr :5173

# 杀掉对应进程（把 <PID> 替换为实际进程 ID）
taskkill /PID <PID> /F
```

**错误 3：TypeScript 类型错误**

```
Argument of type 'number' is not assignable to parameter of type 'string'.
```

**原因**：传入了错误类型的参数。

**解决**：检查函数调用的参数类型，确保类型匹配。TypeScript 的错误信息通常很明确，跟着提示改就行。

## 第六章：项目规范与最佳实践

### 6.1 代码命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 文件名 | kebab-case（短横线分隔） | `realtime-chart.tsx` |
| 组件名 | PascalCase（大驼峰） | `RealtimeChart.tsx` |
| CSS 类名 | kebab-case | `.chart-container` |
| 变量名 | camelCase（小驼峰） | `mockData` |
| 常量名 | UPPER_SNAKE_CASE（全大写） | `MAX_RETRY_COUNT` |
| 接口/类型名 | PascalCase + 后缀 | `SidebarProps`、`TreeNode` |

### 6.2 组件编写规范

1. **每个组件一个文件夹**：逻辑和样式放在一起，便于维护
2. **Props 必须有类型定义**：
   ```typescript
   // ✅ 好的做法
   interface ChartProps {
     data: number;
     color: string;
   }
   
   // ❌ 不好的做法
   function Chart(props) { ... }  // 没有类型定义
   ```
3. **组件职责单一**：一个组件只做一件事。如果需要做两件事，拆成两个组件
4. **避免在组件中直接操作 DOM**：用 React 的方式（state + props）来管理 UI

### 6.3 Git 提交规范

```bash
# 格式：类型(范围): 描述

# 类型
feat:     新功能
fix:      修复 bug
docs:     文档变更
style:    代码格式（不影响功能）
refactor: 重构（不改变功能）
test:     测试相关
chore:    构建/工具相关

# 示例
git commit -m "feat(Sidebar): 添加搜索过滤功能"
git commit -m "fix(Dashboard): 修复图表数据更新时闪烁问题"
git commit -m "docs: 更新前端入职指南"
```

## 附录 C：FAQ（常见问题）

**Q：我没有用过 Electron，能直接上手吗？**

A：可以。这个项目已经封装好了 Electron 的复杂部分（窗口管理、IPC 通信），你主要关注 React 部分就行。Electron 的特定知识可以在需要时查阅文档。

**Q：TypeScript 不会写怎么办？**

A：先从简单的类型开始：`string`、`number`、`boolean`、`array`、`interface`。项目中大部分类型定义都在组件的 Props 接口中，照着抄就能学会。

**Q：为什么不用 Vue 或 Angular？**

A：这是团队的技术选型决策。React 在 Electron 生态中最成熟，社区资源最丰富。当然，如果你更熟悉 Vue，也可以尝试用 Vue 重写这个模板——这是一个很好的学习项目。

**Q：这个项目能直接用于商业项目吗？**

A：可以作为起点使用。但商业项目需要添加：错误处理、日志系统、国际化、单元测试、CI/CD 流水线、安全审计等。这个模板专注于 UI 框架和开发体验，业务逻辑部分需要你自己实现。
