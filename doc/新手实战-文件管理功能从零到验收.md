# 新手实战：文件管理功能从零到验收

> **写给谁**：刚加入本项目的前端开发。建议先读 `doc/新手实战-单据号规则功能从零到验收.md`（第一篇实战陪跑，架构速览与八条铁律不再重复），本篇默认你已了解六层通路、DTO 单一类型源、版本化迁移。
> **本次做什么**：亲手交付「文件管理」——上传（LOCAL 本地磁盘 / FTP 远程服务器，可配置切换）、单条删除（行右侧按钮）、批量删除（左侧多选 + 工具栏按钮）。
> **为什么这篇值得做**：文件是本项目第一个「**二进制数据 + 物理副作用**」的功能。之前的功能（用户/菜单/单据号）数据都只活在一个 SQLite 文件里；文件管理做错，会在用户磁盘留垃圾、甚至被恶意文件名攻击——它是把「CRUD 思维」升级为「资源管理思维」的最佳练手题。

## 0. 需求分析：把「文件管理」想清楚

### 0.1 需求描述（原始一句话）

> 「文件管理功能：支持文件上传，存储位置 LOCAL、FTP 可配置；支持删除——记录右侧按钮单条删，记录左侧多选后批量删。」

拆成可验收的点：

| # | 需求点 | 验收方式 |
|---|---|---|
| 1 | 上传：选择一个或多个文件 | 「上传文件」按钮弹出文件选择器，multiple |
| 2 | 存储 LOCAL/FTP 可配 | 「存储设置」弹窗可切换、可填 FTP 连接信息 |
| 3 | 单条删除 | 每行右侧「删除」按钮 → 确认 → 物理文件 + 记录一起消失 |
| 4 | 批量删除 | 行左侧 checkbox 多选 → 工具栏「批量删除」按钮 → 确认 |
| 5 | 列表 | 文件名/大小/存储位置/上传人/上传时间 |

### 0.2 三个关键设计决策（新手最容易跳过的部分）

**决策一：物理文件怎么存？——服务端重命名 + 月分桶，不信用户给的任何路径信息。**

渲染端传来的文件名是**不可信输入**：可能含路径分隔符（`../../etc/passwd`，路径穿越攻击）、Windows 非法字符（`<>:"|?*`）、控制字符。所以：

- 原始文件名只作**展示名**存库（清洗后）；落盘时服务端统一重命名为 `yyyyMMddHHmmss-<随机6位>-<清洗名>`——时间戳+随机段保证同毫秒上传同名文件不冲突；
- 相对目录由服务端按月生成 `yyyy/MM/`（月分桶），避免单目录文件数无限膨胀；
- 物理根目录由存储配置决定：LOCAL 默认 `userData/files`（可配绝对路径），FTP 是登录后的远程目录。

**决策二：删除的语义是什么？——物理尽力删，记录必删。**

「删除」要删两个东西：磁盘上的物理文件 + SQLite 里的记录。它们可靠性不对等：

- 物理文件可能已被用户在资源管理器手动删掉（`unlink` 报 ENOENT），FTP 可能网络不通——**这类失败不阻塞记录删除**，否则列表永远留着删不掉的幽灵记录；
- 记录是唯一权威（DB 在，入口就在）——记录删了，即使物理文件删失败，也不再产生用户可见的脏数据；删失败的物理文件记 warn 日志，人工可查。

> 对比单据号功能：那个是「失败即回滚」（被拦的创建不消耗计数），这里恰恰相反「失败也继续」——**没有放之四海皆准的失败策略，每个功能要想清楚「什么才是权威」**。DB 是记录的权威，磁盘不是。

**决策三：FTP 凭据怎么处理？——只写不读。**

`fileConfigGet` 的返回契约 `FileConfigRecord` **刻意不含 `ftpPassword`**：

- 渲染端编辑配置时不回显明文（编辑弹窗密码框永远为空，placeholder「留空 = 不修改」）；
- 保存契约 `FileConfigInput` 才有 `ftpPassword`，缺省表示不改密码；
- HTTP 通路（Dev API）也不下发密码——任何能打开 DevTools 的人都不该看到 FTP 明文密码。

与登录密码同一思路：**凭据只有两个合法时刻——写进去、用出来，中间永远不可见**。

### 0.3 数据模型设计

```sql
-- 迁移 v6：上传记录表
CREATE TABLE files (
  id TEXT PRIMARY KEY,            -- file-<时间戳>-<随机6位>
  name TEXT NOT NULL,             -- 清洗后的原始名（展示用）
  stored_name TEXT NOT NULL,      -- 服务端重命名的存储名（物理定位用）
  storage TEXT NOT NULL DEFAULT 'local',  -- 'local' | 'ftp'：该文件当时落在哪
  size INTEGER NOT NULL,          -- 字节数
  mime TEXT NOT NULL DEFAULT '',
  path TEXT NOT NULL DEFAULT '',  -- 相对目录 yyyy/MM/（不含文件名）
  uploaded_by TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL
);

-- 迁移 v6：存储配置表（单行表）
CREATE TABLE file_config (
  id INTEGER PRIMARY KEY CHECK (id = 1),   -- 单行约束：物理上杜绝多配置
  active_storage TEXT NOT NULL DEFAULT 'local',
  local_dir TEXT NOT NULL DEFAULT '',      -- 空 = userData/files
  ftp_host TEXT NOT NULL DEFAULT '',
  ftp_port INTEGER NOT NULL DEFAULT 21,
  ftp_user TEXT NOT NULL DEFAULT '',
  ftp_password TEXT NOT NULL DEFAULT '',
  ftp_root TEXT NOT NULL DEFAULT '',
  ftp_secure INTEGER NOT NULL DEFAULT 0    -- 1 = FTPS
);
```

两个新手问题提前回答：

- **为什么 `files.storage` 每行存，而不是查全局配置？** 存储类型随时可切换，但**已上传的文件不会搬家**——切换只影响新上传。每行记录自己当时的落点，删除时才知道去哪删。
- **为什么配置是单行表而不是键值对（key-value）？** 单行表 = 一次 `SELECT * WHERE id=1` 拿到强类型整行；键值对要 N 次查询或拼对象，类型全靠 cast。配置项固定就该用宽表，键值对适合配置项动态增减的场景。

### 0.4 边界与例外（需求完整性检查清单）

| 场景 | 决策 |
|---|---|
| 文件名全是非法字符（`???***`） | 清洗后为空 → 校验拒绝 |
| 文件名含路径穿越（`../../x`） | 分段剥 `..`，落点始终在存储根内 |
| 同一文件连选两次 | input value 清空 + 随机存储名，重传成功 |
| 单文件超 20MB | 拒绝（IPC 整块传输约束，见第 3 章） |
| 切到 FTP 但没填主机 | **保存时**就拒绝（不等首次上传才半路失败） |
| FTP 上传中途失败 | 不插记录（无孤儿），错误浮出到页面 |
| 删除时物理文件已不在磁盘 | ENOENT 容忍，记录照删 |
| 删除时 FTP 不可达 | 物理删失败记日志，记录照删 |

## 2. Step 2 契约：dto.ts 定义类型

**做什么**：`src/main/dto.ts` 追加「文件管理」区，四个类型。

**代码**（完整见源码，关键设计在注释里）：

```ts
export type FileStorage = 'local' | 'ftp';

export interface FileRecord {
  id: string;
  name: string;         // 原始文件名（清洗后，展示用）
  storedName: string;   // 服务端重命名的存储名（物理定位用）
  storage: FileStorage;
  size: number;
  mime: string;
  path: string;         // 相对目录 yyyy/MM/，物理根由存储配置决定
  uploadedBy: string;
  createdAt: string;
}

/** 存储配置：fileConfigGet 的返回。
 * 刻意不含 ftpPassword —— 密码只写不读 */
export interface FileConfigRecord {
  activeStorage: FileStorage;
  localDir: string;     // 空 = 默认 userData/files
  ftpHost: string;
  ftpPort: number;
  ftpUser: string;
  ftpRoot: string;
  ftpSecure: boolean;
}

/** 存储配置保存入参（字段缺省保留原值；ftpPassword 缺省 = 不改密码） */
export interface FileConfigInput {
  activeStorage?: FileStorage;
  localDir?: string;
  ftpHost?: string;
  ftpPort?: number;
  ftpUser?: string;
  ftpPassword?: string; // 只写不读：保存后任何出口不再返回
  ftpRoot?: string;
  ftpSecure?: boolean;
}

/** 上传入参的公共部分（二进制由各通路自行编码：IPC 传 Uint8Array，HTTP 传 base64） */
export interface FileUploadMeta {
  name: string;
  mime: string;
  uploadedBy?: string;
}
```

**为什么**：

- **安全边界画在契约层**：`FileConfigRecord`（读）没有 `ftpPassword`、`FileConfigInput`（写）才有——编译期就不存在「读出密码」的代码路径。与 `UserInput` 不含 `userCode`（服务端生成不可伪造）是同一手法：**TS 类型是免费的、最强的权限声明**；
- `FileUploadMeta` 与二进制分离：名字/MIME 走结构化对象，bytes 单独传——IPC 和 HTTP 对二进制编码方式完全不同（第 5 章详述），契约只描述「公共部分」，传输差异下放到适配层。

**踩坑与经验**：

> 渲染端 import 类型必须走 `services/sqlite.ts` 的 re-export（`import type { FileRecord } from '../../services/sqlite'`），**不要**从 `../../main/dto` 深度导入——渲染端 tsconfig 不含主进程目录，深度导入编不过。第一次写 FileManager.tsx 就这么栽了，18 个编译错误一次性涌出来。

## 3. Step 3 纯函数 + FTP 客户端

本功能**新增两个主进程文件**——都不依赖 electron/数据库，可被单测直接导入（与 `doc-number.ts` 同样的分层约定）。

### 3.1 `src/main/file-util.ts`：文件名清洗与校验

```ts
/** 清洗文件名：先按路径分隔符分段并剥 .. 穿越段，再逐段去 Windows 非法字符/控制字符、压缩空白，
 * 段间以空格连接（原分隔符不进文件名）；中文等 Unicode 正常保留。
 * 注意顺序：先分段后清洗——若先删分隔符，`../../etc/passwd` 会连成 `....etcpasswd`，穿越段再也剥不掉 */
export function sanitizeFileName(name: string): string {
  return name
    .split(/[\\/]/)
    .filter((seg) => seg !== '..' && seg !== '.')
    .map((seg) => seg.replace(/[:*?"<>|\u0000-\u001f]/g, '').replace(/\s+/g, ' ').trim())
    .filter((seg) => seg !== '')
    .join(' ');
}

/** 生成存储名：`yyyyMMddHHmmss-<随机6位>-<清洗后的原始名>` */
export function buildStoredName(originalName: string, now: Date): string;

/** 相对目录：按月分桶（yyyy/MM/） */
export function buildRelativeDir(now: Date): string;

/** 单文件大小上限（20MB）：IPC 结构化克隆整块传输，过大的文件会撑爆渲染/主进程内存 */
export const FILE_MAX_BYTES = 20 * 1024 * 1024;

/** 上传入参校验（service 层最后防线）：返回错误消息，null 表示通过 */
export function validateFileUpload(name: string, size: number): string | null;
```

**为什么上限 20MB**：本项目上传走 IPC 结构化克隆，整个文件要在渲染进程读成 ArrayBuffer、跨进程序列化、主进程再收一份——**内存峰值约 3 倍文件大小**。生产项目应改分片上传/流式管道；模板级以显式上限 + 明确报错兜底。这是典型的「**约束写进代码而不是文档**」——文档没人看，报错弹窗人人看得见。

**踩坑与经验（本功能最贵的一课）**：

> `sanitizeFileName` 第一版是「先删所有分隔符，再剥 `..`」——单测直接打脸：`../../etc/passwd` 先被删掉分隔符连成 `....etcpasswd`，后续无论怎么剥都剥不干净。**正确顺序是先分段、后清洗**：`split(/[\\/]/)` 拆段，整段等于 `..`/`.` 的直接丢弃，剩余段再逐个清洗。
>
> 通用教训：**处理「由多个危险 token 组合的输入」时，先结构化（分段/分词）再逐段处理**——字符级的删除/替换会把危险 token 焊接出新变体。也再次证明「给纯函数上单测」不是仪式感：这缺陷手工测试根本测不出（谁会手动传 `../../etc/passwd` 当文件名？），单测里它就是一行字符串。
>
> 顺带：控制字符正则 `\u0000-\u001f` 会触发 ESLint `no-control-regex`——这是安全清洗的刚需场景，行内 `eslint-disable-line` + 注明理由即可，不要为此改弱清洗规则。

### 3.2 `src/main/ftp-client.ts`：FTP 传输薄封装

用 [`basic-ftp`](https://www.npmjs.com/package/basic-ftp)（纯 JS、无原生编译依赖，与本项目 sql.js「免 native 编译」取向一致）：

```ts
export interface FtpConnectionConfig {
  host: string; port: number; user: string; password: string;
  secure: boolean; root: string;
}

/** 上传到 FTP：ensureDir 建远端分桶目录后 uploadFrom。
 * root 非空时以 root 为基拼接（POSIX 路径——FTP 协议层永远是 / 分隔） */
export async function ftpPut(cfg, relDir, storedName, data: Uint8Array): Promise<void>;

/** 删除 FTP 文件：550（文件不存在）视作已清理返回 false，其余错误抛出 */
export async function ftpRemove(cfg, relDir, storedName): Promise<boolean>;
```

**为什么**：

- **POSIX joinRemote 自己写**，不用 `path.join`——Node 的 `path.join` 在 Windows 上拼 `\`，FTP 服务器只认 `/`。跨平台代码里凡「远端路径」一律 POSIX；
- `ftpRemove` 对 550 特判：FTP 删不存在的文件报 550，语义上等于「已经是想要的状态」，吞掉它正是「物理尽力删」策略的一环；
- 20 秒超时 + finally close：网络操作没有超时就是薛定谔的挂起。

**踩坑与经验**：

> `basic-ftp` 曾因「看似没人用」在打包体积优化时被当死依赖删过——这次装回 `dependencies` 后它是**真依赖**（主进程运行时 import）。依赖死活的判断标准是「有无代码 import 它」，不是「有无功能看起来在用它」。

## 4. Step 4 业务层：service.ts 文件管理区

**做什么**：`src/main/service.ts` 追加约 200 行：五个导出函数 + 私有映射。核心节选：

```ts
export async function fileConfigSave(input: FileConfigInput) {
  const existing = await loadFileConfigRow(db);
  // 吸取 docRuleUpsert 教训：先读既有行合并，未传字段保持原值
  const merged = { activeStorage: input.activeStorage ?? ..., /* 逐字段合并 */ };
  if (merged.activeStorage !== 'local' && merged.activeStorage !== 'ftp') throw new Error('存储类型只能是 local 或 ftp');
  if (typeof merged.ftpPort !== 'number' || !Number.isInteger(merged.ftpPort)
    || merged.ftpPort < 1 || merged.ftpPort > 65535) throw new Error('FTP 端口需为 1-65535 的整数');
  // 切到 ftp 时前置校验主机：保存时就把配置缺口暴露出来，而不是等首次上传才半路失败
  if (merged.activeStorage === 'ftp' && !merged.ftpHost.trim()) throw new Error('切换到 FTP 前请先填写主机地址');
  db.run('UPDATE file_config SET ... WHERE id=1', [...]);
  db.persist();
}

export async function fileUpload(meta: FileUploadMeta, data: Uint8Array): Promise<FileRecord> {
  const cfg = await loadFileConfigRow(db);
  // 入参校验放 service 层：渲染端可绕过（HTTP 直调），这里是最后防线
  const error = validateFileUpload(meta.name, data.byteLength);
  if (error) throw new Error(error);
  const now = new Date();
  const storedName = buildStoredName(meta.name, now);
  const relDir = buildRelativeDir(now);
  const record: FileRecord = { id: `file-${now.getTime()}-${...}`, name: sanitizeFileName(meta.name), ... };
  if (storage === 'ftp') {
    if (!cfg.ftp_host) throw new Error('FTP 存储未配置主机地址，请先在存储设置中完善');
    await ftpPut(toFtpConfig(cfg), relDir, storedName, data);   // 物理先行
  } else {
    const abs = localAbsolutePath(cfg.local_dir, relDir, storedName);
    await fsp.mkdir(nodePath.dirname(abs), { recursive: true });
    await fsp.writeFile(abs, data);
  }
  db.run('INSERT INTO files ...');  // 物理成功才插记录（无孤儿）
  db.persist();
  return record;
}

export async function fileDelete(ids: string[]): Promise<{ deleted: number }> {
  // 单条/批量统一入口：单条即长度 1 的数组
  const rows = db.all(`SELECT * FROM files WHERE id IN (${placeholders})`, ids);
  // 物理删除（尽力而为）：ENOENT 容忍；FTP 失败也不阻塞记录删除
  for (const row of rows) {
    try {
      if (row.storage === 'ftp') { if (cfg.ftp_host) await ftpRemove(toFtpConfig(cfg), row.path, row.stored_name); }
      else await fsp.unlink(localAbsolutePath(...)).catch((err) => { if (err.code !== 'ENOENT') throw err; });
    } catch (err) {
      logger.warn(`[File] 物理文件删除失败（记录仍将删除）: ${row.stored_name}`, err);
    }
  }
  db.transaction(() => { db.run(`DELETE FROM files WHERE id IN (${placeholders})`, rowIds); });
  db.persist();
  return { deleted: rows.length };
}
```

**为什么**：

- **上传顺序：先物理后记录**。物理写失败（磁盘满/FTP 断连）异常直接抛、INSERT 不执行——不留「记录在、文件无」的孤儿记录（反过来「文件在、记录无」只是磁盘垃圾，用户不可见，危害小得多）；
- **删除顺序：先物理后记录 + 失败不回滚**。与上传相反——删除的权威是记录（0.2 决策二），物理失败仅记日志；
- **fileConfigSave 逐字段合并**：`input.X !== undefined ? input.X : existing.x`。这是上一轮 docRuleUpsert 覆盖缺陷（部分更新用默认值顶掉未传字段）的直接复用——同一个坑，项目里不会再有第三次；
- `resolveLocalRoot`：`localDir` 空串回落 `userData/files`，默认值收在 service 一处，页面 placeholder 只负责提示；
- 写函数尾部 `db.persist()`：sql.js 全内存不自动落盘（项目既有铁律，忘 persist = 重启丢数据）。

**踩坑与经验**：

> service 追加的 import（`app`、`fsp`、`nodePath`、`logger`）要么复用文件顶部已有的，要么补上——漏一个就是 build:main 报错。主进程文件不在渲染端 tsc 覆盖范围，**改完主进程必须跑 `npx tsc -p tsconfig.main.json --noEmit`**，别等 build 才发现。

## 5. Step 5 IPC + preload + HTTP：二进制怎么过桥

本功能与之前所有功能的**最大差异点**：之前六层传的都是可 JSON 化对象，这次还要过桥二进制。

### 5.1 IPC 通路：结构化克隆直传 Uint8Array

```ts
// src/main/ipc/file.ts（新建，薄壳 18 行）
export async function registerFileIpc(): Promise<void> {
  ipcMain.handle('file:list', () => svc.fileList());
  // 上传：二进制走 IPC 结构化克隆（Uint8Array 整块传输，单文件上限见 file-util.FILE_MAX_BYTES）
  ipcMain.handle('file:upload', (_event, meta: FileUploadMeta, data: Uint8Array) =>
    svc.fileUpload(meta, new Uint8Array(data)),
  );
  ipcMain.handle('file:delete', (_event, ids: string[]) => svc.fileDelete(ids));
  ipcMain.handle('file:config-get', () => svc.fileConfigGet());
  ipcMain.handle('file:config-save', (_event, input: FileConfigInput) => svc.fileConfigSave(input));
}
```

Electron 的 `ipcRenderer.invoke` 参数走**结构化克隆**（不是 JSON 序列化），`Uint8Array` 可原样过桥——所以 IPC 通路的二进制**什么都不用做**，直传即可。`new Uint8Array(data)` 是防御式拷贝，成本可忽略。

### 5.2 HTTP 通路：base64 编解码

Dev API 走 HTTP JSON，没有二进制字段——需要编解码：

```ts
// src/main/api-server.ts（服务端解码：base64 → Buffer）
if (pathname === '/api/files' && method === 'POST') {
  const { name, mime, uploadedBy, dataBase64 } = await readBody(req);
  const data = Buffer.from(String(dataBase64 || ''), 'base64');
  return json(await svc.fileUpload({ name: String(name || ''), mime: String(mime || ''), uploadedBy }, new Uint8Array(data)));
}
```

```ts
// src/renderer/services/adapter.ts（渲染端编码：分块 btoa 防 String.fromCharCode 展开爆栈）
function arrayBufferToBase64(buffer: ArrayBufferLike, byteOffset: number, byteLength: number): string {
  const bytes = new Uint8Array(buffer as ArrayBuffer, byteOffset, byteLength);
  let binary = '';
  const chunk = 0x8000;                       // 32KB 一块
  for (let i = 0; i < bytes.length; i += chunk) {
    binary += String.fromCharCode(...bytes.subarray(i, i + chunk));
  }
  return btoa(binary);
}
```

**为什么分块**：`String.fromCharCode(...bytes)` 的展开参数是数组字面量入栈——一次传几十万个参数，某些引擎直接 RangeError。0x8000 一批分次拼接，稳。

**架构要点**：编码差异被 adapter 吃掉了。`DataAdapter` 接口签名是 `uploadFile(meta, data: Uint8Array)`——**页面拿到的永远是 Uint8Array**，IpcAdapter 还是 HttpAdapter 在各自实现里决定直传还是转 base64。这就是六层通路的价值：新增「二进制」这种横切关注点时，页面代码零感知。

### 5.3 preload + electron.d.ts + main.ts

`preload.ts` 暴露 5 个方法、`electron.d.ts` 补 5 个签名（照抄 DTO 类型）、`main.ts` `await registerFileIpc()`。漏注册的话页面调用永远 pending 且**没有任何报错**（invoke 一个没人 handle 的 channel 返回 undefined，全靠类型检查兜返回值形状）——新增 IPC 后「页面白等没反应」先查 main.ts 注册没注册。

**踩坑与经验**：

> 有新人会想「把文件塞 BLOB 进库不就一个文件搞定」——小文件可以，20MB 级 BLOB 会把 sql.js 每次 `persist()` 的全量落盘放大成灾难。**元数据进库、二进制落文件系统**，是桌面应用的常规分界。

### 7.2 多选状态：Set<string> 而不是数组

```ts
const [selectedIds, setSelectedIds] = useState<Set<string>>(new Set());

const toggleAll = () => {
  setSelectedIds((prev) => {
    const allSelected = pagedFiles.length > 0 && pagedFiles.every((f) => prev.has(f.id));
    const next = new Set(prev);
    if (allSelected) pagedFiles.forEach((f) => next.delete(f.id));   // 本页全选 → 反选
    else pagedFiles.forEach((f) => next.add(f.id));                  // → 勾选本页
    return next;
  });
};
```

**为什么 Set**：勾选/反勾是 O(1) 的 `add/delete/has`；批量删除要 `Array.from(selectedIds)` 时再转数组。数组做 `includes` 判断是 O(n)，列表渲染每行都查一次。

**勾选语义的两个决策**（新手容易忽略的交互细节）：

- 全选只作用**本页**（`toggleAll` 基于 `pagedFiles`），不是全结果集——跨页全选容易误删，宁可让用户翻页；
- 删除/重载后 `setSelectedIds(new Set())` 清空——列表变了，旧勾选可能已指向不存在的记录，保留只会让「批量删除（3）」按钮骗人。

### 7.3 上传：隐藏 input + value 清空

```ts
const handleUploadClick = () => { setUploadError(''); fileInputRef.current?.click(); };

const handleFilesPicked = async (files: FileList | null) => {
  if (!files || files.length === 0) return;
  setUploading(true);
  let failed = 0; let lastError = '';
  for (const file of Array.from(files)) {
    try {
      // FileReader → ArrayBuffer → Uint8Array：适配层按通路编码（IPC 直传/HTTP 转 base64）
      const buffer = await file.arrayBuffer();
      await uploadFile({ name: file.name, mime: file.type, uploadedBy: username }, new Uint8Array(buffer));
    } catch (err) {
      failed += 1;
      lastError = err instanceof Error ? err.message : '上传失败';
    }
  }
  setUploading(false);
  if (fileInputRef.current) fileInputRef.current.value = '';   // 选完即清：同名文件可连续重传
  await reload();
  if (failed > 0) setUploadError(failed === 1 ? lastError : `${failed} 个文件上传失败（最后一个原因：${lastError}）`);
};
```

三个细节：

- **逐个串行上传而非 Promise.all 并发**：多文件并发写库在 sql.js 单连接下会互相 persist 打架；串行的失败隔离也简单（failed 计数 + 最后错误）；
- **上传后清 `input.value`**：不清的话，选同一个文件第二次 onChange 不触发（值没变）——用户会以为按钮坏了；
- **uploadedBy 取自登录态**（`useAuthStore((s) => s.userInfo?.username ?? '')`），不是让用户填。

### 7.4 删除：单条与批量共用一个 service 入口

```ts
const handleDeleteSingle = async () => {
  if (!deleteTarget) return;
  await deleteFiles([deleteTarget.id]);                 // 单条 = 长度 1 的数组
  setDeleteTarget(null);
  setSelectedIds((prev) => { const next = new Set(prev); next.delete(deleteTarget.id); return next; });
  await reload();
};

const handleDeleteBatch = async () => {
  if (selectedIds.size === 0) return;
  await deleteFiles(Array.from(selectedIds));           // 批量
  setBatchConfirmVisible(false);
  setSelectedIds(new Set());
  await reload();
};
```

**为什么契约是 `deleteFiles(ids: string[])` 而不是 `deleteFile(id)` + `deleteFiles(ids)` 两个函数**：单条即长度 1 的数组，service 层一个 `IN (...)` 查询天然覆盖。两个函数意味着两条几乎一样的代码路径、两份测试。**API 设计先看能不能合并，再考虑拆**。

批量删除按钮按需求放在「上传文件」右侧，未勾选时 disabled 并用 title 提示「先勾选左侧多选框」——按钮可见但不可点，比隐藏按钮有更好的可发现性。

### 7.5 存储设置弹窗

- LOCAL 显示「存储目录」一个字段（placeholder：留空 = 应用数据目录下的 files）；
- FTP 显示 主机/端口/用户名/密码/根目录/FTPS 六个字段；**密码框永远为空**（只写不读），placeholder「留空 = 不修改」；

## 10. 感悟（写给刚做完这个功能的你）

做完文件管理，回头看你应该能体会到三件事：

**第一，「资源」和「数据」不一样。** 用户、菜单、单据号是纯数据——它们的生命周期与 SQLite 文件同生共死。文件是资源——它有自己的物理存在，分布在磁盘或远端，记录只是它的「目录卡片」。删除资源时要想清楚谁权威、删除顺序、失败怎么办；上传资源时要想清楚名字可信吗、重名怎么办、写一半断电怎么办。**每引入一类新资源，就把这些问题重问一遍**——下一个可能是图片缓存、导出的 Excel、日志归档。

**第二，安全不是功能，是层层假设。** 这个功能没有一行代码叫「安全模块」，但安全无处不在：文件名当不可信输入（清洗）、密码只写不读（契约）、校验放 service 最后防线（渲染端可绕过）、上传物理先行（不留孤儿）。单据号功能的安全是「号源不可伪造」，这里的安全是「路径不可穿越 + 凭据不可回显」——**每个功能的安全间都长得不一样，但思路同源：找到不可信的输入面，把它挡在最外层**。

**第三，架构的价值在「新增横切关注点时」爆发。** 二进制传输是这个项目的第一个横切关注点（之前全是 JSON 可对象）。如果六层通路不存在，每个页面都要自己写「判断环境 → 选 IPC/HTTP → 编码二进制」；现在只有 adapter 的两个实现各改一处，页面完全无感。**好架构不是少写代码，而是让变化集中在一处**。

## 11. 迭代记录：路径展示与下载（2026-09-07）

### 11.1 需求

> 「列表支持显示文件完整路径与相对路径；支持单条下载与批量下载到指定目录。」

### 11.2 实施要点

**① 路径展示：fullPath 是「按当前配置视角」解析的展示字段。**

- 契约 `FileRecord` 新增必填 `fullPath`：local = 磁盘绝对路径；ftp = `ftp://host:port/远端路径`（拼接复用 ftp-client 导出的 `joinRemote`，POSIX 规则不重写第二遍）；
- 相对路径不加契约字段——`path + storedName` 两个字段已可直接拼接，服务端再算一遍是冗余；需要服务端信息（物理根）的才上契约（DTO 出口字段优先必填，但**不代表把一切可推导的都塞进去**）；
- 注意语义限制（已写进 DTO 注释）：配置变更后旧文件不迁移，fullPath 是定位参考而非迁移后的真值；
- `mapFileRow` 从无参映射改为 `(row, cfg)`——fullPath 依赖配置行，fileList 需先 `loadFileConfigRow`。

**② 下载：二进制不过渲染进程，主进程直连磁盘。**

- 目录选择用主进程 `dialog.showOpenDialog({ properties: ['openDirectory'] })`（IPC 层 handler，渲染端拿不到本机目录选择器）；
- `fileSaveTo(ids, targetDir)` 在主进程完成「读物理（LOCAL copyFile / FTP ftpDownload 到内存）→ 写目标目录」，一个函数同时服务单条（长度 1 的数组）与批量——与删除同构；
- 失败语义与删除相反：**下载要的是内容，单文件失败必须报出来**（`FileSaveResult.failed` 逐条收集 name+reason），但不阻塞其余文件；
- 目标文件名用原始展示名（而非存储名，用户预期是「下回原名」），重名自动 `名字 (n).ext` 递增，绝不覆盖已有文件（`uniqueDestPath`）；
- HTTP 通路：`/api/files/save` 供 curl 调试；`selectDownloadDir` 在 HttpAdapter 明确抛错「仅支持 Electron 窗口」——比静默降级诚实。

### 11.4 经验

> **同一资源的三种操作可以有三套失败语义**：上传「物理失败则回滚记录」（不留孤儿）；删除「物理尽力删，记录必删」（容忍缺失）；下载「单文件失败报错但不阻塞」（要内容）。新手常想找一个统一的 try/catch 模板套所有操作——不存在，先问「这个操作里谁是权威、什么算成功」。
>
> **下载文件名用展示名还是存储名？** 存储名全局唯一但用户不认识（`20260907-abc123-需求说明.pdf`）；展示名友好但会重名——所以有 `名字 (n).ext` 递增兑底。命名策略跟从用户场景，技术唯一性只负责不覆盖。

### 11.5 迭代二：两个缺陷修复（按钮样式 / 下载报错）

**① 批量删除按钮「不统一不美观」的真相：`.btn-danger` 从未被定义。**

工具栏三个按钮：`btn-primary`（pages.css，实心蓝）、`btn-danger`（**无任何定义**，渲染成浏览器默认灰按钮）、`btn-secondary`（定义在 Modal.css，13px 偏小）。修复：

- pages.css 补全局 `.btn-danger`（与 btn-primary 同规格的实心红），三个类统一 `:disabled` 态（opacity 0.5 + not-allowed）；
- `.btn-secondary` 从 Modal.css 提升到 pages.css 并对齐尺寸（8px 16px / 14px）——组件私有样式被页面工具栏借用本来就是漂移源，借用了就该提升为全局。

**② 下载报「selectDownloadDir is not a function」的两层原因。**

- 直接原因：preload 只在页面加载时注入一次——开发中改了主进程代码，Vite HMR 让渲染端拿到新页面（有下载按钮），但 Electron 进程还是旧 preload，新方法自然不存在；
- 顺带发现的环境问题：验证时误跑了 `npx vite build`（未带 `--config vite.renderer.config.ts`），vite 默认 outDir=dist 且 emptyOutDir=true，把 tsc 产出的 dist/main 整个清掉——**构建必须走项目脚本**（`npm run build:renderer`），裸 CLI 工具不知道项目约定；
- 防御：IpcAdapter 新增 `requireMainApi` 能力检测，方法缺失时报「主进程版本过旧（缺少目录选择）：请重启 npm run start 后重试」——把不可理解的技术错误翻译成用户可执行的动作。

> **Electron 开发常识**：渲染端改动 HMR 即生效；主进程/preload 改动必须重启 npm run start（concurrently 不会自动重启 electron）。遇到「页面有按钮但一调 API 就 is not a function」，先想 preload 版本不匹配。

### 11.7 迭代三：目录结构（多级目录 / 只删空目录）

**核心决策：逻辑目录，不物理镜像。**

目录是纯组织层（file_dirs 表 + files.dir_id 列），物理文件仍按 yyyy/MM 月分桶不动。为什么不把目录落盘？——物理镜像需要递归建目录/递归删目录/FTP 递归同步/配置变更后目录树迁移，复杂度全部翻倍；而「只允许删空目录」在逻辑层只需两次 COUNT。目录与物理存储解耦后，删除目录零物理副作用，FTP/LOCAL 两种后端零分支。

**多级目录的实现：parent_id 自引用 + DFS 序扁平列表。**

- file_dirs 不建 parent_id 外键：业务规则是「只允许删空目录」（应用层校验），ON DELETE CASCADE 反而会绕过规则连锢子目录；
- fileDirList 出口是扁平 DFS 序（父必在子前）+ fileCount（含子目录累加）——渲染端按深度缩进直接逐行渲染，不需要再组树；
- 同层不查重：目录 id 全局唯一已足够，同名兄弟目录用场景很少，查重逻辑反而拦住合法场景；
- 目录名清洗复用 sanitizeFileName：逻辑目录虽不落盘，但名字进 DB 与 UI，防注入性展示与后续物理化时的穿越。

**三处边界语义：**

- 上传时 dirId 指向已删除目录 → 拒绝上传（不静默落未分组，否则用户文件丢进「看不见的目录」）；
- 删除目录：有子目录或有文件（含子目录内）都拒绝，错误消息直指处置方式；
- 删除文件不动目录（文件删完目录自然变空，用户再删）。

**页面交互：**

- 左侧目录侧栏（240px）：根行「全部文件」（含未分组）+ 目录树行（深度缩进 + 文件计数），悬停出现「子目录/删除」行内操作；
- 选中目录 = 文件列表过滤为该目录**含子目录**的文件；上传按钮变为「上传文件到「目录名」」——选中目录视图下上传即入该目录；
- 表格新增「目录」列（未分组弱化展示）；空态按选中目录区分文案。

> **两个进阶 React 坑（本迭代踩过）**：① **TDZ**——useQueryTable 内部的 useMemo 首次渲染就执行 filter，filter 闭包引用的 const（selectedSubtreeIds/filterByDirAndKey）必须声明在 hook 调用**之前**，否则报「Cannot access before initialization」；② **过滤不重算**——filtered 的 useMemo 只依赖 [records, query]，选中目录变化不在依赖里，切换目录后列表不会刷新，需在 selectDir 里同步 reload() 拉新 records 触发重算。自定义 Hook 的闭包状态依赖问题，要么改 Hook 依赖，要么在调用侧主动触发数据重拉。
>
> **列表/侧栏双数据源的同步刷新（迭代四修复）**：文件列表（reload）与目录侧栏计数（reloadDirs）是两条独立数据流，凡改变文件↔目录归属的操作（上传/删文件/删目录）都必须两边同步刷新，漏一边就出现「上传后计数不变」。另：确认框的错误提示必须在 Modal **保持打开**时展示——先关 Modal 再 setErr 的错误会被吞掉（无处显示）。
>
> **两个展示层细节（迭代五修复）**：① **flex 子项宽度随内容收缩**——.file-page 是 flex 容器，QueryTableLayout 根元素默认 flex: 0 1 auto，删数据后表格内容变窄连带整个右侧区域收缩，需显式 flex: 1 + min-width: 0；② **IPC 错误前缀**——ipcRenderer.invoke 抛错时 Electron 会包一层「Error invoking remote method 'channel': Error: 原始消息」，业务提示不应携带这层技术前缀，适配层加 invokeClean 统一剥离（重抛时保留 cause 链，lint preserve-caught-error 要求；Error cause 是 ES2022 特性，tsconfig 需补 lib "ES2022.Error"）。
