# 一、设计背景

要理解 Vite 为什么存在，必须先理解它出现之前的世界。这一章我们回溯前端工程化的演进史，看看是什么痛点催生了 Vite。

## 1.1 前端工程化的历史起源

最早的网页是"静态"的——一个 HTML 文件，里面写死所有内容。那时候没有"构建"这个概念，你把 HTML 文件丢到服务器上，浏览器就能直接打开。

随着网页越来越复杂，出现了三个需求：
1. **复用**：多个页面有相同的头部和尾部，不想复制粘贴
2. **模块化**：JavaScript 代码越来越多，需要拆分管理
3. **自动化**：压缩代码、处理图片、编译预处理器（如 Sass）需要自动完成

这三个需求催生了"前端工程化"——用工程化的方法管理前端代码。而**构建工具**就是工程化的核心基础设施。

> **新人小结**
>
> 你可以把"构建工具"想象成一家餐厅的**中央厨房**。食材（源代码）进来，经过切配、烹饪、装盘（编译、压缩、打包），变成成品（浏览器能运行的代码）。没有中央厨房，你就得手动处理每一份食材，效率极低。

## 1.2 jQuery 时代的"无构建"开发

2006 年到 2015 年左右，是 jQuery 的黄金时代。那时候的开发模式非常简单：

```html
<script src="jquery.js"></script>
<script src="my-script.js"></script>
```

直接在 HTML 里用 `<script>` 标签引入 JavaScript 文件，浏览器按顺序执行。**没有打包，没有编译，没有构建**。

这种模式的优点是简单直观，但缺点也很明显：
- **全局变量污染**：所有脚本共享同一个全局作用域，变量名冲突是家常便饭
- **加载顺序依赖**：脚本必须按正确顺序引入，否则报错
- **无法模块化**：没有 `import`/`export`，代码组织全靠约定

> **新人小结**
>
> 理解这个阶段很重要，因为今天很多"看起来多余"的工程化配置，其实都是在解决这个时代遗留的问题。比如模块化打包，最初就是为了解决全局变量污染。

## 1.3 模块化打包器的崛起

为了解决 1.2 节的问题，社区开始探索"模块化"方案。

**CommonJS**（Node.js 的模块规范）：
```javascript
const fs = require('fs');
module.exports = myFunction;
```

**AMD**（异步模块定义，浏览器端）：
```javascript
define(['dependency'], function(dep) {
  return myFunction;
});
```

但这些模块规范浏览器原生不支持，于是出现了**打包器**（bundler）——把多个模块文件合并成一个浏览器能理解的文件。

代表性工具：
- **RequireJS**（AMD 规范）
- **Browserify**（把 CommonJS 打包给浏览器用）

这是"打包"概念的起源：**把一堆文件，捆成一个文件**。

## 1.4 Webpack 时代的统治

2014 年，Webpack 出现，并逐渐成为事实标准。它的核心能力：

1. **模块打包**：把 JS、CSS、图片等所有资源都当作"模块"处理
2. **依赖图谱**：自动分析模块之间的依赖关系，生成依赖树
3. **Loader 机制**：通过 loader 处理各种非 JS 文件（如 CSS、图片）
4. **Plugin 机制**：通过插件扩展功能
5. **代码分割**：把代码拆成多个块，按需加载

Webpack 极其强大，但也越来越复杂。一个中大型项目的 `webpack.config.js` 动辄几百行，配置项多达上百个。

> **新人小结**
>
> Webpack 就像一个**全能但复杂的瑞士军刀**——什么都能干，但每个功能都需要你手动配置。对于新手来说，光是理解"为什么要这么配置"就要花很长时间。这就是后来者（包括 Vite）想要解决的问题。

## 1.5 构建速度问题的演变

Webpack 虽然功能强大，但有一个致命弱点：**慢**。

慢的根本原因在于它的工作方式：

```
启动开发服务器
    ↓
读取所有源文件
    ↓
构建完整的依赖图谱（遍历所有模块）
    ↓
把所有模块打包成 bundle
    ↓
启动服务器，提供 bundle
```

问题在于**启动时必须打包所有代码**。项目越大，模块越多，启动越慢。一个有几千个模块的大型项目，冷启动可能要 30 秒甚至几分钟。

而且每次修改代码，Webpack 需要重新打包受影响的部分，这也会带来明显的等待。

**这就是"构建速度问题"——随着项目规模增长，开发体验急剧下降。**

## 1.6 开发体验的痛点

除了慢，传统打包工具还有其他开发体验痛点：

| 痛点 | 具体表现 | 对开发者的影响 |
|------|---------|---------------|
| **启动慢** | 冷启动 30 秒到几分钟 | 每次开机都要等，打断心流 |
| **热更新慢** | 改一行代码等几秒才生效 | 频繁等待，效率低下 |
| **配置复杂** | 几百行配置文件 | 新人上手难，维护成本高 |
| **Source Map 慢** | 生成调试信息耗时 | 调试体验差 |
| **内存占用高** | 大型项目占用几 GB 内存 | 电脑卡顿 |

这些痛点叠加起来，让"写代码 5 分钟，等构建 10 分钟"成为很多团队的日常。开发者迫切需要一个新的工具来打破这个困境。

## 1.7 浏览器对 ES Module 的支持演进

转机出现在浏览器层面。**ES Module**（ESM）是 JavaScript 的官方模块标准：

```javascript
import { foo } from './module.js';
export function bar() { ... }
```

浏览器对 ESM 的支持是逐步演进的：

| 时间 | 浏览器 | 支持情况 |
|------|--------|---------|
| 2017 | Safari 10.1 | 首个原生支持 ESM 的主流浏览器 |
| 2017 | Chrome 61 | 支持 ESM |
| 2018 | Firefox 60 | 支持 ESM |
| 2020 | Edge 79（Chromium 版） | 支持 ESM |
| 至今 | 所有现代浏览器 | 完整支持，包括动态 `import()` |

关键点：**浏览器现在能原生理解 `import`/`export` 了，不再需要打包器把模块"翻译"成浏览器能懂的形式。**

这为一种全新的思路打开了大门：既然浏览器能直接加载模块，那开发时为什么还要打包？

## 1.8 原生 ES Module 生态的成熟

浏览器支持 ESM 只是第一步，生态的成熟同样关键：

1. **HTTP/2 普及**：早期 ESM 的问题是"一个文件一个请求"，在 HTTP/1.1 下会产生大量请求。HTTP/2 的多路复用解决了这个问题，让多个小文件能并行传输。
2. **`<script type="module">` 标准化**：HTML 标准明确了如何在页面中加载 ESM。
3. **动态 `import()` 支持**：允许运行时按需加载模块，为代码分割提供了原生能力。
4. **import maps**（后续支持）：允许自定义模块路径映射。

这些条件的成熟，意味着"不打包、直接用原生 ESM 开发"在技术上变得可行。

> **新人小结**
>
> 这里有一个关键认知转变：**打包不是目的，让浏览器能运行代码才是目的**。既然浏览器现在能直接运行 ESM，那么开发阶段就可以跳过打包这一步，直接从源文件服务代码。这就是 Vite 的核心思想。

## 1.9 esbuild 的诞生

如果说浏览器 ESM 支持提供了"可能性"，那么 **esbuild** 的出现提供了"速度"。

esbuild 是一个用 **Go 语言**编写的 JavaScript 打包器和压缩器。它的核心特点是**极快**——比传统的 JavaScript 编写的工具（如 Babel、Webpack）快 10 到 100 倍。

快的原因：
1. **Go 语言编写**：编译型语言，执行速度远超 JavaScript
2. **并行处理**：充分利用多核 CPU
3. **零依赖设计**：从头实现解析器、转换器，没有历史包袱
4. **内存优化**：减少内存分配和垃圾回收

esbuild 于 2020 年发布，正好赶上了"前端工具链需要提速"的历史节点。它成为了 Vite 的核心引擎之一。

## 1.10 Vue 3 的诞生与尤雨溪的思考

Vite 的作者是**尤雨溪**（Evan You），他同时也是 Vue 框架的作者。

2020 年，尤雨溪在开发 Vue 3 时，深刻感受到传统构建工具（当时 Vue CLI 基于 Webpack）的瓶颈。他开始思考：

> "如果浏览器原生支持 ESM，我们能不能在开发时完全不打包，只在生产环境打包？"

这个想法最终催生了 Vite。最初，Vite 是作为 Vue 3 的配套开发工具而生的，但它的设计是**框架无关**的，很快就被 React、Svelte 等社区采用。

"Vite" 这个名字来自法语，意为"快速"（fast），发音类似 "veet"。这个名字直接点明了它的核心追求——**快**。

# 二、设计目的

理解了背景，我们来看 Vite 的设计目的。它到底想解决什么问题，达成什么目标？

## 2.1 毫秒级启动开发服务器

**目标**：无论项目多大，开发服务器都能在毫秒级启动。

**实现思路**：开发时不打包。服务器启动时，不做任何全量的代码转换，只是简单地启动一个 HTTP 服务器。当浏览器请求某个模块时，才按需转换那个模块。

**对比**：
- Webpack：启动时打包所有模块 → 项目越大越慢
- Vite：启动时几乎不做事 → 项目大小几乎不影响启动速度

> **新人小结**
>
> 这就像外卖的两种模式：
> - Webpack = 中央厨房先把所有菜做好，再配送（启动慢，但配送快）
> - Vite = 接到订单才开始做菜（启动快，按需制作）
>
> 对于"开发"这个场景，我们更希望"点单后立即看到结果"，所以 Vite 的按需模式更合适。

## 2.2 极速的热模块替换（HMR）

**目标**：修改代码后，浏览器能在一秒内更新，且保留组件状态。

**HMR**（Hot Module Replacement，热模块替换）是指：修改代码后，只替换发生变化的模块，不刷新整个页面。

Vite 的 HMR 之所以快，是因为它基于**原生 ESM**：
- 修改一个模块，只需重新请求那一个模块
- 不需要重新打包整个依赖链
- 更新速度与项目规模无关

传统打包工具的 HMR 速度会随项目规模下降，而 Vite 的 HMR 始终保持快速。

## 2.3 开箱即用的零配置体验

**目标**：新项目不需要写任何配置就能运行。

运行 `npm create vite@latest` 后，生成的项目开箱即用，不需要写 `vite.config.js`（除非你要自定义）。

这是因为 Vite 内置了大量**合理的默认配置**：
- 自动处理 TypeScript
- 自动处理 JSX
- 自动处理 CSS（包括 PostCSS）
- 自动处理静态资源
- 内置开发服务器和 HMR

只有当你需要定制时，才需要写配置文件。这大大降低了上手门槛。

> **新人小结**
>
> "约定优于配置"（Convention over Configuration）是 Vite 的核心哲学。它假设大多数项目的需求是相似的，所以提供一套覆盖 90% 场景的默认配置。你只需要关心剩下 10% 的个性化需求。

## 2.4 框架无关的设计

**目标**：不为任何特定框架服务，支持所有主流前端框架。

虽然 Vite 诞生于 Vue 生态，但它从设计上就是框架无关的。通过**插件机制**，Vite 可以支持：
- Vue（`@vitejs/plugin-vue`）
- React（`@vitejs/plugin-react`）
- Svelte（`@sveltejs/vite-plugin-svelte`）
- Solid、Preact、Lit 等

这也是为什么我们的项目（React + Electron）能用 Vite——只需要引入 `@vitejs/plugin-react` 插件。

## 2.5 原生 ES Module 优先

**目标**：开发和生产都尽可能使用原生 ESM，减少对打包的依赖。

**开发时**：完全不打包，直接服务原生 ESM。
**生产时**：使用 Rollup 打包（因为生产环境仍需优化，如代码压缩、Tree Shaking、兼容性处理）。

这种"开发不打包、生产打包"的双轨设计，是 Vite 区别于传统工具的根本特征。

## 2.6 闪电般的生产构建

**目标**：生产构建要快，产物要小。

Vite 的生产构建使用 **Rollup**，并配合：
- **esbuild 预压缩**：用 esbuild 做初步的转换和压缩，速度极快
- **Tree Shaking**：移除未使用的代码
- **代码分割**：按需拆分包
- **资源内联与优化**：小资源转 base64，大资源加哈希缓存

实测中，Vite 的构建速度通常比 Webpack 快 2-5 倍。

## 2.7 强大的插件生态

**目标**：通过插件机制，让社区能扩展 Vite 的能力。

Vite 的插件系统**兼容 Rollup 插件接口**，这意味着大量现有的 Rollup 插件可以直接在 Vite 中使用，极大丰富了生态。

同时，Vite 提供了自己的插件钩子（如 `configureServer`、`transformIndexHtml`），让插件能深度介入开发和构建流程。

## 2.8 TypeScript 一等公民

**目标**：无需额外配置就能开发 TypeScript 项目。

Vite 内置了 TypeScript 支持：
- 自动转换 `.ts`/`.tsx` 文件（使用 esbuild）
- 支持 `../../tsconfig.json` 中的路径别名
- 无需安装 `ts-loader` 或 `babel-loader`

但要注意：**Vite 只做语法转换，不做类型检查**。类型检查由编辑器（通过 tsc）或独立的 `tsc --noEmit` 命令完成。这种分离让构建更快。

> **新人小结**
>
> 这是一个常见误解：很多人以为 Vite 会检查 TypeScript 类型错误。实际上不会。Vite 只是把 TypeScript 语法"翻译"成 JavaScript，类型对不对它不管。类型检查是编辑器或 `tsc` 的职责。所以你可能在 Vite 构建通过的情况下，仍然有类型错误——记得运行 `tsc --noEmit` 来检查。

## 2.9 跨平台与多环境支持

**目标**：在 Windows、macOS、Linux 上行为一致，并支持多环境配置。

- **跨平台**：路径处理使用跨平台兼容的方式（如 `path.resolve`）
- **多环境**：通过 `.env` 文件和环境模式（development/production）管理不同环境的配置

## 2.10 长期可维护性与性能基准

**目标**：工具本身要易于维护，且性能有明确的基准和回归测试。

Vite 团队建立了：
- **性能基准测试**（benchmark）：每次发版都跑性能测试，防止性能回归
- **完善的测试套件**：覆盖核心功能和边界情况
- **清晰的 RFC 流程**：重大变更通过 RFC（Request for Comments）讨论

这保证了 Vite 在快速迭代的同时，不会引入性能退化或破坏性变更。

# 三、完整技术设计架构

这一章深入 Vite 的技术架构。我们会从整体到局部，拆解它的每一个组成部分。

## 3.1 整体架构图

Vite 的整体架构可以分为三层：

```
┌─────────────────────────────────────────────────┐
│              用户层（User Layer）                  │
│   vite.config.ts / index.html / 源代码            │
└────────────────────┬────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────┐
│              核心层（Core Layer）                  │
│  ┌──────────────┐    ┌──────────────────────┐   │
│  │ 开发服务器     │    │  构建器（Builder）     │   │
│  │ (Dev Server)  │    │  (Rollup-based)      │   │
│  └──────────────┘    └──────────────────────┘   │
│           │                      │               │
│  ┌────────▼──────────────────────▼─────────┐    │
│  │         插件系统（Plugin System）          │    │
│  └─────────────────────────────────────────┘    │
└────────────────────┬────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────┐
│              引擎层（Engine Layer）                │
│   esbuild（依赖预构建、TS转换）                     │
│   Rollup（生产构建）                              │
│   PostCSS（CSS 处理）                             │
└─────────────────────────────────────────────────┘
```

- **用户层**：你写的代码和配置
- **核心层**：Vite 的核心逻辑，包括开发服务器和构建器
- **引擎层**：Vite 依赖的底层工具（esbuild、Rollup、PostCSS）

## 3.2 开发与构建的双引擎架构

Vite 最独特的设计是**开发和构建使用不同的引擎**：

| 阶段 | 引擎 | 原因 |
|------|------|------|
| **开发** | esbuild + 原生 ESM | 追求启动速度和 HMR 速度 |
| **构建** | Rollup | 追求产物质量（Tree Shaking、代码分割） |

**为什么开发用 esbuild 而不是 Rollup？**
- esbuild 快 10-100 倍，适合"按需转换"的开发场景
- 开发时不需要 Tree Shaking 等重型优化

**为什么构建用 Rollup 而不是 esbuild？**
- 生产构建需要成熟的 Tree Shaking、代码分割、插件生态
- esbuild 在这些方面还不够成熟（Vite 6 时代）
- Rollup 产物质量更可控

> **新人小结**
>
> 这种"双引擎"设计是 Vite 的精髓。它承认了一个现实：**开发和生产的诉求不同**。开发要快（快速反馈），生产要优（产物质量）。用同一个工具同时满足两者，往往两头都不讨好。Vite 干脆用两个最合适的工具分别处理。

## 3.3 esbuild 的核心角色

esbuild 在 Vite 中承担多个职责：

1. **依赖预构建**（Dependency Pre-bundling）：把 `node_modules` 中的依赖转换成浏览器友好的 ESM 格式
2. **TypeScript/JSX 转换**：快速把 `.ts`/`.tsx` 转换成 JavaScript
3. **生产构建的预压缩**：在 Rollup 打包前，先用 esbuild 做初步转换提速

esbuild 的速度优势是 Vite 开发体验的基础。

## 3.4 Rollup 在生产构建中的角色

生产构建时，Vite 实际上是**配置并调用 Rollup**：

```
vite build
    ↓
Vite 读取配置，生成 Rollup 配置
    ↓
Rollup 执行：
  - 解析依赖图谱
  - Tree Shaking（移除死代码）
  - 代码分割
  - 调用插件转换代码
    ↓
输出优化后的产物到 dist/
```

Vite 对 Rollup 做了大量封装和默认配置，让开发者不需要直接面对 Rollup 的复杂性。

## 3.5 插件系统设计

Vite 的插件系统是其可扩展性的核心。一个插件本质上是一个对象，包含若干**钩子函数**（hooks）：

```javascript
export default function myPlugin() {
  return {
    name: 'my-plugin',

    // 在解析配置后调用
    configResolved(config) { ... },

    // 配置开发服务器（添加中间件等）
    configureServer(server) { ... },

    // 转换单个模块
    transform(code, id) { ... },

    // 构建开始时调用
    buildStart() { ... },

    // 生成产物时调用
    generateBundle(options, bundle) { ... },
  };
}
```

Vite 的插件钩子分为两类：
- **通用钩子**：与 Rollup 兼容（如 `transform`、`buildStart`）
- **Vite 专有钩子**：只在 Vite 中有效（如 `configureServer`、`transformIndexHtml`）

## 3.6 开发服务器的请求管道

开发服务器是 Vite 的心脏。它本质上是一个 **Node.js HTTP 服务器**（基于 Connect 中间件框架），通过一系列中间件处理请求：

```
浏览器请求 /src/App.tsx
    ↓
┌─────────────────────────────┐
│ 1. 静态资源中间件             │ → 直接返回静态文件
├─────────────────────────────┤
│ 2. 依赖预构建中间件           │ → 返回预构建的依赖
├─────────────────────────────┤
│ 3. 转换中间件（transform）    │ → 转换源码（TS→JS）
├─────────────────────────────┤
│ 4. 缓存中间件                 │ → 命中缓存则直接返回
├─────────────────────────────┤
│ 5. 错误处理中间件             │ → 捕获并美化错误
└─────────────────────────────┘
    ↓
返回处理后的代码给浏览器
```

每个中间件负责一个环节，请求依次流过，最终得到可执行的代码。

## 3.7 模块图谱（Module Graph）

Vite 维护一个**模块图谱**，记录所有模块及其依赖关系：

```
main.tsx
  ├── App.tsx
  │     ├── Sidebar.tsx
  │     ├── Dashboard.tsx
  │     └── index.css
  └── index.css
```

模块图谱的作用：
1. **HMR 边界计算**：当某个模块变化时，通过图谱找到受影响的模块，决定更新范围
2. **缓存失效**：模块变化时，标记相关缓存失效
3. **循环依赖检测**：帮助发现潜在的循环依赖问题

## 3.8 依赖预构建系统

**依赖预构建**（Dependency Pre-bundling）是 Vite 的关键优化。

**问题**：`node_modules` 中的依赖通常是 CommonJS 格式（如 `module.exports = ...`），浏览器无法直接理解。而且一个依赖可能由上百个小文件组成，逐个请求会很慢。

**解决方案**：开发服务器首次启动时，用 esbuild 把所有依赖预构建成**单个 ESM 文件**，缓存在 `node_modules/.vite/`：

```
node_modules/lodash/ (上百个文件, CommonJS)
    ↓ esbuild 预构建
node_modules/.vite/deps/lodash.js (单个 ESM 文件)
```

这样浏览器只需请求一个文件，且是浏览器能直接运行的 ESM 格式。

> **新人小结**
>
> 你可能会注意到，首次运行 `npm run dev` 时会有一小段"预构建"时间，之后启动就很快了。这就是依赖预构建在起作用——第一次把依赖处理好并缓存，后续直接用缓存。如果你新增了依赖，Vite 会自动重新预构建。

## 3.9 CSS 处理管道

Vite 对 CSS 的处理同样精心设计：

**开发时**：
- CSS 文件被转换成 JavaScript 模块（通过 `<style>` 标签注入页面）
- 支持 HMR：修改 CSS 后，样式立即更新，不刷新页面
- 支持 CSS 预处理器（Sass、Less、Stylus）和 PostCSS

**构建时**：
- 所有 CSS 被提取并合并成独立的 `.css` 文件
- 自动添加浏览器前缀（通过 PostCSS + autoprefixer）
- 压缩 CSS

## 3.10 缓存系统设计

Vite 的缓存是速度的关键保障，分为多层：

| 缓存层 | 位置 | 内容 |
|--------|------|------|
| **依赖预构建缓存** | `node_modules/.vite/` | 预构建的依赖 |
| **转换缓存** | 内存 | 已转换的源码模块 |
| **文件系统缓存** | `node_modules/.vite/` | esbuild 的转换结果 |

缓存失效策略：
- 依赖的 `../../package.json` 或锁文件变化 → 依赖缓存失效
- 源文件变化 → 对应模块缓存失效
- 配置文件变化 → 重启服务器

这种多层缓存确保了重复操作（如重启服务器）依然快速。

# 四、设计细节

这一章深入 Vite 的具体设计细节，解析那些"魔鬼藏在细节里"的部分。

## 4.1 依赖预构建的实现原理

依赖预构建的完整流程：

```
1. 扫描源代码，收集所有 import 的依赖
   （使用 esbuild 的扫描能力）
        ↓
2. 过滤出需要预构建的依赖
   （排除已经是 ESM 的、排除链接的本地包）
        ↓
3. 用 esbuild 把每个依赖打包成单个 ESM 文件
   - CommonJS → ESM 转换
   - 合并内部小文件
        ↓
4. 写入 node_modules/.vite/deps/
        ↓
5. 生成 _metadata.json 记录预构建信息
```

**触发重新预构建的条件**：
- `../../package.json` 的 dependencies 变化
- 锁文件（package-lock.json 等）变化
- 用户手动删除 `.vite` 缓存
- 配置中 `optimizeDeps` 变化

## 4.2 HMR 的设计与实现

HMR（热模块替换）的完整机制：

**1. 文件监听**：
Vite 使用 `chokidar` 监听文件系统变化。

**2. 变更传播**：
当文件变化时，Vite 通过模块图谱计算"更新边界"：
- 从变化的模块出发，向上查找
- 找到"自接受"（self-accepting）的模块作为边界
- 如果一直找到入口都没有边界，则触发整页刷新

**3. 通知浏览器**：
通过 **WebSocket** 把更新信息推送给浏览器。

**4. 浏览器更新**：
浏览器收到通知后，重新请求变化的模块，执行更新逻辑。

```
文件变化
    ↓
chokidar 检测到
    ↓
计算 HMR 边界（通过模块图谱）
    ↓
通过 WebSocket 发送更新
    ↓
浏览器重新请求模块
    ↓
执行模块的 hot.accept 逻辑
    ↓
界面更新（保留状态）
```

## 4.3 路径别名设计

路径别名让你能用简短的符号代替冗长的相对路径：

```javascript
// 配置
resolve: {
  alias: {
    '@': '/src'
  }
}

// 使用
import Foo from '@/components/Foo'  // 等价于 ../../components/Foo
```

**实现原理**：
- 开发时：开发服务器拦截请求，把 `@/` 替换为实际路径
- 构建时：Rollup 的 `@rollup/plugin-alias` 处理

**注意**：路径别名需要同时在 `vite.config` 和 `../../tsconfig.json` 中配置，否则 TypeScript 类型检查会报错（我们在项目的 `文件解析-04` 文档中详细讨论过这个问题）。

## 4.4 环境变量与模式

Vite 通过 `.env` 文件管理环境变量：

```
.env                # 所有环境加载
.env.local          # 所有环境加载，但被 git 忽略
.env.development    # 只在开发环境加载
.env.production     # 只在生产环境加载
```

**变量暴露规则**：
- 只有以 `VITE_` 为前缀的变量才会暴露给客户端代码
- 这是安全设计，防止敏感信息（如数据库密码）泄露到前端

```
# .env
VITE_API_URL=https://api.example.com   ✅ 客户端可用
DB_PASSWORD=secret                      ❌ 客户端不可用（无前缀）
```

在代码中通过 `import.meta.env.VITE_API_URL` 访问。

> **新人小结**
>
> `VITE_` 前缀是一个安全边界。任何不带这个前缀的环境变量都不会打包进前端代码。如果你发现某个环境变量在前端读不到，先检查它是不是忘了加 `VITE_` 前缀。同时，**永远不要把真正的密钥放在 `VITE_` 变量里**，因为它们会暴露在客户端代码中。

## 4.5 静态资源处理

Vite 对静态资源（图片、字体、视频等）有智能处理：

| 资源类型 | 处理方式 |
|---------|---------|
| 小于阈值（默认 4KB） | 内联为 base64，减少请求 |
| 大于阈值 | 输出为独立文件，加内容哈希 |
| 特殊后缀（如 `?raw`） | 以字符串形式导入 |
| 特殊后缀（如 `?url`） | 返回文件的 URL |

```javascript
import logo from './logo.png'
// 小图片：logo 是 base64 字符串
// 大图片：logo 是 '/assets/logo-abc123.png'
```

## 4.6 插件钩子执行顺序

Vite 插件的钩子按特定顺序执行。理解这个顺序对编写插件至关重要：

**开发服务器启动顺序**：
1. `options`（修改配置）
2. `config`（修改配置）
3. `configResolved`（配置确定后）
4. `configureServer`（配置服务器）
5. `buildStart`
6. 请求到来时：`resolveId` → `load` → `transform`

**插件排序**：
- 通过 `enforce: 'pre'` 或 `enforce: 'post'` 控制插件在普通插件之前或之后执行
- 默认插件在中间执行

## 4.7 中间件设计

Vite 开发服务器基于 **Connect**（一个极简的中间件框架）。每个中间件是一个函数：

```javascript
function middleware(req, res, next) {
  // 处理请求
  // 调用 next() 传递给下一个中间件
}
```

Vite 内置了多个中间件，按顺序处理：
1. **时间中间件**：记录请求耗时
2. **CORS 中间件**：处理跨域
3. **代理中间件**：处理代理请求
4. **基础路径中间件**：处理 `base` 配置
5. **静态资源中间件**：服务静态文件
6. **转换中间件**：转换源码
7. **HTML 中间件**：处理 `index.html`

插件可以通过 `configureServer` 钩子插入自己的中间件。

## 4.8 WebSocket 通信协议

Vite 使用 WebSocket 实现服务器与浏览器的实时通信，主要用于 HMR。

**为什么需要 WebSocket 而不是纯 HTTP？**

这是一个常见的疑问：既然浏览器最终是通过 HTTP 请求获取新代码的，为什么还要引入 WebSocket？

核心原因在于 **HTTP 是"请求-响应"模型**——浏览器必须先发起请求，服务器才能回复。但 HMR 的场景是：

1. 开发者在编辑器里修改了 `Sidebar.tsx` 并保存
2. **服务器检测到文件变化**（不是浏览器触发的）
3. 服务器需要**主动通知**浏览器"有更新了"

这个"服务器主动推送通知"的需求，HTTP 做不到。所以需要 WebSocket——一个**双向、持久连接**的协议，允许服务器随时向浏览器推送消息。

**WebSocket 和 HTTP 的分工**：

| 协议 | 职责 | 方向 | 时机 |
|------|------|------|------|
| **WebSocket** | 推送"更新通知" | 服务器 → 浏览器 | 文件变化时，服务器主动推送 |
| **HTTP** | 获取"新代码内容" | 浏览器 → 服务器 | 收到通知后，浏览器发起请求 |

两者配合使用，各司其职：WebSocket 负责"告诉你有更新了"，HTTP 负责"把新代码给你"。

**完整通信流程**：

```
─────────────────────────────────────────────────────┐
│  开发阶段                                            │
└─────────────────────────────────────────────────────┘

1. 页面首次加载时
   浏览器 ──HTTP GET /src/main.tsx──▶ Vite 服务器
   ◀──返回 main.tsx 的 JavaScript──
   
   同时，Vite 注入的 HMR 客户端代码执行：
   const ws = new WebSocket('ws://localhost:5173/')
   ws.onmessage = (event) => {
     // 收到更新通知，重新请求变化的模块
   }
        ↓
2. 开发者修改 Sidebar.tsx 并保存
        ↓
3. chokidar（文件监听器）检测到文件变化
        ↓
4. Vite 服务器通过 WebSocket 主动推送：
   ws.send(JSON.stringify({
     type: 'update',
     updates: [{ path: '/src/components/Sidebar.tsx' }]
   }))
        ↓
5. 浏览器收到 WebSocket 消息
        ↓
6. HMR 客户端重新请求变化的模块：
   浏览器 ──HTTP GET /src/components/Sidebar.tsx?t=12345──▶ Vite
   （注意：这是新的 HTTP 请求，带时间戳避免缓存）
        ↓
7. Vite 转换并返回新代码
        ↓
8. 浏览器执行 hot.accept 回调，更新界面
```

**关键理解**：

- **WebSocket 只用于"通知"**：它不传输实际的代码内容，只是告诉浏览器"哪个文件变了"
- **HTTP 用于"传输代码"**：浏览器收到通知后，像正常加载模块一样发起 HTTP 请求获取新代码
- **时间戳参数 `?t=12345`**：确保浏览器不会使用缓存的旧版本

**消息类型**：
- `connected`：WebSocket 连接建立
- `update`：模块更新（触发 HMR）
- `full-reload`：需要整页刷新（如配置文件变化）
- `error`：构建错误（显示错误遮罩层）

> **新人小结**
>
> 你可以把 WebSocket + HTTP 的配合想象成**外卖配送**：
> - WebSocket = 骑手打电话通知你"餐到了"（主动推送通知）
> - HTTP = 你去门口取餐（你主动去拿东西）
>
> 如果只用 HTTP，就像你得每隔几秒就去门口看看餐到没到——效率极低。有了 WebSocket，骑手会主动通知你，你只需要在接到通知后去取就行。这就是为什么 HMR 需要两种协议配合。

## 4.9 Source Map 处理

Source Map 让浏览器能把运行时的错误映射回源代码位置，方便调试。

**开发时**：
- 默认生成 Source Map，支持精确的断点调试
- 错误遮罩层（error overlay）能显示源码位置和调用栈

**构建时**：
- 默认不生成 Source Map（减小产物体积）
- 可通过 `build.sourcemap: true` 开启

Vite 确保 Source Map 在多层转换（TS→JS、JSX→JS）后依然准确，这需要各转换工具正确传递 source map 链。

## 4.10 错误处理与错误遮罩层

开发时，Vite 提供了优秀的错误处理体验：

**编译错误**：
- 在终端显示详细错误
- 在浏览器显示**错误遮罩层**（error overlay），包含：
  - 错误信息
  - 出错的源码位置（文件、行号、列号）
  - 出错代码的上下文片段

**运行时错误**：
- 捕获未处理的异常
- 通过 WebSocket 上报并显示

**错误遮罩层的设计**：
- 半透明黑色背景
- 红色错误信息
- 可点击跳转到编辑器（如果配置了编辑器集成）
- 按 Esc 关闭

这大大提升了开发时的调试效率——出错时不用切到终端，直接在浏览器看到问题所在。

# 五、工作原理

这一章从"执行流程"的角度，解析 Vite 在开发和构建两个阶段到底做了什么。

## 5.1 开发服务器的启动流程

完整的启动流程：

```
执行: vite (或 npm run dev)
    ↓
1. 解析命令行参数
    ↓
2. 加载配置文件 (vite.config.ts)
   - 用 esbuild 把 TS 配置编译成 JS
   - 执行配置，合并默认配置
    ↓
3. 解析环境变量 (.env 文件)
    ↓
4. 依赖预构建（如果需要）
   - 扫描依赖
   - esbuild 预构建到 .vite 缓存
    ↓
5. 创建 HTTP 服务器 (基于 Connect)
   - 注册所有内置中间件
   - 执行插件的 configureServer 钩子
    ↓
6. 启动 WebSocket 服务器 (用于 HMR)
    ↓
7. 启动文件监听器 (chokidar)
    ↓
8. 监听端口，开始接受请求
    ↓
打印: Local: http://localhost:5173/
```

关键点：**整个启动过程不做任何源码的全量转换**，所以非常快。

## 5.2 模块请求的处理流程

当浏览器请求一个模块时：

```
浏览器请求: /src/App.tsx
    ↓
1. 中间件链开始处理
    ↓
2. 检查是否是静态资源
   - 是 → 直接返回
   - 否 → 继续
    ↓
3. 检查缓存
   - 命中 → 返回缓存
   - 未命中 → 继续
    ↓
4. 解析模块 (resolveId)
   - 处理路径别名
   - 处理 node_modules 依赖
    ↓
5. 加载模块内容 (load)
    ↓
6. 转换模块 (transform)
   - TypeScript → JavaScript (esbuild)
   - JSX → JavaScript
   - 处理 import（重写依赖路径）
    ↓
7. 缓存结果
    ↓
8. 返回 JavaScript 给浏览器
```

## 5.3 HMR 的工作原理

一个完整的 HMR 周期：

```
开发者修改 Sidebar.tsx
    ↓
chokidar 检测到文件变化
    ↓
Vite 使 Sidebar.tsx 的缓存失效
    ↓
通过模块图谱计算更新边界：
  - Sidebar.tsx 是否自接受更新？
  - 如果否，向上查找父模块（App.tsx）
  - 找到最近的接受边界
    ↓
通过 WebSocket 发送 update 消息：
  { type: 'update', updates: [{ path: '/src/components/Sidebar.tsx', ... }] }
    ↓
浏览器收到消息
    ↓
浏览器重新请求 Sidebar.tsx（带时间戳参数避免缓存）
    ↓
Vite 转换并返回新的 Sidebar 代码
    ↓
浏览器执行模块的 hot.accept 回调
    ↓
React 重新渲染 Sidebar 组件（保留其他组件状态）
    ↓
界面更新完成
```

**关键点**：整个过程只涉及变化的模块，不重新打包，所以极快。

## 5.4 生产构建的流程

```
执行: vite build
    ↓
1. 加载配置（同开发，但 mode=production）
    ↓
2. 生成 Rollup 配置
   - 入口：index.html
   - 插件：所有 Vite 插件 + Rollup 插件
   - 输出：dist/
    ↓
3. Rollup 开始构建：
   a. 解析 index.html，提取 <script> 入口
   b. 从入口递归解析所有依赖
   c. 调用插件转换每个模块（TS→JS、JSX→JS）
   d. Tree Shaking（移除未使用的导出）
   e. 代码分割（动态 import 拆分包）
   f. 生成 chunk
    ↓
4. 处理 CSS：
   - 提取所有 CSS
   - PostCSS 处理（前缀、压缩）
   - 输出独立 .css 文件
    ↓
5. 处理静态资源：
   - 小资源内联
   - 大资源加哈希输出
    ↓
6. 生成最终的 index.html（注入资源链接）
    ↓
7. 输出到 dist/
```

## 5.5 依赖扫描与预构建的深入

依赖预构建的扫描机制：

**扫描方式**：
- 使用 esbuild 的 `metafile` 能力，快速扫描所有 `import` 语句
- 收集所有从 `node_modules` 导入的依赖

**哪些依赖会被预构建**：
- ✅ CommonJS 格式的依赖（需要转成 ESM）
- ✅ 由大量小文件组成的依赖（需要合并）
- ❌ 已经是标准 ESM 的依赖（无需处理）
- ❌ 链接的本地包（`link:` 或 `file:` 协议）

**预构建的产物**：
```
node_modules/.vite/deps/
├── react.js          # react 预构建产物
├── react-dom.js      # react-dom 预构建产物
├── recharts.js       # recharts 预构建产物
└── _metadata.json    # 预构建元信息
```

## 5.6 代码分割（Code Splitting）

代码分割把应用拆成多个小块，按需加载。

**分割的触发方式**：
1. **动态 import**：`import('./HeavyComponent')` 会创建一个新 chunk
2. **多入口**：多个入口文件各自成为 chunk
3. **共享依赖**：被多个 chunk 引用的依赖被提取为公共 chunk

**好处**：
- 首屏只加载必要的代码，加快首次加载
- 用户导航到新页面时才加载对应代码

```javascript
// 动态导入，HeavyComponent 会被拆分成独立 chunk
const HeavyComponent = React.lazy(() => import('./HeavyComponent'))
```

## 5.7 Tree Shaking 原理

Tree Shaking 移除"未使用的代码"，减小产物体积。

**原理**：基于 ESM 的静态结构分析。
- ESM 的 `import`/`export` 是静态的，编译时就能确定
- 构建工具分析哪些导出被实际使用
- 未被使用的导出被标记为"死代码"并移除

**示例**：
```javascript
// utils.js
export function used() { ... }     // 被使用，保留
export function unused() { ... }   // 未使用，移除
```

**为什么 CommonJS 难以 Tree Shaking**：
- CommonJS 的 `require` 是动态的，运行时才确定
- 无法静态分析哪些导出被使用
- 这也是为什么生产构建必须用 ESM

## 5.8 压缩与优化

生产构建的压缩和优化：

**JavaScript 压缩**：
- 默认使用 esbuild（快）
- 可选 `build.minify: 'terser'`（压缩率更高但更慢）
- 移除注释、空白，缩短变量名

**CSS 压缩**：
- 移除空白和注释
- 合并重复规则

**其他优化**：
- **资源内联**：小资源转 base64
- **预加载提示**：为关键资源添加 `<link rel="modulepreload">`
- **内容哈希**：文件名包含内容哈希，优化浏览器缓存

## 5.9 HTML 生成与注入

`index.html` 是 Vite 应用的入口。构建时，Vite 会处理它：

**开发时**：
- 直接服务 `index.html`
- `<script type="module" src="/src/main.tsx">` 指向源码

**构建时**：
- 解析 `index.html` 中的 `<script>` 和 `<link>` 标签
- 把源码入口替换为构建后的资源
- 注入预加载提示

```html
<!-- 开发时 -->
<script type="module" src="/src/main.tsx"></script>

<!-- 构建后 -->
<script type="module" crossorigin src="/assets/index-abc123.js"></script>
<link rel="stylesheet" crossorigin href="/assets/index-def456.css">
```

## 5.10 性能优化策略总结

Vite 的速度来自多个层面的优化：

| 层面 | 优化手段 | 效果 |
|------|---------|------|
| **启动** | 不打包，按需转换 | 启动速度与项目大小无关 |
| **依赖** | esbuild 预构建 + 缓存 | 依赖只处理一次 |
| **转换** | esbuild 转换（Go 编写） | 比 Babel 快 10-100 倍 |
| **HMR** | 原生 ESM，只更新变化模块 | 更新速度与项目大小无关 |
| **缓存** | 多层缓存（内存 + 文件系统） | 重复操作极快 |
| **构建** | esbuild 预压缩 + Rollup | 构建快且产物优 |

# 六、工作流程

这一章从"开发者日常操作"的角度，梳理各种典型工作流的完整步骤。

## 6.1 项目初始化的完整流程

创建一个新 Vite 项目：

```
1. 执行脚手架命令
   npm create vite@latest my-app
        ↓
2. 选择框架和变体
   - 框架：React / Vue / Svelte / ...
   - 变体：TypeScript / JavaScript
        ↓
3. 脚手架生成项目结构
   my-app/
   ├── index.html
   ├── package.json
   ├── vite.config.ts
   ├── tsconfig.json
   └── src/
        ├── main.tsx
        ├── App.tsx
        └── ...
        ↓
4. 进入目录，安装依赖
   cd my-app && npm install
        ↓
5. 启动开发服务器
   npm run dev
        ↓
6. 浏览器访问，开始开发
```

## 6.2 开发模式的完整流程

日常开发的循环：

```
1. 启动开发服务器
   npm run dev
        ↓
2. 浏览器打开应用
   http://localhost:5173
        ↓
3. 编写/修改代码
        ↓
4. 保存文件
        ↓
5. Vite 检测到变化，触发 HMR
        ↓
6. 浏览器自动更新（保留状态）
        ↓
7. 查看效果，继续修改
   （回到第 3 步）
```

这个循环的核心优势是**第 5-6 步极快**，让开发者能保持心流。

## 6.3 调试与排查流程

遇到问题时的排查步骤：

**问题 1：依赖无法解析**
```
1. 检查依赖是否已安装 (npm install)
2. 检查 import 路径是否正确
3. 删除 .vite 缓存，重新预构建
   rm -rf node_modules/.vite
4. 重启开发服务器
```

**问题 2：HMR 不生效**
```
1. 检查浏览器控制台是否有 HMR 错误
2. 检查模块是否有循环依赖
3. 确认框架插件正确配置（如 @vitejs/plugin-react）
4. 检查是否触发了整页刷新（而非 HMR）
```

**问题 3：构建失败**
```
1. 阅读错误信息，定位出错文件
2. 运行 tsc --noEmit 检查类型错误
3. 检查是否有语法错误
4. 检查依赖版本兼容性
```

## 6.4 生产构建的完整流程

```
1. 运行构建命令
   npm run build
        ↓
2. Vite 执行构建（参见 5.4）
        ↓
3. 产物输出到 dist/
   dist/
   ├── index.html
   └── assets/
        ├── index-abc123.js
        └── index-def456.css
        ↓
4. 本地预览构建结果
   npm run preview
   （启动一个静态服务器服务 dist/）
        ↓
5. 验证功能正常
        ↓
6. 部署到生产环境
```

> **新人小结**
>
> `npm run preview` 是一个容易被忽略但很有用的命令。它让你在部署前，用接近生产的方式（静态文件服务）验证构建产物。很多"开发时正常、部署后出问题"的 bug，都能在这一步被发现。

## 6.5 部署流程

Vite 构建产物是纯静态文件，部署非常灵活：

```
1. 构建产物 (dist/)
        ↓
2. 选择部署目标：
   - 静态托管：Netlify / Vercel / GitHub Pages
   - 传统服务器：Nginx / Apache
   - CDN：配合缓存策略
        ↓
3. 配置服务器：
   - 对于 SPA，配置路由回退（所有路径返回 index.html）
   - 配置缓存策略（带哈希的资源长缓存，index.html 不缓存）
        ↓
4. 上传/同步产物
        ↓
5. 验证线上功能
```

**Nginx 配置示例**（SPA 路由回退）：
```nginx
location / {
  try_files $uri $uri/ /index.html;
}
```

## 6.6 插件开发流程

开发一个自定义 Vite 插件：

```
1. 明确插件要解决的问题
   （如：自动注入版本号到页面）
        ↓
2. 创建插件文件
   my-plugin.ts
        ↓
3. 实现插件钩子
   export default function myPlugin() {
     return {
       name: 'my-plugin',
       transformIndexHtml(html) {
         return html.replace('__VERSION__', '1.0.0')
       }
     }
   }
        ↓
4. 在 vite.config.ts 中注册插件
   plugins: [myPlugin()]
        ↓
5. 测试插件（开发 + 构建）
        ↓
6. 发布到 npm（如果需要共享）
```

## 6.7 多环境配置流程

管理开发、测试、生产多套环境：

```
1. 创建环境文件
   .env.development    # 开发
   .env.staging        # 测试
   .env.production     # 生产
        ↓
2. 在每个文件中定义变量
   # .env.development
   VITE_API_URL=http://localhost:8080

   # .env.production
   VITE_API_URL=https://api.example.com
        ↓
3. 在代码中使用
   const apiUrl = import.meta.env.VITE_API_URL
        ↓
4. 通过 --mode 指定环境
   vite build --mode staging
```

## 6.8 CI/CD 集成流程

在持续集成中构建和部署：

```
1. 代码推送到仓库
        ↓
2. CI 触发（GitHub Actions / GitLab CI / Jenkins）
        ↓
3. 安装依赖
   npm ci  （使用锁文件，确保版本一致）
        ↓
4. 类型检查
   npx tsc --noEmit
        ↓
5. 运行测试
   npm test
        ↓
6. 构建
   npm run build
        ↓
```

## 6.9 从 Webpack 迁移到 Vite 的流程

迁移现有 Webpack 项目：

```
1. 评估迁移可行性
   - 检查是否有 Vite 不支持的 Webpack 特性
   - 检查依赖的兼容性
        ↓
2. 安装 Vite 和对应框架插件
   npm install -D vite @vitejs/plugin-react
        ↓
3. 创建 vite.config.ts，迁移关键配置
   - 路径别名
   - 代理
   - 环境变量
        ↓
4. 调整入口文件
   - 确保 index.html 在根目录
   - 确保 <script> 用 type="module"
        ↓
5. 处理 Webpack 特有的功能
   - require.context → import.meta.glob
   - module.hot → import.meta.hot
   - process.env → import.meta.env
        ↓
6. 逐步验证
   - 先跑通开发模式
   - 再验证生产构建
        ↓
7. 移除 Webpack 相关依赖和配置
```

## 6.10 性能调优流程

当项目变大、性能下降时的调优步骤：

```
1. 定位瓶颈
   - 启动慢？→ 检查依赖预构建
   - HMR 慢？→ 检查是否有循环依赖
   - 构建慢？→ 分析 Rollup 构建日志
        ↓
2. 优化依赖预构建
   - 用 optimizeDeps.include 预构建大型依赖
   - 用 optimizeDeps.exclude 排除无需预构建的
        ↓
3. 优化代码分割
   - 合理拆分路由
   - 避免过大的单个 chunk
        ↓
4. 优化构建
   - 调整 build.rollupOptions
   - 考虑使用 build.commonjsOptions
        ↓
5. 使用性能分析工具
   - vite --profile 生成性能分析
   - 用 rollup-plugin-visualizer 可视化包体积
```

# 七、发展历程

这一章回顾 Vite 从诞生到现在的演进历程，理解每个重大版本带来了什么。

## 7.1 Vite 1.0 时代（2020）

**发布时间**：2020 年

**背景**：作为 Vue 3 的配套工具诞生。

**核心特征**：
- 最初只支持 Vue
- 开发服务器基于原生 ESM
- 生产构建基于 Rollup
- 引入了依赖预构建的概念

**局限**：
- 框架绑定（主要服务 Vue）
- 插件系统还不够成熟
- 配置选项较少

Vite 1.0 验证了"开发不打包"这一核心思想的可行性，引起了社区广泛关注。

## 7.2 Vite 2.0 时代（2021）

**发布时间**：2021 年 2 月

**重大变化**：
- **框架无关**：不再绑定 Vue，通过插件支持任意框架
- **全新的插件系统**：兼容 Rollup 插件 + Vite 专有钩子
- **改进的依赖预构建**：更智能的扫描和缓存
- **CSS 预处理器支持**：内置 Sass、Less、Stylus
- **SSR 支持**：开始支持服务端渲染

Vite 2.0 是一个里程碑，它让 Vite 从"Vue 的工具"变成"通用的前端构建工具"，生态开始爆发。

## 7.3 Vite 3.0 时代（2022）

**发布时间**：2022 年 7 月

**重大变化**：
- **Vite 3 使用 esbuild 优化依赖预构建**：速度进一步提升
- **改进的 HMR**：更稳定的热更新
- **WebSocket 连接优化**：减少连接问题
- **更小的产物**：优化构建输出
- **Template 改进**：脚手架生成的模板更现代化

Vite 3.0 巩固了 Vite 在性能上的领先地位，成为新项目的首选。

## 7.4 Vite 4.0 时代（2023）

**发布时间**：2023 年 1 月

**重大变化**：
- **升级到 Rollup 3**：带来更好的性能和代码分割
- **改进的依赖扫描**：更准确的依赖发现
- **esbuild 版本升级**：更快的转换速度
- **配置改进**：更灵活的配置选项
- **破坏性变更**：移除了一些废弃的 API

Vite 4.0 的重点是底层引擎升级和稳定性提升。

## 7.5 Vite 5.0 时代（2023-2024）

**发布时间**：2023 年 11 月

**重大变化**：
- **要求 Node.js 18+**：利用新版 Node 的能力
- **Rollup 4**：构建性能进一步提升
- **`vite preview` 改进**：更好地模拟生产环境
- **API 稳定化**：为未来的 Rolldown 做准备
- **性能优化**：启动和构建速度持续提升

Vite 5.0 是一个承上启下的版本，开始为 Rolldown 的整合铺路。

## 7.6 Vite 6.0 时代（2024-2025）

**发布时间**：2024 年底

**重大变化**：
- **Environment API**：统一的开发/构建环境抽象
- **为 Rolldown 做准备**：逐步引入 Rolldown 相关能力
- **默认配置优化**：更合理的开箱即用体验
- **性能持续提升**

我们项目使用的就是 Vite 6.0（`../../package.json` 中 `"vite": "^6.0.3"`）。

## 7.7 核心团队的演进

Vite 的开发模式也值得一提：

- **创始人**：尤雨溪（Evan You）
- **核心团队**：逐渐扩展为一个国际化的开源团队
- **治理模式**：通过 RFC 流程讨论重大变更
- **资金来源**：通过 GitHub Sponsors、Open Collective 等获得赞助

Vite 团队还孵化了多个相关项目：
- **Vitest**：基于 Vite 的单元测试框架
- **Rolldown**：用 Rust 编写的打包器（见 7.8）

## 7.8 Rolldown 的崛起

**Rolldown** 是 Vite 团队正在开发的、用 **Rust** 编写的打包器，目标是**统一 Vite 的开发和构建引擎**。

**为什么需要 Rolldown**：
- 当前 Vite 开发用 esbuild、构建用 Rollup，两套引擎有行为差异
- 这种差异可能导致"开发正常、构建出错"的问题
- Rolldown 旨在用单一引擎同时服务开发和构建

**现状**（截至 2025）：
- Rolldown 仍在积极开发中
- 设计目标是兼容 Rollup 插件 API
- 未来会逐步整合进 Vite，最终替代 esbuild + Rollup 的双引擎架构

> **新人小结**
>
> Rolldown 代表了前端工具链的一个重要趋势：**用 Rust/Go 等编译型语言重写工具链，追求极致性能**。类似的还有 esbuild（Go）、SWC（Rust）、Turbopack（Rust）。理解这个趋势，能帮你把握前端基建的未来方向。

## 7.9 生态发展

Vite 的成功带动了整个生态的繁荣：

**框架集成**：
- **Nuxt 3**（Vue）：默认使用 Vite
- **SvelteKit**（Svelte）：默认使用 Vite
- **Remix**（React）：支持 Vite
- **Astro**：基于 Vite 构建

**测试工具**：
- **Vitest**：与 Vite 深度集成的测试框架，复用 Vite 的转换能力

**其他工具**：
- **vite-plugin-pwa**：PWA 支持
- **vite-plugin-inspect**：调试插件
- **rollup-plugin-visualizer**：包体积可视化

Vite 已经成为现代前端工程化的事实标准之一。

## 7.10 未来展望与趋势

展望 Vite 和前端构建工具的未来：

**1. Rolldown 整合**：
- 统一开发和构建引擎
- 消除双引擎的行为差异
- 进一步提升性能

**2. 更快的工具链**：
- Rust/Go 编写的工具将成主流

**3. 更智能的默认配置**：

> **新人小结**

> 作为新人，你不需要掌握所有这些历史细节，但理解"为什么会有 Vite"能帮你更好地使用它。记住核心主线：**浏览器原生支持 ESM → 开发可以不打包 → 用 Rust/Go 工具提速 → 追求极致的开发体验**。这条主线会贯穿前端工具链的未来演进。

## 总结

Vite 的出现，标志着前端构建工具从"功能优先"走向"体验优先"。它的核心贡献可以概括为三点：

1. **重新定义了开发体验**：通过"开发不打包 + 原生 ESM"，让启动和热更新达到毫秒级
2. **双引擎架构的智慧**：承认开发和生产诉求不同，用 esbuild 和 Rollup 分别优化
3. **开放可扩展的生态**：框架无关 + 插件系统，让 Vite 成为通用的基建

对于我们的项目（desktop-app-template），Vite 承担的是**渲染进程**的构建职责——把 React + TypeScript 代码快速编译并提供给 Electron 窗口。理解 Vite 的工作原理，能帮你在遇到构建问题时快速定位和解决。
